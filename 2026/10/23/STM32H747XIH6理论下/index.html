4.14 IIC

IIC，通常也写作 I2C，是嵌入式里最常见的串行通信总线之一。
它最大的特点很简单：只用两根线，就能让主控和多个外设通信。
像 EEPROM、RTC、温湿度传感器、OLED、触摸芯片这类器件，经常都挂在 IIC 总线上。

4.14.1 什么是IIC

IIC 的全称是 Inter-Integrated Circuit。
它是一种同步、串行、半双工通信协议。
这里几个关键词要先理解：

  • **同步：**有单独的时钟线
  • **串行：**数据一位一位传
  • **半双工：**同一时刻一般只能单方向传输
  • **总线型：**多个设备可以挂在同一组线上

IIC 解决的问题，本质上就是：
主控怎么用尽量少的引脚，去连接多个外设。

4.14.2 IIC 只需要哪两根线

IIC 总线只需要两根信号线：

  • SCL：时钟线
  • SDA：数据线

其中：

  • SCL 由主机发出时钟节拍
  • SDA 用来传输数据

但 IIC 还有一个很重要的电气特点：
SCL 和 SDA 都是开漏/开集电极结构，必须配上拉电阻。

也就是说，IIC 设备只能主动把线拉低，不能主动输出高电平。
当没有器件拉低总线时，线上的高电平是靠上拉电阻提供的。

所以你在原理图里经常会看到：

  • SCL 接一个上拉电阻到 VCC
  • SDA 接一个上拉电阻到 VCC

如果没有上拉，IIC 总线通常是跑不起来的。

4.14.3 IIC的通信过程是怎么进行的

IIC 通信不是随便发数据，它有一套固定流程。
一帧最典型的 IIC 通信，大致是这样：

  1. 主机发送起始信号
  2. 主机发送从机地址
  3. 主机发送读写方向位
  4. 从机返回应答
  5. 主机和从机传输数据
  6. 每发完 1 个字节，对方返回一次应答
  7. 最后发送停止信号

这里最重要的几个概念是：

  • Start：起始信号
  • Stop：停止信号
  • ACK：应答
  • NACK：非应答

你可以把它理解成两个人对话：

  • 主机先说“我要开始说话了”
  • 再说“我要找谁”
  • 再说“我是要读还是要写”
  • 对方回应“我在”
  • 然后双方开始真正传数据
  • 最后主机说“这次通信结束”

4.14.4 起始信号、停止信号、应答信号分别是什么

这是 IIC 最基础也最关键的部分。

起始信号 Start
当 SCL 保持高电平时，SDA 从高电平跳变到低电平，这就表示起始信号。
也就是说：

  • 时钟线高
  • 数据线高变低
  • 表示通信开始

停止信号 Stop
当 SCL 保持高电平时，SDA 从低电平跳变到高电平，这就表示停止信号。
也就是说：

  • 时钟线高
  • 数据线低变高
  • 表示通信结束

应答信号 ACK
IIC 按字节传输，每发完 8 位数据，接收方都要在第 9 个时钟给出应答。

  • 拉低 SDA：表示 ACK
  • 不拉低 SDA：表示 NACK

这一步非常重要，因为它告诉发送方：

  • 数据我收到了
  • 或者我没收到/不想继续了

4.14.5 IIC 的读写到底是怎么区分的

IIC 通信里，地址后面会带一个读写位。
通常是：

  • 0：写
  • 1：读

比如主机要给 EEPROM 写数据，流程一般是：

  • 起始
  • 从机地址 + 写位
  • 应答
  • 寄存器地址或存储地址
  • 应答
  • 数据
  • 应答
  • 停止

如果主机要从器件读数据，流程一般会稍复杂一点，常见是：

  • 起始
  • 从机地址 + 写位
  • 应答
  • 先告诉对方要读哪个寄存器地址
  • 重起始
  • 从机地址 + 读位
  • 应答
  • 从机发送数据
  • 主机应答/非应答
  • 停止

所以 IIC 读数据经常不是“直接读”，而是：
先写地址，再重新开始读数据。
这也是很多传感器、EEPROM 读操作的标准流程。

  • 为什么主机读从机的数据多几个步骤
    I2C 从机不知道你接下来要读哪个寄存器，必须先发一次“写操作”，把要读取的寄存器编号发给从机；重起始（Repeated Start） 用来切换方向，变成读，不发停止信号、不释放总线。

拆开讲
1.I2C 的从机内部有一个「寄存器地址指针」
从机（EEPROM、传感器、OLED）里有很多寄存器，你想读哪一个，要先告诉它。
告诉它地址这件事，只能用【写方向】 发给从机。

这一步不是写数据，只是设置从机内部的读取指针，让它指向你想要读的那个寄存器。

2.正常流程对比

  • 写操作：Start → 从地址+W → 寄存器地址 → 数据 → Stop
  • 读操作（标准）：Start → 从地址+W →【发寄存器地址】→ Repeated Start → 从地址+R → 接收数据 → Stop

为什么不能发 Stop？
如果这里发 Stop，总线就释放了，从机就会把刚才设置的寄存器指针丢掉，不知道你等下要读哪里。

3.重起始的作用

  • 不发送停止，不结束本次总线会话，保留刚才设置好的寄存器指针
  • 直接再次发起起始信号，把读写位改成读（R=1）
  • 通知从机：好了，地址我告诉你了，现在我要读这个地址里面的数据，你把数据发出来

4.14.6 为什么 IIC 可以挂多个设备

因为 IIC 是靠地址区分设备的。
在同一条总线上，可以同时挂多个从机。
主机发起通信时，先发送从机地址，只有地址匹配的那个设备才会响应，其它设备保持安静。

所以 IIC 的优势很明显：

  • 节省引脚
  • 布线简单
  • 一个主控能挂多个外设

但它也有一个限制：
同一条总线上，设备地址不能冲突。
如果两个设备地址一样，它们就可能同时响应，通信会混乱。

4.14.7 IIC 常见速度模式有哪些

IIC 并不是只有一种速度，常见模式有：

  • 标准模式：100kHz
  • 快速模式：400kHz
  • 快速模式增强：1MHz
  • 高速模式：3.4MHz

在实际项目里，最常见的还是：

  • 100kHz
  • 400kHz

如果你接的是 EEPROM、RTC、普通传感器，100kHz 和 400kHz 通常就够用了。

速度不是越高越好，因为速度越高，对下面这些要求也越高：

  • 走线质量
  • 上拉电阻选择
  • 总线电容
  • 芯片本身支持能力

所以很多项目里，IIC 不稳定时，第一件事不是怀疑协议，而是先把速度降下来试试。

4.14.9 IIC 最容易出问题的地方有哪些

IIC 看起来简单，但它很容易卡在细节上。
最常见的问题有这些：

  • 没加上拉电阻
  • 上拉电阻选得不合适
  • 器件地址搞错
  • 7 位地址和 8 位地址混淆
  • 读流程里漏掉重复起始
  • 写 EEPROM 后没等内部写周期完成
  • 总线被某个从机一直拉低
  • 时钟速度开太高
  • GPIO 复用、开漏模式配置不对

其中有一个特别经典的问题：
很多芯片手册给的是 8 位地址，而 STM32 HAL 有时用的是 7 位地址左移后的格式。
这个地方一旦搞混，现象通常就是：

  • 总线有波形
  • 但设备始终不应答

4.14.10 总结

IIC 的核心并不复杂，它就是一套“两根线 + 地址 + 时序”的通信协议。
你可以把最重要的几句话记住：

  • IIC 只有两根线：SCL 和 SDA
  • 它是同步、串行、半双工总线
  • 总线必须有上拉电阻
  • 通信靠起始、地址、应答、数据、停止来组织
  • 多设备共线靠地址区分
  • IIC 很适合连接 EEPROM、RTC、传感器等低速外设

4.15 EEPROM（BL24C16F）

  • EEPROM 是什么？
    EEPROM（Electrically Erasable Programmable Read-Only Memory，电可擦可编程只读存储器）是一种非易失性存储器：断电后数据仍保留，需要时可用电擦写。

和 Flash、RAM 的常见对比：

类型 断电后 擦写方式 典型用途
RAM 数据丢失 随时读写 程序运行变量
Flash 保留 按块擦，再写 程序固件、大容量存储
EEPROM 保留 按字节/页擦写 配置参数、校准值、序列号

  • 主要特点
    1.非易失：适合存“掉电也要记住”的数据（设备 ID、校准系数、用户设置等）。
    2.按字节或页写：比 Flash 更细粒度，改几个字节不必整片擦除。
    3.擦写次数有限：常见约 10 万 ~ 100 万次（芯片不同），不能当 RAM 频繁写。
    4.写入较慢：单次写常需几毫秒（内部自定时），读一般较快。
    5.容量偏小：几 Kbit 到几 Mbit 都常见，你用的 BL24C16F 是 16Kbit（2KB）。

  • 常见接口

  • I²C（如 BL24C16F）：两根线 SCL/SDA，接线少，MCU 常用。
  • SPI：速度更高，引脚稍多。
  • 也有并行接口，嵌入式里 I²C/SPI 更常见。
  • 典型应用场景
  • 保存 MAC、序列号、产品配置
  • 校准数据（ADC 增益/偏移、传感器零点）
  • 用户设置（亮度、语言、上次工作模式）
  • 运行日志/计数（注意擦写寿命，可做磨损均衡）

  • 使用时要注意的几点
    1.写前不必整片擦：I²C EEPROM 一般可直接覆盖写，但要以手册为准。
    2.写保护 WP：拉高 WP 可禁止写入，防止误改。
    3.地址与容量：16Kbit = 2048 字节，I²C 设备地址由 A0/A1/A2 等引脚决定。
    4.页写限制：很多芯片一页 16 字节，跨页写要分两次，否则地址会回绕。
    5.寿命：同一地址不要高频写，重要参数可配合 Flash 或做写次数统计。

  • 从设备获取

BL24C16F 和普通 I2C 传感器不一样：它的从机地址不是固定一个值，而是和你要访问的存储位置有关。
先看芯片容量
BL24C16F 是 16 Kbit = 2048 字节 = 2 KB。
要表示 2048 个地址，需要：
2^11=2048
所以内部地址是 11 位：A10 ~ A0。
地址格式如下：

B7 B6 B5 B4 B3 B2 B1 B0
1 0 1 0 A10 A9 A8 R/W

含义：

位 含义
B7~B4 固定为 1010，表示这是 EEPROM 类器件
B3~B1 存储地址的高 3 位：A10、A9、A8
B0 读/写位：0=写，1=读

也就是说：

  • A10、A9、A8 → 放进 I2C 设备地址
  • A7 ~ A0 → 作为“字地址”单独发出去

I2C 7 位地址只有 7 位可用，而 EEPROM 有 11 位地址，多出来的 3 位怎么办？

芯片的做法是：
把地址最高的 3 位（A10、A9、A8）编进设备地址里，
剩下的 8 位（A7~A0）当作一次传输里的“字地址”发送。

这样一块芯片在总线上相当于 8 个不同的从机地址，每个地址对应 256 字节：

A10 A9 A8 对应存储范围 大小
0 0x000 ~ 0x0FF 256 字节
1 0x100 ~ 0x1FF 256 字节
10 0x200 ~ 0x2FF 256 字节
… … …
111 0x700 ~ 0x7FF 256 字节

8 × 256 = 2048 字节，正好用完。

BL24C16F 的从机地址 = 固定前缀 1010 + 存储地址的高 3 位
代码计算方式：

  • 写操作：
    字节写（Byte Write）
    BL24C16F 写一个字节的流程如下：主机先发 START，再发 8 位设备地址（格式为 1010 + A10/A9/A8 + 0，0 表示写），EEPROM 应答 ACK 后，主机发送 1 字节字地址（A7~A0，即存储地址低 8 位），EEPROM 再次 ACK，随后主机发送 8 位数据，EEPROM 第三次 ACK，最后主机发 STOP 结束传输。STOP 之后芯片进入内部写周期 tWR（约 5ms），期间不再响应 I2C，必须等写完成才能继续操作。

页写（Page Write）
页写与字节写开头相同，区别在于 STOP 前可连续发送多个数据字节。16K 器件页大小为 16 字节，最多一次写 16 字节；每收到 1 字节 EEPROM 都会 ACK，全部发完后再发 STOP，只触发一次内部写周期，比逐字节写更高效。

页写注意事项
页写 不能跨 16 字节页边界。若一次写入超出当前页末尾，地址会在页内回绕，覆盖同页前面的数据。例如从地址 0x0E 起写 4 字节，实际只会写入 0x0E、0x0F，后 2 字节会写到 0x00、0x01。因此驱动需按页拆分，当前 BL24C16F_Write 已自动处理页边界和写周期等待。

页写时序
页写与字节写开头相同：主机发 START → 设备地址（写） → ACK → 字地址 → ACK，之后不再立即发 STOP，而是连续发送 DATA(n)、DATA(n+1)… 多个数据字节，每发 1 字节 EEPROM 都 ACK 一次，全部发完后再发 STOP，触发 一次 内部写周期。相比逐字节写，这种方式效率更高。

内部地址自增规则
页写过程中，EEPROM 每收到 1 字节数据，内部地址 自动 +1，但 只有低 4 位会递增（对应 16 字节页大小，2⁴=16）。高 7 位地址不变，因此一次页写始终在同一页内。若写入超出页末尾，地址会在 当前页内回绕 到页首，后续数据会 覆盖同页前面已写入的内容，而不是写到下一页。

应答轮询（Acknowledge Polling）
STOP 之后 EEPROM 进入内部写周期，期间 不响应任何 I2C 命令。主机可通过 应答轮询 判断是否写完：再次发 START + 设备地址，若仍在写周期内，EEPROM 不应答（NACK）；写完成后才会 ACK，表示可以开始下一次读写。当前驱动里的 BL24C16F_WaitWriteCycle 就是用 HAL_I2C_IsDeviceReady 做这件事，等价于手册里的应答轮询。


读操作：
BL24C16F 的读操作与写操作类似，区别在于设备地址最低位 R/W = 1 表示读。读操作分为三种：当前地址读、随机地址读、顺序读。

当前地址读（Current Address Read）
芯片内部有一个 地址计数器，记录上次读/写访问的位置，每次访问后自动 +1，断电前一直有效。当前地址读不需要先发字地址，主机直接发 START → 设备地址（读） → ACK，EEPROM 就从计数器当前位置 输出 1 字节数据；主机收到后 不应答（NACK），再发 STOP 结束。对应 Figure 8 的时序： START → DEVICE ADDRESS(READ) → ACK → DATA → NO ACK → STOP。

地址回绕规则
读操作读到 最后一页最后一个字节 时，地址会回绕到 第一页第一个字节；写操作则是读到 当前页末尾 时回绕到 同一页开头（不会自动进入下一页）。这与页写时低 4 位自增、高 7 位不变是一致的。

随机地址读（Random Read）
随机地址读用于从 任意指定地址 读取 1 字节，是最常用的读方式。它分两个阶段：先做一次 假写（Dummy Write） 把目标地址装入芯片内部地址计数器，再发起真正的读操作。

第一阶段：假写（定位地址）
主机发 START → 设备地址（写，R/W=0） → ACK → 字地址（A7~A0） → ACK。到这里与字节写相同，但 不发数据，也不发 STOP，目的是让 EEPROM 知道要从哪个地址读。

第二阶段：真正读取
主机立即发 重复START（Re-START） → 设备地址（读，R/W=1） → ACK → EEPROM 输出 1 字节 DATA → 主机 NACK（不应答） → STOP 结束。对应 Figure 9：DUMMY WRITE 定位地址，之后 START → DEVICE ADDRESS(READ) → ACK → DATA → NO ACK → STOP。

顺序读（Sequential Read）
顺序读不能单独发起，必须 先通过当前地址读或随机地址读定位到起始地址，之后 EEPROM 会 连续输出后续字节，无需每读 1 字节都重新发地址。

读多字节的时序
定位完成后，EEPROM 先输出 DATA(n)，主机 ACK 表示还要读；EEPROM 内部地址 +1，再输出 DATA(n+1)，主机再 ACK……如此循环。对应 Figure 10： DEVICE ADDRESS(READ) → ACK → DATA(n) → ACK → DATA(n+1) → ACK → … → DATA(n+x) → NO ACK → STOP。读到最后 1 字节时，主机发 NACK（不应答） 再 STOP，告诉 EEPROM 停止发送。

地址回绕
顺序读过程中内部地址持续自增，若读到 存储器末尾（0x7FF），地址会 回绕到 0x000 继续读，不会自动停止。跨 256 字节块时，由于设备地址块切换，实际需在块边界处分段处理。

4.16 SPI

4.16.1 什么是SPI

SPI 的全称是 Serial Peripheral Interface，中文一般叫 串行外设接口。
它是一种很常见的 同步串行通信协议，经常用在 MCU 和外部器件之间，比如：

  • Flash
  • 传感器
  • 屏幕
  • ADC
  • DAC

它和 UART 不一样。UART 不需要时钟线，双方约定好波特率就能通信；而 SPI 必须依赖时钟线来统一节奏，所以它属于同步通信。
它和 IIC 也不一样。IIC 更省线，适合挂多个设备；SPI 占线更多，但结构直接，速度通常更高。

刚开始学 SPI，可以先记住一句话：
SPI 就是主机提供时钟，主从双方跟着时钟一位一位交换数据。

4.16.2 SPI 需要哪几根线

最标准的 SPI 一般是 4 根线。

SCLK
这是时钟线，由主机输出。
它的作用是给整条总线提供节拍。主机每打出一个时钟，主从双方就往前推进一位数据，所以这根线是 SPI 通信的基础。

MOSI
全称是 Master Out Slave In。
这根线表示 主机发，从机收。也就是说，主机要写给从机的数据，通常走这根线。

MISO
全称是 Master In Slave Out。
这根线表示 从机发，主机收。也就是说，从机回传给主机的数据，通常走这根线。

CS 或 SS
这是片选线。
主机想和哪个从机通信，就把哪个从机的 CS 拉到有效电平。大部分器件里，CS 都是 低电平有效，也就是拉低表示选中。

所以最基础的认识就是：

  • SCLK 决定节奏
  • MOSI 负责主机发送
  • MISO 负责从机返回
  • CS 负责选中设备

4.16.3 SPI接线怎么理解

这部分很基础，但也是很多人一开始最容易接错的地方。

  • 单个设备时怎么接
    如果系统里只有一个主机和一个从机，那么接法通常是这样的：
  • 主机 SCLK 接从机 SCLK
  • 主机 MOSI 接从机 MOSI
  • 主机 MISO 接从机 MISO
  • 主机 CS 接从机 CS
  • 主机和从机 GND 一定要共地

很多初学者会误以为 MOSI 和 MISO 要交叉连接，其实大部分器件的数据手册里，管脚名已经是按总线功能命名好的，所以一般就是同名直接连接。

你可以这样理解：

  • MOSI 是总线上的“主发从收”通道
  • MISO 是总线上的“主收从发”通道

所以它们不是互相对调，而是各自承担一条固定方向的数据路径。

  • 多个设备时怎么接
    如果一个主机要带多个 SPI 从设备，通常不会给每个从机都单独一套总线，而是这样接：
  • 所有从机共用 SCLK
  • 所有从机共用 MOSI
  • 所有从机共用 MISO
  • 每个从机单独分配一根 CS

这样做的逻辑很简单。
主机在任意时刻只拉低其中一个从机的 CS，这个被选中的从机才会真正参与通信。其他从机因为 CS 没有被拉低，所以即使时钟线上有波形，也不会响应当前数据。

这就是 SPI 能挂多个从设备的原因。
但它也有明显代价：从设备越多，片选线占用的 GPIO 越多。这也是为什么 SPI 在多设备场景下，经常不如 IIC 节省引脚。

  • 接线时还要注意什么
    除了逻辑连接，硬件层面还有几个很重要的点。

第一，共地一定不能忘。
如果主机和从机没有共地，那么双方对高低电平的参考基准就不一致，通信很容易异常，甚至完全失败。

第二，电平必须匹配。
比如主控是 3.3V，从设备是 1.8V，这时就不能直接硬连。否则轻则通信不稳定，重则损坏器件。

第三，线不要太长。
SPI 速度一般比 IIC 更高，频率一上去之后，过长的飞线、接触不良或者地线处理不好，都会让时钟波形和数据信号质量变差。

第四，时钟线尤其要稳。
因为所有采样动作都靠时钟边沿来决定，一旦时钟边沿失真，接收方就可能在错误时刻采到数据。

4.16.4 SPI 的通信过程是怎么进行的

理解 SPI，不能只停留在“有四根线”这个层面，更重要的是知道它一轮通信到底是怎么跑起来的。

一轮典型的 SPI 通信，通常会经过下面这个过程：
1.主机先把目标从机的 CS 拉低
2.主机开始输出时钟 SCLK
3.主机在 MOSI 上送出数据
4.从机在 MISO 上返回数据
5.双方跟着时钟一位一位交换数据
6.传输结束后，主机再把 CS 拉高

这里面有两个动作特别重要。

▼ CS 拉低表示什么
CS 拉低，一般表示主机告诉从机：

这轮通信开始了，你现在要准备接收命令或者回传数据。

所以很多器件在 CS 拉低之后，才会真正开始识别后面的时钟和数据。
如果 CS 没有被选中，从设备即使看到了时钟跳变，通常也不会处理这次通信。

时钟为什么这么关键
SPI 是同步通信，它和异步协议最大的不同就是：
数据不是随便什么时候都能读，而是必须跟着时钟节奏来。

主机每输出一个时钟脉冲，双方就推进一位。
所以你可以把 SPI 想成一个“移位”过程：

  • 主机移出一位数据
  • 从机也移出一位数据
  • 双方在某个约定好的边沿完成采样

也正因为这样，SPI 天生就支持全双工。

为什么说 SPI 是全双工
因为 SPI 有两条独立的数据线：

  • MOSI 用来主机发给从机
  • MISO 用来从机发给主机

所以理论上每来一个时钟：

  • 主机都能发 1 位给从机
  • 从机也能回 1 位给主机

这就是“发送”和“接收”同时进行。

不过在实际器件里，虽然物理层是全双工，但协议层不一定每个阶段都有意义。比如主机正在发命令时，从机回传的那几位可能只是无效值；等真正进入读数据阶段时，MISO 上的数据才开始有效。

4.16.5 SPI 的时序最关键的是什么

SPI 最核心的内容，不是管脚名字，而是时序。
很多通信问题，看起来像代码错了，实际上根本原因是时序没对齐。

什么叫时序
时序，说白了就是两个问题：

  • 数据在什么时候发生变化
  • 接收方在什么时候把数据读进去

这两个动作不能乱来。
如果发送方刚把数据线切换，接收方就立刻去采样，那这一位可能还没稳定下来；反过来，如果接收方采样太晚，也可能错过本该读取的时刻。

所以 SPI 必须事先约定好：

  • 哪个时钟边沿用来改变数据
  • 哪个时钟边沿用来采样数据

为什么要有“边沿”这个概念
因为时钟线不是只有高低电平两种状态，它还存在变化过程。

  • 从低变高，叫上升沿
  • 从高变低，叫下降沿

在 SPI 里，很多动作不是在“高电平期间”或者“低电平期间”发生的，而是在某个边沿发生的。

可以简单理解成：

  • 某个边沿负责让数据切换到下一位
  • 另一个边沿负责把当前这位读进去

只要主从双方对这个约定一致，通信就能正常进行。

为什么时序错了会出问题
如果主机和从机对采样时刻理解不一样，就会出现很典型的现象：

  • 有波形
  • 也确实在通信
  • 但读出来的内容不对

常见的错误包括：

  • 数据整体左移一位
  • 数据整体右移一位
  • 每个字节都不稳定
  • 某些位总是错

所以学 SPI 时，真正要学明白的不是“时钟在跳”，而是“数据到底在哪一拍被读走了”。

4.16.6 SPI 的四种模式怎么理解

这部分很多人第一次学会觉得抽象，其实抓住两个参数就够了。

这两个参数分别是：

  • CPOL
  • CPHA

CPOL 决定什么
CPOL 决定时钟空闲时的默认电平。

  • CPOL = 0，表示时钟空闲时为低电平
  • CPOL = 1，表示时钟空闲时为高电平

也就是说，CPOL 主要决定时钟“平时停在哪里”。

CPHA 决定什么
CPHA 决定数据在哪个边沿被采样。

  • CPHA = 0，在第一个边沿采样
  • CPHA = 1，在第二个边沿采样

也就是说，CPHA 决定“先读还是后读”。

四种模式分别是什么
把这两个参数组合起来，就得到 4 种模式：

  • Mode 0：CPOL=0，CPHA=0
  • Mode 1：CPOL=0，CPHA=1
  • Mode 2：CPOL=1，CPHA=0
  • Mode 3：CPOL=1，CPHA=1

学习这部分时，不建议一开始就死背图形。
更有效的方式是先记住这个核心规律：

一条边沿负责改数据，另一条边沿负责采样数据。

然后再去对应具体模式。

最常见的理解方式
以最常见的 Mode 0 为例，可以把它理解成：

  • 时钟空闲时为低
  • 在第一个边沿采样
  • 在另一个边沿准备下一位数据

于是整个通信节奏就变成：

  • 先把当前这位数据放到线上
  • 等采样边沿到来时读进去
  • 然后在另一个边沿切换到下一位

其他模式也是同样的思路，只是空闲电平和采样先后顺序不同。

为什么模式一定要和器件手册一致
因为主机和从机的理解必须完全一致。

如果主机按 Mode 0 发，而从机按 Mode 1 收，那么主机觉得“现在该采样了”，从机可能还觉得“我还在准备数据”。这时通信表面上是通了，实际上数据内容已经不可靠。

所以做 SPI 时，模式配置通常不是自己随便选，而是要按照器件手册要求来设。

4.16.7 SPI 读写数据时要注意什么

很多人一开始会把 SPI 理解成写就是写，读就是读，但它没有那么分离。
在 SPI 里，只要时钟一起来，收发往往就是同时进行的。

写数据时在发生什么
主机拉低 CS 之后，开始输出时钟，并在 MOSI 上一位一位送出数据。
从机会在约定好的边沿把这些位采进去。
这就是最基础的“主机写，从机收”。

读数据时为什么还要发送东西
这是很多初学者最容易卡住的地方。
主机想读从机的数据，并不是自己站着等就行了。因为从机要把数据送出来，也得跟着主机提供的时钟走。所以主机在读数据时，通常还得继续发一些占位值，比如：

  • 0x00
  • 0xFF

主机发送这些值，不一定是想把它真正写给对方，而是为了继续把时钟打出来。只有时钟在走，从机才有机会把目标数据从 MISO 上送回来。

所以 SPI 里有一个很重要的认识：

想从从机读数据，主机必须继续发时钟。

实际器件里的读写往往不是单一步骤
大多数 SPI 外设都不会简单到“发一个字节就完”。
更常见的情况是：

  • 先发一个命令
  • 再发一个寄存器地址
  • 然后再进入数据阶段

比如读寄存器时，主机可能先告诉从机“我要读哪个地址”，从机收到这个命令后，才会在后续时钟里把对应内容送回来。

再比如 SPI Flash，很多时候会包含：

  • 指令阶段
  • 地址阶段
  • 等待阶段
  • 数据阶段

所以真正做项目时，不只是学 SPI 的底层时序，还要会看上层器件协议。

4.16.8 学 SPI 时最常见的问题有哪些

SPI 其实是一个非常适合调试的协议，因为大多数问题最后都能落到接线、模式、时钟或者片选上。

模式配错
这是最常见的问题之一。
表现通常是：

  • 波形能看到
  • 片选也正常
  • 但读出来的数据完全不对

这时候很大概率就是 CPOL 或 CPHA 配错了。

CS 控制不对
有些器件要求：

  • CS 拉低后才能识别命令
  • 整个事务期间 CS 不能中断
  • 数据收发完成后再拉高

如果中途把 CS 提前抬高，从设备可能会把这次通信直接判定为结束，后面的数据就都无效了。

频率开太高
很多人代码看着没问题，但频率一提上去就开始错。
这种情况通常和下面这些因素有关：

  • 线太长
  • 板子布线一般
  • 地线处理不好
  • 从设备本身支持的最高时钟有限

所以遇到莫名其妙的错码，先把 SPI 频率降下来，往往是很有效的排查办法。

接线和电平问题
这类问题也很多见，比如：

  • MOSI / MISO 理解错了
  • 没有共地
  • CS 接错设备
  • 电平不匹配

这类问题的特点是：代码可能完全没问题，但总线就是不工作。

4.17 QSPI Flash

4.17.1 什么是 QSPI

QSPI 的全称是 Quad Serial Peripheral Interface，中文常叫四线串行外设接口。它是在普通 SPI 基础上扩展出来的一种同步串行通信方式，本质仍是主机提供时钟、从机按时钟同步收发，但数据不再只靠 1 根 MOSI + 1 根 MISO 逐位传输，而是可以同时用 4 根数据线传数据，所以吞吐更高。

在嵌入式里，QSPI 最常见的用途不是接普通传感器，而是接 Nor Flash、Nand Flash 这类容量大、需要高速读写的存储器。例如 STM32H7 的外部程序存储、OTA 固件缓存、大容量配置参数、字库/图片资源等，往往都会优先考虑 QSPI Flash，而不是用 I2C EEPROM 或普通 SPI Flash 慢慢读。

它和几种常见接口的关系可以这样理解：

  • 和 UART 比：UART 是异步的，靠波特率约定速度，没有专用时钟线；QSPI 是同步的，必须有时钟，速度更稳定、也更容易做高速。
  • 和 I2C 比：I2C 线少、能挂多个从机，但速度通常较低；QSPI 线更多，结构更“直连”，适合点对点高速访问 Flash。
  • 和 SPI 比：SPI 一般 1 发 1 收；QSPI 在传输数据阶段可以 4 线同时传，同样时钟下，数据吞吐理论上能接近 4 倍（实际还受 Flash 器件、控制器、指令阶段等影响）。

一句话概括：QSPI 就是“带时钟的串行通信 + 数据阶段可升级为 4 线并行传输”，特别适合 MCU 高速访问外部 Flash。

4.17.2 QSPI 需要哪几根线

标准 SPI 常见是 4 根线：SCK、MOSI、MISO、CS。
QSPI 在此基础上扩展，常见是 6 根线：

信号 作用
CLK 时钟，由主机输出，从机跟着时钟采样/输出
CS / nCS 片选，低有效，选中当前要通信的 Flash
IO0 数据线 0（单线模式时常作 MOSI）
IO1 数据线 1（单线模式时常作 MISO）
IO2 数据线 2（双线/四线模式才用）
IO3 数据线 3（四线模式才用）

需要注意：

  • 在单线 SPI 模式下，IO0/IO1 可以像普通 SPI 一样当 MOSI/MISO 用；
  • 在双线 Dual 模式下，用 IO0、IO1 同时传；
  • 在四线 Quad 模式下，IO0~IO3 同时传，这才是 QSPI 名字里“Quad”的核心。

所以，QSPI 不是“线越多越好乱接”，而是同一组 IO 在不同阶段切换工作方式。

4.17.3 QSPI 的接线怎么理解

单个从设备时怎么接
最常见就是 MCU 的 QSPI 引脚 ↔ 一片 QSPI Flash：

  • CLK 对 CLK
  • CS 对 CS
  • IO0IO3 对 IO0IO3
  • 电源、地、去耦电容按手册接好

这类连接是点对点，没有 I2C 那种地址概念，选中哪片芯片靠 CS 片选。

多个从设备时怎么接
如果挂多片 Flash，常见两种方式：

  • 多个 CS：CLK、IO0~IO3 共享，每片 Flash 用自己的 CS；
  • 不同 QSPI 控制器：比如 MCU 有两个 QSPI 外设，各接一片。

一般不推荐多片 Flash 长期共享同一组 IO 又不做 CS 管理，否则总线会冲突。

接线时还要注意什么

  • IO 电压要一致，3.3V 就全 3.3V，避免电平不匹配；
  • CLK 频率不能一上来就拉满，要按 Flash 手册、PCB 走线、MCU QSPI 能力逐步调高；
  • IO2/IO3 在部分 Flash 上可能有特殊用途（如写保护、Hold），要查具体型号手册；
  • 高速时走线尽量等长、CLK 附近加地、铺地要好，否则边沿变差，容易读写出错；
  • 若启用 DTR（双倍数据速率）或 DDR 模式，对硬件要求更高，初学先掌握普通 SDR 即可。

4.17.4 QSPI 的通信过程是怎么进行的

和普通 SPI “发什么算什么”不同，访问 QSPI Flash 时，一次完整操作通常分成几个阶段：
（1）指令阶段（Instruction）
主机先发命令字节，告诉 Flash 要干什么，例如：

  • 读数据
  • 页编程（写）
  • 擦除
  • 读状态寄存器
    这一阶段通常是单线发送，类似普通 SPI。

（2）地址阶段（Address）
接着发地址，告诉 Flash 从哪个存储单元开始操作。

  • 24 位地址：最多寻址 16MB
  • 32 位地址：可寻址更大容量
    地址阶段可以是单线 / 双线 / 四线，取决于你配置的传输模式。

（3）空周期阶段（Dummy Cycles）
有些读命令发完地址后，不能立刻读数据，需要空跑若干个时钟周期，等 Flash 内部准备好。
这个阶段叫 Dummy Cycles，不是没意义，而是给 Flash 内部电路预留响应时间。

（4）数据阶段（Data）
最后才是真正读或写数据：

  • 读：Flash 把数据放到 IO0~IO3 上，MCU 采样；
  • 写：MCU 把数据发到 IO0~IO3，Flash 接收后进入内部编程。
    四线读就发生在这个阶段，所以速度提升最明显。

CS 拉低表示什么
和 SPI 一样，CS 拉低表示：

  • 本次传输开始；
  • 当前这片 Flash 被选中；
  • 在 CS 拉高之前，本次命令的各阶段（指令、地址、Dummy、数据）属于同一次事务。

时钟为什么这么关键
QSPI 所有阶段都靠 CLK 同步：

  • 时钟越快，单位时间传的数据越多；
  • 时钟太快，若 Flash 或 PCB 跟不上，就会误码、CRC 错、读出来全是 0xFF 或乱码。

所以 QSPI 调速度不是“越高越好”，而是 在稳定前提下尽量高。

为什么说 QSPI 很适合读 Flash
因为 Flash 读操作经常是：

发命令 → 发地址 → 等几个 Dummy → 连续大量读数据

其中 数据阶段最长，用 Quad 模式能显著缩短读取时间，所以 QSPI 读 Flash 特别合适。

4.17.5 QSPI 的时序最关键的是什么

  • 什么叫时序
    时序就是：在哪一个时钟边沿，哪根线应该是什么状态，数据才算有效。
    例如：
  • 上升沿采样还是下降沿采样；
  • 数据在时钟第几个边沿变化；
  • CS 什么时候拉低、什么时候拉高；
  • Dummy 周期到底要几个 CLK。
  • 为什么要由“边沿”这个概念
    因为 QSPI 是同步通信，接收方必须在约定的边沿去看数据，否则就会把 0 看成 1。
    这和 SPI 的 CPOL / CPHA 思想一致，只是 QSPI 还多了：
  • 单线 / 双线 / 四线切换；
  • 指令、地址、数据各阶段可能用不同线宽；
  • 有的还支持 DTR，上升沿和下降沿都传数据。
  • 为什么时序错了会出问题
    时序错了，典型现象有：
  • 读出来全 0xFF；
  • 读出来数据错位；
  • Flash ID 读不对；
  • 能读 ID，但不能正常读程序区；
  • 高温或低温时偶发失败；
  • 频率一高就出错，降频又正常。

这些都说明：不是软件逻辑一定错了，而是 QSPI 时序配置和硬件不匹配。

  • QSPI 配置里最需要关心的时序项
    在 STM32 的 QSPI 外设里，通常要关心：
  • 时钟分频 / 波特率预分频
  • CS 高电平保持时间
  • 指令/地址/数据相位（第几个边沿采样）
  • Dummy Cycles 个数
  • 单线/双线/四线模式是否和 Flash 手册一致

4.17.6 QSPI 的几种传输模式怎么理解

单线模式（Single SPI）

  • 只用 IO0 发、IO1 收，类似普通 SPI；
  • 常用于发命令、发地址；
  • 兼容性好，速度最慢。

双线模式（Dual SPI）

  • 用 IO0、IO1 同时传；
  • 每个时钟传 2 bit；
  • 常用于地址阶段或数据阶段加速。

四线模式（Quad SPI）

  • 用 IO0~IO3 同时传；
  • 每个时钟传 4 bit；
  • 常用于大数据量读取；
  • 是 QSPI 的核心优势。

为什么要分阶段用不同线宽
因为 Flash 命令格式是固定的，不是一上来就能 4 线乱传。典型流程是：

单线发命令 → 单线/四线发地址 → Dummy → 四线读数据

这样既符合芯片协议，又能把最耗时的数据阶段加速。

4.18 低功耗

4.18.1 什么是STM32的低功耗

低功耗不是指芯片“更省电”这一个口号，而是：在功能可接受的前提下，让 MCU 在运行、空闲、休眠各阶段尽量少消耗电能。

常见目标包括：

  • 电池设备续航更长（传感器、穿戴、手持仪表）
  • 发热更低、电源更小
  • 待机时只保留必要唤醒能力

功耗大致可理解为：P = V * I
所以降功耗通常从两方面入手：降低电压/调节器档位，以及减少电流（关时钟、关外设、进休眠）。

4.18.2 功耗主要由哪几部分构成

做低功耗前，先弄清电流花在哪里：

来源 说明
内核 + 总线 CPU跑多快、跑不跑，影响最大
外设 UART、SPI、ADC、定时器等未关闭会一直耗电
GPIO / 外部电路 引脚浮空、强上拉、驱动LED/传感器会额外耗电
时钟树 HSE/HSI、PLL、各总线分频；时钟越多、频率越高，电流越大
存储器 Flash等待周期、是否低功耗读、备份域SRAM等
唤醒源 RTC、EXTI、UART等要保持一定电路“醒着”才能唤醒

经验上：先量电流，再改代码。用万用表、功耗分析仪或 ST 的 PowerShield 看 Run / Sleep / Stop / Standby 各状态电流，比盲目改寄存器更有效。

4.18.3 STM32 低功耗模式怎么理解

STM32 不是只有一种“睡眠”，而是一组由浅到深的模式，越深越省电，但唤醒越慢、RAM/外设保留越少。

  • 常见模式（以 Cortex-M 系列为主）
模式 CPU 典型时钟 外设/RAM 唤醒后
Run 运行 全开 全开 —
Sleep 停止取指 多数外设时钟可开 保持 继续原代码
Stop 停止 多数时钟停 保持（系列有差异） 从进 Stop 的下一条执行
Standby 掉电级休眠 几乎全停 仅备份域等 常相当于复位启动

不同系列命名略有差别（如 Stop0/1/2、Standby、Shutdown），要以当前芯片参考手册为准。

  • STM32H7 双核时多一层：电源域
    H7 有 D1 / D2 / D3 等电源域，M7 多在 D1，M4 多在 D2。可以：
  • 只让某一域进 Stop
  • 用 HSEM 协调双核谁先睡、谁后醒

你工程里 CM4 上电后先进 D2 的 Stop，等 CM7 完成时钟等初始化再通过硬件信号量唤醒，就是典型的双核低功耗启动协调。

4.18.4 进入和退出低功耗是怎么进行的

  • 1.进入 Sleep（最浅）
  • 关闭或降低不需要的外设
  • 执行 __WFI() 或 __WFE()（或 HAL 封装）
  • 任意已使能 NVIC 中断可唤醒，从 WFI/WFE 后一条继续执行

适合：主循环没事做，但还要快速响应中断。

  • 2.进入 Stop（常用、省电明显）
    典型步骤：
    1.挂起 SysTick（避免周期性唤醒）
    2.关闭不必要外设时钟（__HAL_RCC_XXX_CLK_DISABLE()）
    3.GPIO 设为模拟/上拉下拉，避免漏电
    4.配置唤醒源（EXTI、RTC、UART 等）
    5.调用 HAL_PWR_EnterSTOPMode() 或 HAL_PWREx_EnterSTOPMode()（H7 带参数）

唤醒后注意：

  • 系统时钟往往恢复为 HSI，需重新 SystemClock_Config()
  • 外设若依赖 PLL，要重新初始化
  • 3.进入 Standby（最深之一）
  • 备份域、RTC、唤醒引脚等按手册配置
  • 唤醒后多为冷启动流程（main 重新跑）
  • 适合长时间几乎不工作，偶尔按键/RTC 唤醒

唤醒源要事先配好
未使能的唤醒源会导致：进了低功耗却醒不来。常见唤醒：EXTI、RTC Alarm、USART（需匹配 Stop 下时钟要求）、LPTIM、IWDG 等。

4.18.5 做低功耗最关键的是什么

可以概括成四句话：

  • 1.先定“睡多深”
  • 要 RAM 保持、毫秒级唤醒 → Sleep / Stop
  • 要 μA 级、可接受重启 → Standby
    没有统一最优，只有业务可接受的最深模式。
  • 2.时钟和外设必须“真关”
  • Run 时 480 MHz 和 64 MHz 电流差很多
  • Sleep/Stop 里仍开着 UART DMA、定时器，会白睡
  • Clock Gating：不用就 __HAL_RCC_xxx_CLK_DISABLE()
  • 3.GPIO 和硬件电路不能漏
  • 浮空输入可能振荡耗电
  • 外部芯片未关电、LED 常亮、上拉电阻过大都会吃掉 Stop 的收益
  • 进 Stop 前：无关引脚 模拟输入 或明确上下拉
  • 4.唤醒路径要短、要可靠
  • 中断里只做置标志，复杂逻辑放主循环
  • Stop 唤醒后第一件事往往是恢复时钟
  • 双核要约定：谁先睡、谁释放 HSEM、谁等 D2CKRDY

4.18.6 低功耗相关配置怎么理解和选用

  • 电压调节（VOS / Scale）
    H7 等有 Voltage Scaling（Scale0～3）：电压越低，可跑最高频率越低，但同频率下更省电。需查手册：频率 ↔ VOS 对应表，不能超规格跑。

  • Stop 子模式（以 H7 为例）

  • Stop0：唤醒快，电流相对高
  • Stop1/2：更省电，部分域/外设行为不同

用 HAL_PWREx_EnterSTOPMode(调节器, WFI/WFE, 域) 时，三个参数都要和手册一致。

  • 进入方式：WFI 还是 WFE
    指令 含义
    WFI 等待中断，中断来了就醒
    WFE 等待事件，SEV、部分EXTI等可醒

双核启动里 CM4 用 WFE + 事件 等 CM7，是常见写法。

  • 调试与测量时的配置
  • Debug 连接时部分低功耗会被调试器拉住，测电流要断开调试或看 DBGMCU 配置
  • 用 DWT / GPIO 翻转 标定“进 Stop → 唤醒”时间

4.18.7 低功耗代码实战

实现原理就是一个“中断唤醒的状态机”：

  • 系统正常运行时，按键引脚配置为外部中断源（EXTI），作为后续唤醒源。
  • 第一次按键触发中断后，不在中断里做复杂处理，只记录“请求进入低功耗”的事件。
  • 主循环检测到这个事件后，执行进入低功耗流程：暂停系统节拍、清理待处理事件、执行 WFI 进入 STOP。
  • 进入 STOP 后，CPU 主执行流暂停，等待可唤醒中断。
  • 再次按键触发 EXTI 中断，硬件把内核从 STOP 拉起，程序从低功耗入口返回。
  • 唤醒后恢复系统运行上下文（尤其是时钟树与串口等外设），再回到主循环继续工作。
  • 同时通过去抖和状态标志避免按键抖动、重复触发、重入进入低功耗。

本质上是：“中断负责通知和唤醒，主循环负责状态切换，STOP 负责降功耗”。

4.19 SDRAM

4.19.1 什么是SDRAM

SDRAM（Synchronous Dynamic Random Access Memory，同步动态随机存储器）是一种需要周期性刷新的大容量RAM，通过时钟同步的地址/数据/控制信号访问，常用于MCU/MPU扩展大块可读写内存（帧缓冲、协议栈、音频缓冲、大数组等）。

和片内SRAM对比：

对比项 片内SRAM SDRAM
容量 通常几百KB级 常见8MB ~ 128MB+
速度 与内核同域，最快 经FMC/控制器，有延迟
掉电 掉电丢失 掉电丢失
成本 已在芯片内 需外挂芯片 + PCB
使用 直接当内存用 需初始化控制器 + 刷新

“动态”的含义：每个存储单元用电容保存电荷，会漏电，必须按行定时刷新，否则数据丢失。

4.19.2 SDRAM 需要哪些硬件连接

MCU 通过 FMC（Flexible Memory Controller） 或专用 SDRAM 控制器接 SDRAM 芯片，信号可分成几类理解：

  • 1.时钟与数据

    信号 作用
    CLK 同步时钟，所有操作按时钟沿采样
    DQ[0:15/31] 数据总线，常见16位宽，可两片拼32位
    DQM 数据掩码，按字节屏蔽写入

  • 2.地址

    信号 作用
    A[0:n] 行/列地址复用线，具体位宽看芯片容量
    BA / BA0、BA1 Bank 地址，选L-Bank
    片选 CS# 选中当前SDRAM芯片（低有效）

  • 3.控制（名字因厂商略有差异）

    信号 作用
    RAS# 行选通：锁存行地址、发刷新命令
    CAS# 列选通：锁存列地址
    WE# 写使能
    CKE 时钟使能，进低功耗或保持刷新

STM32H7 上这些多数由 FMC SDRAM 接口引出，引脚需对照数据手册与 PCB 原理图一一对应。

  • 4.电源与硬件注意
  • VDD / VDDQ / VREF：按芯片手册供电、去耦
  • 拓扑：高速信号等长、阻抗控制，否则大时钟下易不稳定
  • 容量：由 行地址 × 列地址 × Bank 数 × 数据宽度 决定

4.19.3 SDRAM 的存储结构怎么理解

把 SDRAM 想成带行列地址的表格仓库，而不是一根线性地址棒：

芯片
└── Bank（通常 4 个）
  └── Row（行，例如 4096 行）
    └── Column（列，例如 512 列）
      └── 每个单元若干 bit（×16/32 位数据宽）

CPU 看到的线性地址，由 FMC/控制器内部拆成：
Bank + Row + Column + 字节偏移

因此访问 SDRAM 常有额外延迟：换行（Row）时要 ACT（激活），同一行内连续读列更快；换 Bank 可交错，减轻总线空闲。

4.19.4 SDRAM 的访问过程是怎么进行的

  • 1.上电后必须先初始化
    SDRAM 上电处于未知状态，控制器要按手册发一串命令，例如：
  1. 等电源稳定，发预充电（Precharge）
  2. 自动刷新若干次
  3. 发模式寄存器设置（MRS）：突发长度、突发类型、CAS 延迟、写模式等
  4. 设置 FMC 的刷新计数器（Refresh Rate）

未完成初始化就读写 → 数据错乱或总线异常。

  • 1.一次典型读操作（简化）
  1. ACT：在某一 Bank 上激活一行（RAS）
  2. 等待 tRCD（行到列延迟）
  3. READ：发列地址（CAS），指定突发长度
  4. 经过 CAS Latency（CL）个周期后，数据出现在 DQ 上
  5. 读完可 PRE 关闭当前行，或继续在该行读下一列

写操作类似，用 WE# 配合，并满足 tWR、tRP 等时序。

  • 2.刷新（Refresh）
  • 控制器周期性发 AUTO REFRESH，或由 CPU 配合
  • 刷新间隔与温度、容量有关，FMC 里配置 RefreshCount
  • 刷新期间总线会被占用一小段时间；若刷新配置错误，会静默丢失数据
  • 3.CPU 侧怎么用
    初始化完成后，SDRAM 映射到固定内存地址区间（如 STM32H7 常见 0xC0000000 一带），之后：
  • C 里直接 uint32_t *p = (uint32_t *)0xC0000000;
  • malloc 堆可指向外部 SDRAM（需链接脚本改堆栈/堆区域）
  • LTDC 帧缓冲、摄像头缓冲等可放这里

4.19.5 SDRAM 时序最关键的是什么

SDRAM 是时序器件：不满足手册上的 ns / 时钟周期要求，就会读写失败或偶发错误。

  • 1.CAS Latency (CL)
  • 发 READ 命令后，第几个时钟沿数据有效
  • 常见 CL=2、3（与频率、芯片型号相关）
  • MRS 里配置的 CL 必须和 FMC 时序参数一致
  • 2.行/列相关时间（常出现在 FMC 配置里）
    参数 含义
    tRCD 激活行到读/写列的间隔
    tRP 预充电时间
    tRAS 行激活最小保持时间
    tWR 写恢复时间
    tRFC 刷新周期时间

这些在 ST 的 SDRAM_TimingTypeDef 里用时钟周期数填写，需按数据手册换算。

  • 3.时钟频率
  • SDRAM 有额定最高频率（如 166MHz、200MHz）
  • FMC 时钟过高 → 眼图变差、温漂后易出错
  • 频率上去往往要加大 CL 或放宽其它参数
  • 4.突发（Burst）
  • 一次 READ 命令可连续读出 BL 个数据（如 BL=1/2/4/8）
  • 与 Cache、DMA 突发长度匹配时效率最高
  • 模式寄存器里 Burst Length、Burst Type（顺序/交错）要和驱动一致

调试 SDRAM 时序问题：示波器看 CLK/DQ、先降频、对照芯片 AC Characteristics 表逐项核对 FMC 参数。

4.19.6 SDRAM 的配置与模式怎么理解

  • 1.模式寄存器（Mode Register）
    上电初始化时写入，决定芯片“性格”，主要包括：
  • Burst Length：1 / 2 / 4 / 8 / 全页等
  • Burst Type：Sequential / Interleaved
  • CAS Latency：2 或 3 等
  • Operating Mode：标准 / 测试等
  • Write Burst Mode：读突发时写是否也突发

HAL 里通常在 HAL_SDRAM_Init() 之后的 HAL_SDRAM_ProgramModeRegister() 完成。

  • 2.STM32 FMC 侧主要配置块
    配置项 作用
    SDClockPeriod FMC 给 SDRAM 的时钟分频
    ReadBurst / ReadPipeDelay 读突发与采样延迟
    CAS、RCD、RP、WR… 对应 AC 时序
    RefreshRate 自动刷新频率
    Bank / Column / Row 与芯片容量、接线位宽一致

不同容量芯片（如 IS42S32800、W9825G6KH）行列位宽不同，不能照搬别的板子的参数。

  • 3.低功耗相关（芯片级）
    SDRAM 自身可有：
  • 时钟停止（CKE 拉低，数据保持但需按时唤醒刷新策略）
  • 自刷新（Self-Refresh）：更低功耗，由芯片内部定时刷新

MCU 进 Stop/Standby 前要想清楚：FMC 停了，SDRAM 是否还能保持数据、要不要先进入 Self-Refresh。这和 STM32 低功耗强相关。

  • 4.与 MPU / Cache 的关系（Cortex-M7）
    H7 的 M7 带 Cache：
  • SDRAM 映射区常配为 可缓存、可缓冲
  • DMA 与 CPU 同时访问要做 cache 维护（clean/invalidate）或 MPU 设为 non-cacheable
  • 否则现象是：CPU 看到的数据和 DMA 不一致
  • 5.常见选型对照
    项目 说明
    16bit × 1 片 省引脚，带宽较低
    16bit × 2 片拼32bit 常见 H7 开发板，带宽更好
    容量 看 Row×Col×Bank×Width
    速度等级 -6、-7 等表示更快 CAS 能力

STM32Cubemx配置：

Clock and chip enable
该参数用于选择 SDRAM 的时钟使能与片选信号组合。配置为 SDCKE1 + SDNE1 时，表示启用 SDRAM2 通道对应的 CKE/NE 控制线。其作用是：CKE 控制时钟是否有效，NE 控制芯片是否被选通，二者共同决定 SDRAM 是否参与当前访问周期。

Internal bank number
该参数定义 SDRAM 芯片内部 bank 结构。配置为 4 banks 表示芯片内部有 4 个独立 bank，控制器通过 bank 地址线（BA0、BA1）在不同 bank 间切换。bank 数决定了地址映射方式，也影响突发访问与页切换行为。

Address
该参数表示行地址位宽。配置为 12 bits 时，行地址为 A0~A11，可表示 2^12 = 4096 行。行地址位数与列地址位数共同决定可寻址空间大小，是容量计算的核心参数之一。

Data
该参数表示外部数据总线宽度。配置为 32 bits 时，控制器使用 D0~D31 数据线，单次总线访问宽度为 4 字节。位宽越大，单位时钟可搬运数据越多，同时占用的引脚也越多。

Byte enable
该参数用于配置按字节写屏蔽功能。选择 32-bit byte enable 时，会启用 NBL0~NBL3 四路字节使能信号，可在 32 位数据中按字节选择性写入，避免无关字节被覆盖。该功能对结构体字段更新、字节流写入等场景非常重要。

容量关系（由以上参数共同决定）
SDRAM 总容量可按公式计算：容量 = 2^行地址位数 × 2^列地址位数 × 内部bank数 × (数据位宽/8)。当参数为行地址 12 位、列地址 9 位、4 bank、32 位数据宽度时，容量结果为 32MB。

Bank
选择 FMC 连接的 SDRAM 片选通道。这里是 SDRAM bank 2，表示使用 FMC 的 Bank2 配置去驱动外部 SDRAM（对应前面选的 SDNE1/SDCKE1 这组信号）。

Number of column address bits
列地址位数。这里是 9 bits，表示列地址为 9 位，可寻址 2^9 = 512 列；它决定“页内列”范围，与行地址/内部 bank 一起决定容量与页命中行为。

Number of row address bits
行地址位数。这里是 12 bits，表示行地址为 12 位，可寻址 2^12 = 4096 行；行切换会触发预充电/激活等时序约束。

CAS latency
CAS 延迟（CL），单位是“存储器时钟周期”。这里是 2 memory clock cycles，表示从发出 READ 命令到数据有效需要等待 2 个 SDRAM 时钟周期；该值必须满足芯片手册在当前频率下的要求。

Write protection
写保护。这里 Disabled 表示允许写入 SDRAM；若启用则对该 SDRAM 区域写操作会被禁止（用于防误写）。

SDRAM common clock
SDRAM 时钟分频/周期选择。这里是 2 HCLK clock cycles，含义是 SDRAM 时钟（SDCLK）相对 FMC 内核时钟按“2 个周期”为一拍来输出，等价于常见的 SDClockPeriod = 2（通常表现为 FMC 内核时钟再分频得到 SDCLK）。配置越大，SDCLK 越慢，时序更宽松但带宽下降。

SDRAM common burst read
突发读使能。这里 Enabled 表示开启 SDRAM burst read，连续地址读可以用突发方式提高吞吐与效率；若禁用则按单次读周期工作，性能更差但更保守。

SDRAM common read pipe delay
读管线延迟（RPIPE），单位为 HCLK 周期。这里是 1 HCLK clock cycle，表示读数据从 SDRAM 回到 FMC 侧会额外插入 1 个周期用于对齐/稳定；频率较高时常需要加大该值以满足时序。

Load mode register to active delay
tMRD：加载模式寄存器（LOAD MODE）到下一次可激活/访问之间的最小等待周期数。这里是 2，表示发出 LMR 命令后至少等 2 个 SDRAM 时钟周期。

Exit self-refresh time
tXSR：退出自刷新到可以进行下一条有效命令的等待周期数。这里是 8，表示从 self-refresh 退出后要等 8 个 SDRAM 时钟周期才能继续访问。

Self-refresh time
tRAS（在 CubeMX 里通常对应“自刷新时间/行有效时间”这类约束）：表示一行从激活到允许预充电的最短时间（行保持有效的最小周期数）。这里是 6。

SDRAM common row cycle delay
tRC：行周期时间（同一 bank 两次激活之间的最小间隔）。这里是 8，约束“ACT 到下一次 ACT”的最小周期。

Write recovery time
tWR：写恢复时间，写操作结束到允许 PRECHARGE 的最小等待。这里是 3，保证写入数据能可靠落到存储阵列。

SDRAM common row precharge delay
tRP：预充电时间，从 PRECHARGE 命令到可以再次 ACT 的最小等待。这里是 3。

Row to column delay
tRCD：行到列延迟，从 ACT（激活行）到 READ/WRITE（列访问）之间的最小等待。这里是 3。

4.20 双核通信

4.20.1 什么是核间通信（IPC）

  • 1.定义
    在 STM32H747/H745 等双核芯片上，Cortex-M7 与 Cortex-M4 各跑一套程序，彼此内存独立、不能直接调用对方函数。要在两核之间传数据、发命令、做同步，就需要 IPC（Inter-Processor Communication，核间通信）。

  • 2.要解决的三类问题

  • 传数据：传感器值、状态字、命令参数等。
  • 互斥：同一时刻只允许一核读写某块共享区，避免踩内存。
  • 通知：一核做完初始化或收到数据后，唤醒或打断另一核（含 STOP/WFE 场景）。
  • 3.常见组合方式
层次 做什么 典型手段
载体 数据放哪 双方都能访问的SRAM（链接脚本规划共享段）
互斥/通知 谁在用、何时继续 软件标志位或HSEM
协议 字节含义、顺序 自建队列/状态机（本节的「软件协议」）

4.20.2 共享 RAM + 软件协议

  • 2.1 什么是这种方式
    在两边都能访问的同一块 SRAM 里放置队列、结构体或环形缓冲区，用标志位、序号、状态机 约定「谁写、谁读、何时有效」。协议逻辑完全由应用代码实现，不依赖 OpenAMP/RPMsg。
    适合：传感器数据、简单命令、结构固定且数据量不大的场景。

  • 2.2 需要哪些硬件/工程条件
    2.2.1 共享存储区从哪来

  • H7 上常用 SRAM1 / SRAM2 / SRAM4 等，在 CM7、CM4 链接脚本 里各划一段 相同物理地址、相同长度 的 SHARED 段。
  • 该区域 不要 被某一核单独占满，否则另一核无法链接到同一地址。

2.2.2 Cache 与一致性（很关键）

  • CM7 常开 D-Cache；CM4 侧访问同一块 RAM 时，可能出现「写入了但对方读到旧值」。
  • 做法之一：共享区配置为 non-cacheable（MPU），或在写后 SCB_CleanDCache、读前 SCB_InvalidateDCache。
  • 未处理 Cache 时，协议再正确也会表现为「偶发丢数据、标志位乱跳」。

2.2.3 没有专用 IPC 外设也要配

  • 时钟、复位、双核启动顺序（你工程里 CM7 先跑、CM4 在 STOP 等 HSEM）要先稳定。
  • 共享 RAM 本身不自动互斥，必须 配合同步手段（本节的标志位，或第 3 节的 HSEM）。
  • 2.3 共享区的结构怎么理解
    2.3.1 典型布局（示例）
    [ magic | version | write_idx | read_idx | payload[] ]
  • magic / version：上电后检查区是否合法。
  • write_idx / read_idx：环形队列头尾（或单槽 data_ready 标志）。
  • payload[]：实际传感器帧或命令结构体。

2.3.2 单缓冲 vs 环形队列

  • 单缓冲 + 1 个标志位：实现简单，适合低频、一帧一帧传。
  • 环形队列：适合连续采样；注意满/空判断与索引回绕。

2.3.3 谁拥有哪段 RAM

  • 逻辑上属于两核共享；物理上需在链接脚本里 显式保留，避免被栈/堆覆盖。
  • 2.4 访问过程是怎么进行的（软件握手）
    2.4.1 上电后必须先约定
  • 共享区清零或写入初始 magic。
  • 约定：仅 CM7 写 / 仅 CM4 读，或双向各一组槽位（避免双向同时无锁写同一字段）。

2.4.2 一次典型「写端 → 读端」流程（简化）
1.写核：若 busy==0，写 payload，内存屏障，置 data_ready=1。
2.读核：轮询或等中断发现 data_ready==1，读 payload，清 data_ready，置 busy=0。
3.若两核都可能写同一控制字段，应加 HSEM 或关中断+原子操作（见第 3 节）。

2.4.3 和 HSEM 的分工

  • 仅用标志位：适合单写单读、低竞争；实现快，易踩竞态。
  • 共享 RAM + HSEM：数据在 RAM，拿锁/放锁/唤醒 用 HSEM，适合稍复杂或要唤醒 STOP 中的对端。

2.4.4 CPU 侧怎么用（落地步骤）
1.链接脚本增加 SHARED 段，两边 ORIGIN/LENGTH 一致。
2.定义 volatile 结构体指针指向共享区。
3.实现发送/接收状态机（或极简单标志握手）。
4.处理 Cache/MPU。
5.在 CM7 完成时钟等初始化且 CM4 已唤醒后再开始业务收发。

  • 2.5 软件协议最关键的是什么
    2.5.1 状态机清晰
    每个标志位含义固定：idle / ready / acked，避免一 bit 多义。

2.5.2 内存可见顺序
写数据 先于 置标志；读标志 先于 读数据。必要时使用 __DMB() / __DSB() 等屏障。

2.5.3 超时与异常
对端死机时要有超时复位共享区，防止永久 busy=1。

2.5.4 数据长度与对齐
结构体按 4 字节对齐；长度字段防止越界。

4.20.3 HSEM（硬件信号量）

  • 1.什么是 HSEM
    HSEM（Hardware Semaphore）是芯片内置的 32 路硬件信号量（编号 0～31），两核均可 Take / Release。
  • 用于 互斥（同一时刻只有一个主能持有某路 sem）。
  • 用于 事件通知：Release 时可 唤醒 处于 WFE/STOP 的对端，并可选产生 中断。

不适合：单独用 HSEM 传大块数据（它只负责「锁」和「通知」，数据仍放在共享 RAM）。

  • 2.需要哪些硬件/工程条件
    1.时钟
  • 使用前 __HAL_RCC_HSEM_CLK_ENABLE()

2.编号规划

  • 共 32 路，应用层应文档化分配，例如：
    • HSEM_ID_0：启动同步
    • HSEM_ID_1：共享缓冲区互斥
    • HSEM_ID_2：数据就绪通知

3.中断（若用通知/唤醒）

  • 在 CubeMX NVIC1（M7）/ NVIC2（M4）中启用 HSEM global interrupt，CM4 侧 HAL_HSEM_ActivateNotification()（你 CM4 启动段已有）。
  • 纯 FastTake / Release 做启动握手可不依赖中断回调；业务事件通知建议开中断。

4.与电源模式

  • CM4 HAL_PWREx_EnterSTOPMode(..., PWR_STOPENTRY_WFE, PWR_D2_DOMAIN) 等待 CM7 的 HSEM Release，即 硬件唤醒路径。
  • 3.HSEM 在系统里怎么理解
    1.Take / Release
  • Take：尝试占用该路 sem；已被占用则失败或阻塞（视 API）。
  • Release：释放；可带进程 ID，并触发对端唤醒/中断。

2.与软件标志位的区别

对比项 软件标志位 HSEM
互斥保证 需小心竞态、Cache 硬件原子
唤醒 STOP 中的对端 不可靠 支持
资源数量 自定 固定 32 路

3.和共享 RAM 的关系

  • 推荐：数据在共享 RAM；进临界区 HAL_HSEM_FastTake(id) → 读写 → HAL_HSEM_Release(id)。
  • 或：数据写完后 Release 专门用于 notify 的 sem，对端在中断里读 RAM。
  • 4.使用过程是怎么进行的
    1.启动同步
  1. CM4：使能 HSEM 时钟 → ActivateNotification → 进入 STOP。
  2. CM7：时钟/外设初始化 → FastTake(0) → Release(0) → 等 RCC_FLAG_D2CKRDY。
  3. CM4：被唤醒 → Clear flag → 继续 HAL_Init() 与业务。

2.互斥访问共享区（业务扩展示例）
1.CM7：FastTake(HSEM_ID_1) 成功 → 写共享结构体 → Release(HSEM_ID_1)。
2.CM4：FastTake(HSEM_ID_1) 失败则等待或 WFE；成功后读 → Release。

3.事件通知（数据就绪）

  1. CM7 写完共享 RAM → Release(HSEM_ID_2)。
  2. CM4 在 HAL_HSEM_FreeCallback 或 WFE 唤醒后读 RAM。

4.CPU 侧常用 API（HAL）

  • HAL_HSEM_FastTake(SemID)
  • HAL_HSEM_Release(SemID, ProcessID)
  • HAL_HSEM_ActivateNotification(Mask)
  • HAL_HSEM_IRQHandler / HAL_HSEM_FreeCallback
  • 5.使用 HSEM 最关键的是什么
    1.死锁
    Take 成功后必须 Release；异常路径也要释放。
    2.编号冲突
    启动、互斥、通知分用不同 ID，禁止多模块抢同一路。
    3.仍要处理共享 RAM 的 Cache
    HSEM 只保证「谁可以进临界区」，不替代 D-Cache 维护。
    4.Release 的 ProcessID
    启动同步里常用 0；多进程场景按 HAL 说明传 PID。

4.21 SD NAND

  • 1.定义
    SD NAND 指将 NAND 闪存与 SD 协议控制器集成于单一封装内的板载存储器件。对外呈现标准 SD/MMC 从设备接口：时钟（CLK）、命令（CMD）、数据线（DAT0～DAT3）、电源（VCC）与地（VSS）。主机通过 SDMMC 控制器以 SD 卡相同的命令集与传输模式进行访问，器件为 SMD 封装，焊接于 PCB，无卡槽与热插拔机制。

典型型号命名中容量常以 Gbit 标注（例如 4G 表示约 4 Gbit，即约 512 MByte 用户容量，以厂商数据手册为准）。

  • 2.与 SD 卡、裸 NAND 的对比
项目 可插拔 SD 卡 SD NAND 裸 NAND
封装 卡体 + 金手指 8 脚或类似贴片 IC 独立 Flash 芯片
协议层 SD/MMC SD/MMC ONFI、并行等，需自建协议栈
控制器与 FTL 卡内集成 芯片内集成 由主控或外部方案实现
维护 可更换 与 PCB 一体 取决于设计方案

SD NAND 在协议与驱动模型上归属 SD 存储设备范畴；与裸 NAND 相比，块管理、坏块替换、磨损均衡等由器件内部完成，主机侧仅见逻辑扇区。

  1. 配置 SDMMC（时钟分频、总线宽度、DMA 等）

4.22 FatFs文件系统

  • 1.FatFs是什么，解决什么问题
    FatFs 是一个面向嵌入式系统的轻量级 FAT 文件系统模块（常见于 STM32 + SD 卡/eMMC/U 盘场景）。它把“按扇区读写”的底层存储，抽象成我们熟悉的“文件/目录”操作，比如打开文件、读写文本、创建目录、删除文件等。
  • 核心价值：让 MCU 不再只会读写裸扇区，而是能按文件组织数据。
  • 适配介质：SD/TF、eMMC、SPI Flash（通过块设备仿真）、USB MSC 等。
  • 支持格式：FAT12/FAT16/FAT32（可选 exFAT，取决于配置）。
  • 典型用途：
    • 日志记录（log.txt）
    • 参数保存（config.ini）
    • 资源加载（字体/图片/音频）
    • 固件升级文件读取

一句话：FatFs = 嵌入式里的“文件管理层”，上接应用，下接 diskio 驱动。

  • 2.FatFs 的系统结构与工作流程

FatFs 不是直接访问 SDMMC 外设，它通过一层标准接口访问底层驱动。你可以把它理解为三层：

  • 应用层： f_open / f_read / f_write / f_close / f_mkdir …
  • FatFs 核心层： ff.c + ff.h（FAT 解析、簇分配、目录管理）
  • 磁盘接口层： disk_initialize / disk_read / disk_write / disk_ioctl（在 sd_diskio.c 里）

标准流程一般是：

  • 初始化外设（SDMMC/SPI/USB）
  • MX_FATFS_Init() 关联驱动
  • f_mount() 挂载卷
  • 进行文件操作（open/read/write）
  • f_sync() 或 f_close() 落盘
  • 结束时可 f_mount(NULL, ...) 卸载

你现在这种 STM32H747 场景里，最关键的映射关系是：

  • f_read → disk_read → BSP_SD_ReadBlocks / HAL_SD_ReadBlocks
  • f_write → disk_write → BSP_SD_WriteBlocks / HAL_SD_WriteBlocks

也就是：FatFs 不关心是 SD NAND 还是 TF 卡，它只关心扇区读写是否正确。

  • 3.FatFs 实战要点与常见坑
  • 扇区大小必须一致：ffconf.h 里的 _MIN_SS/_MAX_SS 通常都设 512，并与 disk_ioctl(GET_SECTOR_SIZE) 返回一致。
  • 先挂载再操作：所有文件 API 前必须 f_mount 成功。
  • 首次无文件系统：f_mount 返回 FR_NO_FILESYSTEM 时，用 f_mkfs 格式化（会清空介质）。
  • 写入后要落盘：实时日志建议周期性 f_sync，否则断电可能丢最后一段。

4.23 USB-OTG

  • 1.什么是USB
    1.什么是USB
    USB(Universal Serial Bus, 通用串行总线)是一套完整的连接标准，不只是“两根数据线”。它同时定义了:
  • 物理层：线缆、接口、引脚、电平、速率
  • 协议层：数据怎么分包、怎么寻址、怎么校验
  • 设备管理：插上后如何识别设备（枚举）、加载驱动、分配地址
  • 供电规范：设备怎么从总线取电、最多能取多少电流

所以 USB 的本质是：“数据通信 + 供电 + 即插即用管理”三合一标准。

2．USB 的作用是什么
从用户和工程角度看，USB 主要解决了这几件事：

  • 统一接口：鼠标、键盘、U盘、摄像头、打印机都能用同一类接口
  • 即插即用：插上后主机自动识别，不用手动配复杂硬件参数
  • 同时供电：很多设备不需要额外电源，插上就能工作
  • 支持多类设备：HID、CDC虚拟串口、MSC存储、Audio、Video 等
  • 生态完整：PC/手机/嵌入式都有成熟协议栈和驱动支持

3．为什么会有 USB
在 USB 出现前，PC 外设接口很多且割裂（串口、并口、PS/2、专用口等），问题是：

  • 接口种类太多，用户体验差
  • 不能热插拔或热插拔不稳定
  • 供电能力弱，设备常要独立电源
  • 驱动和资源管理复杂，扩展麻烦

USB 出现的目标就是统一这些混乱：
统一连接方式、支持热插拔、支持供电、降低设备接入门槛。

所以 USB 是“工程标准化和生态化”的产物，不是单纯为了替代某一条通信线。

4．USB 和串口、SPI 有什么区别

  • 与 UART（串口）对比
    • UART 是“点对点异步字节流”，协议很薄，通常你自己定上层协议
    • USB 是“主机-设备架构 + 标准协议栈”，有枚举、端点、类协议
    • UART 简单、调试友好；USB 功能强、生态好但实现更复杂
    • UART 常用于板级调试/短距通信；USB 常用于对接 PC/手机外设生态
  • 与 SPI 对比
    • SPI 是板内高速同步总线，常用于 MCU 连 Flash/屏/ADC
    • SPI 一般不用于直接连 PC，不具备 USB 那种即插即用生态
    • SPI 需要片选、时钟等多线，适合“主控对从设备”的硬件互联
    • USB 侧重“外设互联标准化”，SPI 侧重“板级高速数据搬运”

可以这样记：

  • UART：最轻量，适合“我自己定义协议”
  • SPI：板内高速，适合“芯片到芯片”
  • USB：生态最强，适合“设备接主机”
  • 2.USB 基础概念
    USB 是一套完整标准，不只是“接口形状”或“两根数据线”。它包含：物理连接（线缆/引脚/电气）、通信协议（分包/校验/重传）、设备管理（枚举/地址分配/驱动匹配）和供电规则（电压电流预算）。

核心思想是：由主机统一调度总线，设备按规则响应，从而实现稳定通信和即插即用。

Host（主机）
Host 是总线控制者，典型是 PC、手机（OTG 主模式）、上位机系统。它负责：

  • 给总线提供管理与时序（谁什么时候发数据）
  • 识别新插入设备并发起枚举
  • 分配设备地址、读取描述符、加载对应驱动
  • 发起所有传输（USB 里没有“设备主动抢总线发起通信”这件事）

所以 Host 像“总线调度中心”。

Device（设备）
Device 是被管理的一端，典型是鼠标、键盘、U 盘、CDC 虚拟串口板卡。它负责：

  • 按 USB 协议响应 Host 请求
  • 提供自身能力描述（设备类、端点、功耗等）
  • 在被轮询或被请求时收发数据

设备不能像串口那样随时自己主导发送，而是依赖 Host 的调度节奏。

USB 通信本质
USB 本质是“主机轮询 + 端点通信 + 分层协议”。

  • 主机按帧/微帧节奏安排传输
  • 设备以端点（Endpoint）暴露数据通道
  • 数据通过事务/包进行传输并带校验

从方向上看有 IN/OUT 两个逻辑方向，但在 USB2.0 FS/HS 常见场景下，总线同一时刻只跑一个方向事务，属于总线调度下的时分传输。

你可把 USB 理解为：标准化很强的“受控通信系统”，不是裸字节流。

USB 为什么能即插即用
即插即用来自“标准化枚举流程 + 统一描述符体系 + 操作系统驱动框架”三件事配合：

  1. 插入检测：Host 发现有设备接入
  2. 复位与默认地址通信
  3. 读取设备描述符（Vendor ID、Product ID、设备类等）
  4. 分配唯一地址
  5. 读取配置/接口/端点描述符
  6. 匹配类驱动或厂商驱动并完成配置

因为每个设备都按统一格式“自我描述”，主机就能自动识别并接管，不需要用户手工配置底层细节。

USB 供电机制
USB 同时是数据总线和供电总线，常见 VBUS 为 5V。

基础规则可以这样理解：

  • Host/Hub 提供 VBUS 电源
  • Device 按规范从 VBUS 取电（总电流受版本和协商状态限制）
  • 设备在“未配置前”只能用较小默认电流，完成枚举并获准后才可申请更高电流
  • 设备的功耗信息会写在配置描述符里，供 Host 做电源预算

对 Type-C 来说，还通过 CC 引脚识别角色（供电端/受电端）与电流能力。

工程上你会看到：VBUS 检测、限流/保险丝、ESD、防反灌设计，这些都属于 USB 供电可靠性的一部分。

  • 3.USB 硬件结构
    USB 硬件结构
    从硬件角度看，USB 通常由 4 部分组成：
  • 连接器：Type‑A、Micro‑USB、Type‑C 等物理接口
  • 传输线：电源线（VBUS/GND）+ 数据线（D+/D‑，USB2.0）
  • 控制器/PHY：MCU 里的 USB OTG/Device 控制器和物理层收发器
  • 保护与电源电路：ESD 管、共模/串联电阻、保险丝、VBUS 开关或检测电路
    你画板子时，本质就是把这 4 块按规范连好。

USB 接口类型
常见接口可以按“代际 + 形态”理解：

  • 传统 USB：Type‑A（主机口常见）、Type‑B（打印机等）、Mini‑B、Micro‑B
  • Type‑C：新一代通用接口，正反可插，可承载 USB2.0/USB3.x/PD/Alt Mode
    注意“Type‑C 是接口形态，不等于一定是高速 USB3，也不等于一定支持 PD。”

USB 线内部结构
以 USB2.0 线为例，最核心是 4 根：

  • VBUS：5V 供电
  • GND：地
  • D+ / D‑：差分数据线
    更规范的线材还会有屏蔽层（Shield）和填充结构，降低 EMI、增强抗干扰。
    如果是 USB3.x 线缆，还会额外加多组超高速差分对（TX/RX）。

D+ 与 D‑ 的作用
D+ 和 D‑ 是 USB2.0 的数据差分对，作用是承载协议数据。

  • 两根线传的是互补变化信号，不是“D+ 发、D‑ 收”这种分工
  • 主机通过这对线完成设备检测、枚举、控制传输和数据传输
  • 全速 USB（FS）常见 12Mbps，就是在 D+/D‑ 上完成
    简单说：D+/D‑ 是 USB2.0 的“主通信通道”。

Type‑C 与传统 USB 区别
主要区别在“连接与能力扩展”：

  • 插头体验：Type‑C 正反可插，传统 A/B/Micro 多数有方向要求
  • 角色协商：Type‑C 用 CC1/CC2 做角色与电流能力识别
  • 能力上限：Type‑C 可扩展到更高功率（PD）和更多协议复用（如视频）
  • 兼容关系：Type‑C 也可以只跑 USB2.0（依然可能只有 D+/D‑）
    所以 Type‑C 是更现代的“统一物理入口”，但实际能力看设计有没有把协议和电源协商做全。

USB 差分信号简介
USB2.0 数据使用差分传输（D+ 与 D‑ 成对）主要是为了抗干扰和信号完整性：

  • 抗共模噪声：外界干扰同时耦合到两线时，接收端取差值后大部分能抵消
  • EMI 更可控：差分电流回路更紧凑，对外辐射更低
  • 走线要求：D+/D‑ 需等长、并行、阻抗匹配（常见目标 90Ω 差分）
  • 板级细节：通常会加 ESD、防浪涌、必要时串联小电阻做阻尼
    一句话：差分不是为了“更复杂”，而是为了在现实电磁环境下更稳定地传数据。
  • 4.USB 通信原理
    USB 的核心原理是“主机统一调度，总线分时传输”。

总线上只有 Host 负责发起事务，Device 只在被请求时响应。通信不是像串口那样两边都可随时主动发，而是由 Host 按时间片和带宽预算去安排每个端点何时传什么数据。

所以 USB 的稳定性来自“中心化调度 + 标准化协议栈”。

USB 数据传输流程
可按一次典型设备通信来理解：

  1. 设备接入
  2. 主机检测到接入并复位端口
  3. 枚举：读描述符、分配地址、选择配置
  4. 正常通信：主机按端点和传输类型发起事务
  5. 设备返回 ACK/NAK/数据包等响应
  6. 主机根据结果重试、继续或切换下一个端点

对应用层来说，看起来像“读写接口”；对总线层来说，其实是一连串严格时序的 token/data/handshake 事务。

主机轮询机制
USB 常说“轮询”，意思是主机按计划不断询问各设备端点：

  • 对中断端点（如鼠标键盘）按固定间隔轮询
  • 对批量端点（如 U 盘）在有剩余带宽时尽量传输
  • 对控制端点优先保证（枚举、配置、标准请求）
  • 对同步端点（音视频）按周期保障实时性

设备不能“抢总线说话”，只能在轮到自己时返回数据或状态（比如 NAK 表示暂时没数据）。

这也是为什么 USB 上很多“实时行为”最终取决于 Host 调度策略。

USB 为什么由主机控制
设计成主机控制有几个工程优势：

  • 避免总线冲突：统一仲裁，不会多个设备同时乱发
  • 便于热插拔管理：谁接入、谁掉线由主机统一感知和处理
  • 带宽可分配：不同设备按优先级与类型得到可预测资源
  • 系统安全与兼容性更好：驱动、权限、功耗预算集中在主机侧

简单说：USB 面向的是“一个系统带多个外设”的生态，中心调度比对等抢占更稳、更容易大规模兼容。

USB 数据包简介
USB 传输由多种包组成，理解这几个就够入门：

  • Token 包：主机发，说明“谁、方向、端点号”（如 IN/OUT/SETUP）
  • Data 包：真正承载数据（DATA0/DATA1 等）
  • Handshake 包：事务结果反馈（ACK/NAK/STALL）
  • SOF 包（帧起始）：用于时间基准与调度节奏（特别是 FS/HS）

你可以把一次事务看成：
主机先发“指令包（Token）”-> 某方发“数据包（Data）”-> 对方回“结果包（Handshake）”。

USB 速度等级
常见 USB 速度档位：

  • Low Speed (LS)：1.5 Mbps（早期低速外设）
  • Full Speed (FS)：12 Mbps（很多 MCU 设备端常用）
  • High Speed (HS)：480 Mbps（USB2.0 高速）
  • SuperSpeed (SS)：5 Gbps（USB3.0）
  • SuperSpeed+：10/20 Gbps（USB3.1/3.2 不同模式）

补充两个常见误区：

  • 接口是 Type‑C 不代表一定高速，Type‑C 也可能只跑 USB2.0 FS/HS
  • 协议速度上限不等于实际吞吐，实际还受主机调度、端点类型、协议开销、驱动实现影响。
  • 5.USB 枚举过程
    枚举就是：主机在设备刚接入时，按标准步骤“盘问”设备身份和能力，最后让系统给它配好驱动并进入可用状态。
    你可以把它理解成“设备入职流程”。

什么是枚举
枚举（Enumeration）是 USB 设备从“刚插入、无地址、未知类型”变成“有地址、可识别、可通信”的初始化过程。
没有枚举，设备就只是电气上连上了，系统并不知道它是谁、能干什么、该用什么驱动。

插入 USB 后发生了什么
典型流程（以设备模式为例）：

  1. 物理连接建立
    主机检测到端口电气状态变化（连接事件）。
  2. 端口复位
    主机对端口做 reset，让设备回到默认状态（地址 0）。
  3. 默认地址通信
    主机通过端点 0（EP0）发标准控制请求，先读取设备的基础信息。
  4. 读取关键描述符
    设备描述符、配置描述符（及其接口/端点信息）等。
  5. 分配唯一地址
    主机发送 SET_ADDRESS，设备从地址 0 切到新地址。
  6. 选择配置
    主机发送 SET_CONFIGURATION，设备进入工作配置。
  7. 驱动绑定与接口就绪
    OS 根据 VID/PID/Class 等信息匹配驱动，创建对应设备节点（比如虚拟串口 COM 口）。

获取设备描述符
设备描述符（Device Descriptor）是主机“认识你是谁”的第一份身份证，通常包含：

  • VID（厂商 ID）
  • PID（产品 ID）
  • bcdUSB（USB 规范版本）
  • bDeviceClass/SubClass/Protocol
  • bMaxPacketSize0（EP0 最大包长）
  • 字符串索引（厂家名、产品名、序列号）

实际中主机会先读一小段，再按需要读完整描述符，然后继续读取配置描述符树（Configuration/Interface/Endpoint）。

分配设备地址
刚上电设备默认地址是 0，只能临时通信。
主机在确认设备可正常响应后，发送 SET_ADDRESS(new_addr)。
设备按规范在指定时机切换到新地址，此后主机就用这个唯一地址访问它。
这个步骤解决了“同一总线上多个设备如何区分”的问题。

加载驱动流程
枚举拿到信息后，系统会走驱动匹配：

  • 先看硬件 ID（常见是 USB\VID_xxxx&PID_xxxx）
  • 再看兼容 ID/类信息（Class/SubClass/Protocol）
  • 匹配到类驱动（如 HID、MSC、CDC）或厂商驱动
  • 创建设备对象和用户可见入口（如端口、磁盘、输入设备）

如果没有匹配驱动，设备会出现在“未知设备”或带告警状态。

Windows 如何识别 USB
Windows 识别 USB 可以抓这几个关键点：

  • 识别依据

    • 硬件 ID：VID/PID
    • 设备类/接口类：决定可否走通用类驱动
    • 可选字符串：用于友好名称显示（产品名、序列号）

  • 驱动绑定逻辑（简化）
    a. PnP 管理器检测新设备
    b. USB 总线驱动上报硬件 ID/兼容 ID
    c. INF/驱动商店匹配最合适驱动
    d. 安装并启动功能驱动
    e. 创建设备节点（例如 CDC ACM 场景下出现 COMx）

  • ** STM32 CDC 虚拟串口时常见现象**

    • 枚举成功：设备管理器出现端口设备（COMxx）
    • 枚举失败：可能显示 Unknown USB Device / Device Descriptor Request Failed
    • 常见原因：描述符错误、时钟不稳、DP/DM 布线问题、VBUS/上拉配置不对、驱动未正确匹配
  • 6.USB 描述符解析
    描述符就是 USB 设备给主机看的“自我说明书”。主机通过读取这些结构体，决定设备类型、配置方式和驱动绑定。

Device Descriptor（设备描述符）
这是设备级总描述符，回答“我是谁”。常见关键字段：

  • idVendor：VID（厂商 ID）
  • idProduct：PID（产品 ID）
  • bcdUSB：支持的 USB 规范版本
  • bDeviceClass/SubClass/Protocol：设备类信息（有时放到接口层）
  • bMaxPacketSize0：端点 0 最大包长
  • iManufacturer/iProduct/iSerialNumber：字符串索引
  • bNumConfigurations：有几个配置可选

主机枚举时最先重点读它，用来建立设备身份。

Configuration Descriptor（配置描述符）
配置描述符回答“我有哪些工作模式”。
一个设备可以有一个或多个 configuration（多数简单设备只有 1 个）。

关键字段常见有：

  • wTotalLength：该配置下所有描述符总长度
  • bNumInterfaces：接口数量
  • bmAttributes：供电属性（总线供电/自供电）
  • bMaxPower：该配置声明的最大电流需求

主机会根据它决定是否启用该配置，并做电源预算。

Interface Descriptor（接口描述符）
接口描述符回答“这个配置里每个功能是什么”。
一个 configuration 可以含多个 interface（例如复合设备：CDC + HID）。

关键字段：

  • bInterfaceClass/SubClass/Protocol：功能类别（驱动匹配很关键）
  • bNumEndpoints：该接口下有几个非 EP0 端点
  • iInterface：接口字符串索引（可选）

很多设备把“类信息”放在接口级，而不是设备级。

Endpoint Descriptor（端点描述符）
端点描述符回答“数据怎么进出”。
端点是具体的数据通道，方向和类型都在这定义。

关键字段：

  • bEndpointAddress：端点号 + 方向（IN/OUT）
  • bmAttributes：传输类型（Control/Interrupt/Bulk/Isochronous）
  • wMaxPacketSize：单次最大包长度
  • bInterval：轮询间隔（中断/同步端点常用）

驱动真正收发数据时主要依赖端点信息。

String Descriptor（字符串描述符）
字符串描述符是“给人看的文本信息”，例如：

  • 厂商名（Manufacturer）
  • 产品名（Product）
  • 序列号（Serial Number）

它不决定底层协议能否通信，但影响系统显示名称、设备可识别性和多设备区分体验。
字符串通过索引与其他描述符字段（iManufacturer 等）关联。

VID 与 PID
VID/PID 是 USB 身份识别的核心：

  • VID：由 USB‑IF 分配给厂商
  • PID：厂商在自己 VID 下分配给具体产品

操作系统会用 VID+PID 组合生成硬件 ID（如 USB\VID_xxxx&PID_xxxx），这是驱动匹配最关键依据之一。

实践中：

  • 同一产品线不同功能常用不同 PID
  • 调试阶段乱用 VID/PID 可能导致驱动错绑
  • 量产应使用合法 VID/PID 策略（自有 VID 或合规授权方案）
  • 7.Endpoint（端点）详解
    Endpoint 可以理解成 USB 设备内部的“逻辑数据管道口”。
    主机不是直接对“设备整体”收发数据，而是对某个接口下的某个端点发起传输。

什么是 Endpoint
端点是 USB 协议层的地址化通信节点，通常由两部分标识：

  • 端点号（Endpoint Number）
  • 方向（IN 或 OUT）

例如 EP1 IN 和 EP1 OUT 是两个不同的逻辑端点。
端点还绑定传输类型（控制/中断/批量/同步）和最大包长等属性。

Endpoint0 为什么特殊
Endpoint 0（EP0）是所有 USB 设备必须实现的控制端点，专门用于控制传输，主要负责：

  • 枚举过程中的标准请求（读描述符、设地址、设配置）
  • 设备状态管理与控制命令

它特殊在：

  • 必选：没有 EP0 就无法枚举
  • 双向：要同时支持控制读写流程
  • 优先级高：设备接入后最先依赖 EP0 建立通信身份

所以 EP0 像“管理通道”，而 EP1/EP2…更多是“业务数据通道”。

IN 与 OUT 方向
方向是站在主机角度定义的：

  • IN：设备 -> 主机（主机发 IN token 来“取数据”）
  • OUT：主机 -> 设备（主机发 OUT token 来“送数据”）

很多初学者会误以为 IN/OUT 是站在设备角度，这一点最容易搞反。

单向通信概念
单个端点是单向的：

  • 一个端点实例只负责一个方向（IN 或 OUT）

要实现双向业务，通常需要成对端点，比如：

  • EP1 OUT：主机发命令给设备
  • EP1 IN：设备回数据给主机

注意 EP0 是控制传输例外场景，它流程上支持双向阶段，但本质仍按控制事务规则运行。

Endpoint 与 FIFO 的关系
端点是协议层逻辑概念，FIFO 是控制器硬件缓冲资源，二者关系是“逻辑端口映射到硬件缓冲”：

  • 端点定义“谁、往哪、包多大、类型是什么”
  • FIFO 提供“暂存数据、配合 USB 硬件收发”的物理缓冲

在 STM32 这类控制器里常见做法：

  • RX FIFO：供 OUT/SETUP 接收路径使用
  • 多个 TX FIFO：分别分配给不同 IN 端点（如 EP0 IN、EP1 IN）
  • 你在初始化里配置 FIFO 大小，本质是在做带宽/内存平衡

如果 FIFO 太小，可能导致吞吐下降或传输不稳定；分配合理则能显著提升 CDC/MSC 这类业务端点表现。

  • 8.USB 四种传输方式
    USB 把数据传输分成 4 类，核心区别在于：实时性、可靠性、带宽保证、重传机制。

Control 传输
Control 是控制传输，所有设备都必须支持（至少在 EP0）。
用途：枚举、配置、标准请求、类请求、厂商命令。

特点：

  • 可靠（有握手和重试）
  • 包长度通常较小
  • 优先级高（系统管理必须可达）
  • 典型场景：GET_DESCRIPTOR、SET_ADDRESS、SET_CONFIGURATION

Bulk 传输
Bulk 是批量传输，适合“大量数据、但不强调固定时延”。

特点：

  • 可靠（错误可重传）
  • 吞吐高（有剩余带宽就尽量跑）
  • 时延不确定（总线忙时会被延后）
  • 典型场景：U盘、CDC 虚拟串口数据面、打印数据

Interrupt 传输
Interrupt 是中断传输，适合“小数据量、周期性上报、较低延迟”。

特点：

  • 主机按 bInterval 周期轮询
  • 延迟可预测性比 Bulk 更好
  • 可靠（有握手，失败可在后续周期补）
  • 典型场景：鼠标、键盘、按键状态、传感器状态上报

Isochronous 传输
Isochronous 是同步传输，适合“实时流媒体”。

特点：

  • 预留周期带宽，时序优先
  • 不做重传（错了就丢，保证时间连续）
  • 适合连续流，不追求每包绝对可靠
  • 典型场景：USB 音频、摄像头视频流

四种传输方式对比

  • 可靠性

    • 高：Control / Bulk / Interrupt
    • 低（不重传）：Isochronous

  • 实时性/时延可预测

    • 最好：Isochronous
    • 较好：Interrupt
    • 一般：Control
    • 最弱：Bulk（受总线空闲影响）

  • 吞吐能力

    • 高：Bulk
    • 中：Isochronous（按保留带宽持续）
    • 低到中：Interrupt / Control

  • 典型用途

    • Control：管理与配置
    • Bulk：大数据可靠传输
    • Interrupt：周期小包状态
    • Isochronous：音视频实时流
  • 9.USB 常见设备类
    “设备类（Class）”就是 USB 设备对外声明的功能标准。只要设备按类规范实现，操作系统通常能直接用通用类驱动识别它。

HID（Human Interface Device）
典型设备：键盘、鼠标、游戏手柄、触摸板。

特点：

  • 小数据、低延迟、周期上报
  • 通常走 Interrupt 端点
  • 系统内置支持非常成熟
  • 很多简单自定义控制器也会伪装成 HID，省去安装专用驱动。

CDC（Communications Device Class）
典型设备：USB 虚拟串口（CDC ACM）、部分调制解调设备。

特点：

  • 把 USB 设备抽象成通信设备（常见是 COM 口）
  • 开发板日志输出、上位机命令通道常用
  • 在不同系统上的驱动细节略有差异（如 Windows 历史版本）

MSC（Mass Storage Class）
典型设备：U 盘、移动硬盘、读卡器。

特点：

  • 主机把设备识别为块存储
  • 常见协议组合是 Bulk‑Only + SCSI 命令集
  • 用户体验就是“插上出现盘符”

Audio（USB Audio Class）
典型设备：USB 麦克风、USB 声卡、耳机。

特点：

  • 强调连续实时流
  • 常用 Isochronous 传输
  • 包括采样率、声道、位宽等音频能力描述

UVC（USB Video Class）
典型设备：USB 摄像头、采集卡（部分）。

特点：

  • 视频流传输，常配合 Isochronous/Bulk
  • 系统可用通用摄像头框架直接调用
  • 会声明分辨率、帧率、编码格式等能力

为什么设备“不需要驱动”
严格说不是“不要驱动”，而是“不需要厂商单独安装驱动”。原因是：

  • 操作系统已内置类驱动（HID/MSC/UVC/Audio/CDC 等）
  • 枚举时主机读到设备类信息后，自动匹配通用驱动
  • 设备按标准类协议实现即可被系统接管

所以用户感觉是“即插即用、免驱”。

但本质上驱动依然存在，只是由系统自带并自动绑定了。
只有当你做 Vendor Specific（自定义类）或功能超出标准类范围时，才常常需要专用驱动/INF。

11.USB OTG 工作原理
OTG 的核心是：同一个 USB 控制器支持两种状态（A-Device/Host 与 B-Device/Peripheral），并且能在连接过程中按规则切换供电、谁枚举、谁被枚举。

流程上可以理解为：先判定初始角色 -> 建立会话（Session）-> 按需发起角色切换。

Host 与 Device 动态切换
在 OTG 里角色不是永久固定，设备可在特定条件下切换：

  • 初始通常由硬件连接状态决定谁先当 Host（A-device）
  • 当前 Host 负责 VBUS 供电和总线调度
  • 需要切换时，通过 OTG 协议协商后由另一方接管 Host 职责
  • 切换后新的 Host 重新管理总线，原 Host 退回 Device

注意：不是“随时硬切换”，而是受协议状态机和电源条件约束。

ID 引脚作用
这是传统 Micro‑USB OTG 里的关键识别脚（Type‑C 不再用它）：

  • ID 接地（0）：表示 A‑device，通常作为 Host
  • ID 悬空（1）：表示 B‑device，通常作为 Peripheral
  • OTG 线缆通过是否把 ID 拉低来告诉设备“你该当主机还是从机”

所以 ID 本质是“角色初判硬件信号”。

Session Request Protocol（SRP）
SRP 用于：B‑device 请求 A‑device 打开 VBUS 并开始会话。

典型场景是 A‑device 省电关了 VBUS，B‑device 有通信需求，就用 SRP 发起“唤醒请求”，让 A‑device 重新供电并启动会话。

可以把 SRP 理解成“从设备申请开机通信”。

Host Negotiation Protocol（HNP）
HNP 用于：已建立会话后，A/B 双方协商交换 Host 权限。

常见过程是当前 Host 让出总线，另一方接管成为新 Host。

可以把 HNP 理解成“会话中途换司机”。

OTG 线识别机制
分两代看最清楚：

  • 传统 Micro‑USB OTG：靠 ID 引脚 + OTG 线缆（ID 拉低/悬空）识别角色
  • USB Type‑C：不走 ID 脚，主要靠 CC1/CC2 上的 Rp/Rd 关系识别 Source/Sink 与连接方向，角色切换更多结合 Type‑C/PD 策略完成
  • 12.USB 代码实验
    1.USB 虚拟串口
    USB 虚拟串口（CDC‑ACM）的本质是：把 USB 设备伪装成“传统串口”给上位机用，这样 PC 端看到的是 COMx（Windows）或 /dev/ttyACM0（Linux）这样的串口设备，但底层传输其实是 USB 数据包，不是 UART 电平。

USB 虚拟串口的关键是“接口兼容，传输不兼容”。兼容的是上层编程模型，不兼容的是底层物理链路。PC 端应用一直以为自己在操作串口：打开端口、设置波特率、读写字节流；但设备端并没有走 UART，而是把这些操作映射到 USB CDC‑ACM 协议上。

核心概念先抓四个：枚举、接口、端点、类请求。设备插入后，主机先做枚举，读取设备描述符和配置描述符。虚拟串口设备会声明自己是 CDC 类，并通常拆成控制接口和数据接口。数据接口上有 Bulk IN/Bulk OUT 两个端点，分别对应设备发主机、主机发设备；控制接口上常有一个中断端点用于状态通知。主机看到这套描述后，加载 CDC‑ACM 驱动，并在系统里创建一个 COM 口或 tty 设备。到这里“虚拟串口”才成立，本质是驱动层给应用伪造了传统串口抽象。

实现原理是把“串口 API 语义”翻译成“USB 传输与控制请求”。比如上位机调用串口库设置 115200/8N1，并不是在改 USB 线速，而是驱动发一个 CDC 类请求（如 SET_LINE_CODING）给设备。设备可以选择仅保存这个参数（纯虚拟通道场景），也可以把它同步到真实 UART（USB‑UART 桥接场景）。同样，打开/关闭串口、DTR/RTS 变化，会变成 SET_CONTROL_LINE_STATE 这类控制请求。数据收发则不走这些控制请求，而走 Bulk 端点的数据包传输。

数据路径可以理解为双向缓冲队列。主机写串口时，驱动把用户数据切成 USB 包，通过 Bulk OUT 下发；设备 USB 协议栈在接收完成回调里拿到数据，放入环形缓冲区，再交给业务层。设备回传时，业务层把待发数据写入发送缓冲，USB 栈在端点空闲时提交 Bulk IN 传输，主机轮询到该端点后取走，驱动再把数据交给上层串口读接口。看起来像连续字节流，实际上是“分包 + 缓冲 + 轮询调度”的过程。

要点是 USB 通信由主机主导，设备不能像 UART 那样随时在总线上主动起传输，只能在主机发起事务时应答。所以固件必须处理好发送状态、分包和缓冲，否则就会出现你常见的“偶发发不出去”或“高负载丢数据”。因此典型 CDC 固件都会有接收回调、发送完成回调、环形缓冲区和状态机，用来把上层的“串口式读写”平滑映射到底层 USB 事务。

4.24 环形缓冲区

  • 1.环形缓冲区是什么
    环形缓冲区（Ring Buffer / Circular Buffer）是一种固定长度的队列结构，常用于嵌入式里的串口收发、日志缓存、传感器数据流等场景。
    它的核心特点是：内存一次分配、循环复用、先进先出（FIFO）。
    和普通数组相比，环形缓冲区更适合“持续流式数据”，因为读写指针走到末尾后会回到起点，不需要频繁搬移数据。
  • 2.为什么项目里常用环形缓冲区
  1. 实时性好：写入和读取通常是 O(1)。
  2. 内存可控：容量固定，避免动态分配带来的碎片问题。
  3. 适配中断+任务模型：例如 UART 接收中断写入，主循环/任务读取处理。
  4. 解耦生产者与消费者：数据到达速度和处理速度不一致时能起缓冲作用。
  • 3.基本组成
    一个典型环形缓冲区通常包含：
  • buffer[]：数据存储区
  • size：缓冲区总长度
  • head：写指针（下一个写入位置）
  • tail：读指针（下一个读出位置）

可选字段：

  • count：当前已存数据量（也可不用，靠指针关系判断）
  • 4.工作原理（读写流程）
    写入（push）：
    1.判断是否“满”
    2.把数据写到 buffer[head]
    3.head = (head + 1) % size

读取（pop）：
1.判断是否“空”
2.读 buffer[tail]
3.tail = (tail + 1) % size

% size 的作用就是“走到末尾自动回绕”。

  • 5.空与满的判定方法

常见有两种：

  1. 浪费一个存储单元法（最常见）
  • 空：head == tail
  • 满：(head + 1) % size == tail
    优点是实现简单，缺点是可用容量是 size - 1。
  1. 增加 count 计数法
  • 空：count == 0
  • 满：count == size
    优点是容量利用完整，缺点是需要额外维护 count，并发下要注意一致性。

4.27 单片机内部的Flash编程

单片机里的 Flash，本质上就是一块掉电不丢的 NOR 型存储器：能按地址读、按规则写，但不能像 RAM 那样随便改——写之前通常要先擦，而且擦除粒度比写入粒度大得多。做参数保存、固件升级、日志区、出厂配置，都离不开它。下面按 H7 的实际特性来讲，不绑具体工程。

  • 1.先搞清楚三件事：读、擦、写
操作 特点 典型用途
读 和普通内存映射一样，CPU 直接取指、load 数据 程序运行、读常量
擦除 按扇区（sector）擦，擦完一般是 0xFF 改数据前必须做
编程（写） 只能把 1 改成 0，不能反过来 写入新数据

记住一句就够：Flash 只能“往下写”，不能往上改。要改某个字节，往往得把所在扇区整片擦掉，再把整块数据写回去。

H7 上常见参数（以 H743/H750 一类大容量片为例，具体以你芯片数据手册为准）：

  • 总容量常见 1MB / 2MB
  • 双 Bank 组织（Bank1 / Bank2），每 Bank 多个扇区
  • 扇区大小常见 128KB
  • 编程单位是 Flash Word（256 bit，即 32 字节），不是单字节
  • 地址对齐要满足手册要求，乱对齐会直接报错或写不进去

不同 H7 子系列扇区划分、单/双 Bank 切换会略有差别，以 RM0433 / 对应 Part Number 的数据手册为准，别死记某一型号的表。

  • 2.H7 Flash 在系统里长什么样
    2.1 内存映射
    程序默认从 Flash 启动。CM7 视角下，Flash 挂在固定映射地址（常见从 0x0800_0000 起），CPU 取指、读常量都走这条路径。

如果是双核 H7（M7 + M4），两边可能共用同一片 Flash，但同一时刻只能有一个核在做擦写，还要考虑 HSEM、中断屏蔽、谁先占 Flash 控制器等问题——单核工程可以先不管，双核一定要单独设计。

2.2 和 F1/F4 不一样的地方
H7 跑在较高主频，Flash 访问要走 Flash Latency（等待周期 WS）。系统时钟拉高以后，FLASH_ACR 里的 LATENCY 必须配对，否则表现就是莫名 HardFault、读错指令、调试时“偶发”崩。

另外 H7 有 I‑Cache / D‑Cache。Flash 里刚写完的数据，如果 D‑Cache 里还有旧行，CPU 读到的可能不是刚写进去的值——这是 H7 上非常容易踩的坑，后面单独说。

  • 3.标准操作流程

3.2 擦除

  • 先写副本再切换有效标志，别原地覆盖唯一一份
  • 关键数据加 CRC32

    内部 Flash 适合：少量配置、校准值、序列号、升级标志位——容量不大，但跟着芯片走、成本低。

  2. 先擦后写，不能单字节改
  3. 擦写时注意执行位置，别从正在擦的扇区跑代码
  4. H7 必须处理 Cache，否则读写不一致
  5. 参数区要扇区对齐 + CRC + 掉电保护策略

4.28 使用USB+SDNAND实现虚拟U盘

  • 1.基础概念
    虚拟 U 盘指的是：MCU 通过 USB 以 Mass Storage Class（大容量存储类）设备身份接入 PC，PC 把后面的存储介质当成普通 U 盘，可以格式化、拷贝文件。

这里用的存储是 SD NAND，走 SDMMC 接口，和 SD 卡一样按 512 字节扇区读写。上面通常有 FAT32 文件系统，PC 和 MCU 看到的都是这一层。

两条访问路径：

FatFs 管的是文件（路径、簇、目录）；USB MSC 管的是扇区（LBA + 512 字节块）。底层是同一块 SD NAND，但上层协议完全不同。

MSC 用的是 Bulk-Only Transport（BOT）：PC 发 SCSI 命令（读容量、读扇区、写扇区），设备在 storage_if 里用 SD 读写响应。PC 不经过 FatFs，它自己解析 FAT 分区。

  • 2.为什么不能 FatFs 和 USB 同时用
    FatFs 会在 RAM 里缓存 FAT 表、当前目录等。PC 通过 MSC 直接改扇区时，MCU 里的缓存不会更新；MCU 写文件时，PC 也看不到实时变化。两边同时访问同一块盘，容易把文件系统写坏。

所以规则很简单：同一时刻只允许一方访问 SD NAND。

  • PC 要用盘 → MCU 先 f_mount(NULL) 卸载 FatFs
  • PC 拔线 → MCU 再 f_mount 挂回来

USB 连接/断开可以用设备状态回调自动做这件事。

  • 3.实现流程
    3.1 存储分层
    最底层：SDMMC + SD NAND 块读写（Init、ReadBlocks、WriteBlocks、等卡 ready）。

中间两层并行：

  • FatFs 路径：sd_diskio.c 把 FatFs 的 disk_read / disk_write 接到 SD 驱动，给 MCU 本地用。
  • USB 路径：usbd_storage_if.c 实现 MSC 要求的 storage 回调，内部同样调 SD 块读写，给 PC 用。

可以把 MSC 的扇区操作单独放到 bsp_usb_msc 里，和 FatFs 共用底层 SD 接口，避免两套读写逻辑。

3.2 实现 storage 回调
MSC 库通过下面几个函数操作“磁盘”：

步骤 回调 做什么
初始化 Init 读卡信息，保存扇区总数、扇区大小
报容量 GetCapacity 把扇区数、512 字节扇区大小交给主机
查状态 IsReady 确认 SD 处于可传输状态
读 Read 按 LBA 读若干扇区到 USB 缓冲区
写 Write 把 USB 缓冲区数据写到对应 LBA
写保护 IsWriteProtected 无写保护返回 0

Read / Write 的参数：blk_addr 是起始扇区号（LBA），blk_len 是扇区个数。每次调用读或写连续的一块扇区，底层就是 ReadBlocks(buf, blk_addr, blk_len)。

GetCapacity 必须用卡的真实 LogBlockNbr，不能用固定占位值，否则 PC 看到的容量不对。

3.3 启动顺序
MCU 上电后的逻辑顺序：

FatFs 自测和 USB 启动不要颠倒：必须先卸 FatFs，再开 USB。否则 PC 一插上就可能和 FatFs 抢盘。

3.4 PC 连接/断开时的切换
注册 USB 设备状态回调：

  • 进入 CONFIGURED（PC 枚举完成）→ 再执行一次 f_mount(NULL)，确保 FatFs 已卸
  • 回到 DEFAULT / ADDRESSED（PC 断开）→ f_mount 重新挂载，MCU 恢复文件 API

这样 MCU 平时可以读写文件，PC 插线当 U 盘，拔线后 MCU 继续用 FatFs，中间不用手动切换。

3.5 数据怎么流通

  • PC 读文件
    PC 发 READ(10) → MSC 库调 StorageRead → SD 读扇区 → 数据经 USB 发给 PC → PC 自己按 FAT 解析成文件。

  • PC 写文件
    PC 发 WRITE(10) → MSC 库调 StorageWrite → 数据写入 SD 对应扇区 → PC 改的是 FAT 和文件内容所在的物理扇区。

  • MCU 读文件
    f_open / f_read → FatFs 算簇和扇区 → diskio → SD 读块。

两条路最终都是按 LBA 读写 512 字节扇区，区别只在谁发起、谁解析文件系统。

流程串起来

要点就三条：

  1. MSC 的 storage 回调里做 SD 扇区读写，容量从卡信息里读。
  2. 开 USB 前卸 FatFs，用状态回调在 PC 插拔时自动 mount/unmount。
  3. SD 上先有合法 FAT（MCU 侧 mkfs 或 PC 格式化），PC 才能当 U 盘正常用。

4.29 双缓冲区

  • 1.基础概念
    什么是双缓冲（Double Buffer / Ping-Pong）

双缓冲是指准备两块大小相同的内存，在同一时刻：

  • 一块交给硬件（如 DMA）写入新数据 —— 称为 写缓冲 / 前台缓冲
  • 一块交给软件（CPU）读取、解析、转发 —— 称为 读缓冲 / 后台缓冲

当写缓冲收满一帧后，两块缓冲交换角色，循环往复。这种交替方式也叫 Ping-Pong（乒乓）缓冲。

为什么 UART 接收常用 DMA + 双缓冲

UART 接收是持续、异步的：数据随时可能到来，速率由对端决定。

方式 特点 问题
轮询 读 DR 寄存器 实现简单 CPU 一直占着，效率低，高速易丢字节
单字节中断 每字节进中断 中断过于频繁，开销大
DMA 单缓冲 CPU 不参与搬运 收满或处理期间，新数据无处可写
DMA 双缓冲 DMA 搬运 + CPU 并行处理 需要正确切换，但可连续接收

双缓冲的核心价值：让 DMA 写和 CPU 读并行，减少丢包，降低 CPU 负担。

一帧数据如何界定
双缓冲通常按帧切换，而不是按固定字节 blindly 切换。常见帧边界：

  1. 固定长度：每 N 字节切换（协议定长包）
  2. 接收完成中断：DMA 传完预定长度
  3. 空闲线检测（IDLE）：连续一段时间无新字节，视为一帧结束（变长文本、Modbus 等常用）
  4. 协议头 + 长度字段：软件解析后确定帧长

双缓冲涉及的三类角色

  • 生产者：UART + DMA，往写缓冲填数据
  • 消费者：主循环 / 任务 / 协议栈，从读缓冲取数据
  • 协调者：中断或回调，在帧结束时交换缓冲、重启 DMA
  • 2.为什么单缓冲不够用
    类比原大纲「两个模块不能同时操作同一份资源」，这里的问题是：DMA 和 CPU 不能在同一时刻安全地共用同一块接收缓冲。

单缓冲的典型困境
只有一块缓冲 buf 时，DMA 一直在写 buf：

问题归纳：

  1. 覆盖：CPU 还没读完，DMA 已开始写同一区域
  2. 停收：为避免覆盖，只能等 CPU 处理完再重启 DMA → 停收期间来的数据进 UART 硬件 FIFO，FIFO 满则丢字节
  3. 拷贝开销：停收后把 buf 拷到临时区再重启 DMA，多一次内存拷贝，延迟更大

「停收等待」vs「双缓冲并行」

单缓冲 + 停收 双缓冲
DMA 状态 处理时停止 几乎始终运行
CPU 与 DMA 串行，抢同一块内存 并行，各用一块
连续高速数据 易丢包 只要处理够快，可连续收
实现复杂度 低 中等（需切换逻辑）

双缓冲也解决不了什么
双缓冲不是无限队列：

  • 只有 2 块缓冲；若 CPU 长时间不处理，写缓冲用完、读缓冲未释放，仍会无缓冲可用
  • 缓冲太小，一帧超过单块容量，仍会溢出
  • 需要明确的帧边界和释放时机

因此双缓冲是「一块写、一块读」的流水线，不是无限 backlog。

4.30 把程序放进 RAM 里运行的情况

  • 1.为什么要把代码放在 RAM 里执行？
    MCU 上电后，默认从非易失存储器（Flash / 内部 ROM）取指。多数应用一直这样运行即可。但在以下场景中，必须把部分或全部代码放到 RAM 里执行：
场景 原因
IAP / OTA / 自升级 擦写 Flash 时，正在被操作的 Flash 区域不能同时作为代码源，否则取指会出错
Bootloader 跳转 新固件先加载到 RAM，校验后再执行
性能优化 RAM 访问延迟通常低于 Flash，对时间敏感代码有帮助
动态加载 代码来自外部存储、通信接口等，运行时才写入 RAM
调试特殊布局 某些调试或 RAM 启动方案需要代码链接到 RAM

常见做法是：程序仍从 Flash 正常启动，只把需要的那几个函数放到 RAM 执行。这是工业界最常用、也最适合入门的方式。

  • SP、PC 是什么（Cortex‑M，STM32）
    SP = Stack Pointer 栈指针
    PC = Program Counter 程序计数器
    这两个是 CPU 内核里的核心寄存器，上电复位第一步硬件自动从向量表读取这两个值。

1.PC（程序计数器）

  • 作用：保存下一条要执行指令的地址，CPU 跟着 PC 去取指令运行
  • 复位时：硬件从向量表第2个位置读出地址，赋值给 PC
    这个地址就是 Reset_Handler（复位中断服务函数，在 startup.s 里面）
  • 效果：PC = Reset_Handler 地址 → CPU 立刻跑去执行复位启动代码

简单记：PC 决定 CPU「去哪跑代码」

2.SP（栈指针）

  • 作用：标记栈当前的顶部地址
  • 栈用来：函数调用、局部变量、中断入栈保存寄存器、临时数据
  • 复位时：硬件从向量表第1个位置读出初始栈顶地址，赋值给 SP
  • Cortex‑M 是满递减栈：先 SP 自减，再往栈里存数据

简单记：SP 决定「栈放在RAM哪里」

向量表前两项（重点！）
向量表存放在 Flash 起始地址：

  • 偏移0：初始SP值（栈顶地址）
  • 偏移4：复位入口地址（给PC）

上电复位硬件自动做这一步，不需要软件写代码：

  1. 读 0x08000000 → 放进 SP
  2. 读 0x08000004 → 放进 PC
  3. CPU 跳去 Reset_Handler，开始跑 startup.s

4.32 以太网模块(w5500)

  • 1.以太网是什么
    以太网（Ethernet） 是目前局域网（LAN）里最常用的有线通信技术。你办公室、家里的路由器，开发板上的RJ45 网口，底层基本都是以太网。

它的核心思路很简单：

  1. 多台设备挂在同一条「总线」上（早期是共享介质，现在是交换机点对点）
  2. 用 MAC 地址 标识每一台设备
  3. 数据被打包成 以太网帧（Frame） 在链路上传输

常见速率：

标准 速率 线缆
10Base-T 10 Mbps 双绞线
100Base-TX 100 Mbps 五类线
1000Base-T 1 Gbps 五类/超五类线

W5500支持 10/100 Mbps自适应，不支持千兆。

  • 2、网络分层：先知道自己在哪一层
    做嵌入式联网，不必背完整 OSI 七层，但下面几层要分得清：
代码块 层级 协议/硬件
1 应用层 HTTP、MQTT、自定义协议
2 传输层 TCP、UDP
3 网络层 IP、ICMP、ARP
4 数据链路层 以太网 MAC
5 物理层 PHY、网线、变压器

类比寄快递：

  • 物理层：公路、卡车（电信号、网线）
  • MAC 层：小区门牌号（MAC 地址，全球唯一硬件地址）
  • IP 层：收件人 IP 地址（可配置、可变化）
  • TCP/UDP：快递单类型（可靠传输 vs 尽力而为）
  • 应用层：包裹里具体是什么（网页、传感器数据等）

MCU 做联网时，你要想清楚：哪些层由软件实现，哪些层由硬件芯片代劳——这正是 W5500 的价值所在。

  • 3、以太网帧结构
    一帧以太网数据大致如下：
  • 目的MAC：发给谁（广播地址 FF:FF:FF:FF:FF:FF 表示所有人）

  • 类型：上层协议，例如 0x0800 表示 IPv4

  • CRC：校验

  • 7、嵌入式以太网方案对比
    MCU 接入以太网，常见三种路线：

方案1：MCU 内置 MAC + 外置 PHY
例如 STM32H7 自带 ETH 外设，外接 LAN8720 等 PHY。
优点：带宽高、灵活、可跑完整 LwIP
缺点：软件栈复杂、占用 RAM/Flash、调试成本高

方案2：MCU + 软件 TCP/IP 协议栈（如 LwIP）+ 外置 MAC/PHY
协议栈在 MCU 上跑，工作量大，但可深度定制。

方案3：MCU + 硬件 TCP/IP 芯片（W5500 属于这类）
TCP/IP 协议在芯片内部用硬件逻辑实现，MCU 只通过 SPI 操作 Socket。
优点：开发快、占用 MCU 资源少、行为稳定
缺点：灵活性低于纯软件栈，部分高级特性不支持（如 IP 分片）

  • 8、W5500 是什么
    W5500 是韩国 WIZnet 的硬件 TCP/IP 以太网控制器，一颗芯片集成：
  • 硬件 TCP/IP 协议处理（TCP、UDP、IPv4、ICMP、ARP、IGMP、PPPoE 等）
  • 10/100M 以太网 MAC + PHY
  • 32 KB 内部收发缓冲区
  • 8 个独立硬件 Socket
  • SPI 从机接口（最高约 80 MHz，Mode 0 / Mode 3）

架构可理解为：

MCU不必自己实现ARP、TCP握手、重传等，只需：配置网络参数 → 打开Socket → 收发数据。

  • Master Inter Data Idleness: 00 Cycle — 连续两次传输之间不插入额外空闲时钟。
  • Master Receiver Auto Susp: Disable — 关闭接收自动暂停，主机持续控制收发时序。
  • Master Keep Io State: Master Keep Io State Disable — SPI 关闭后不保持 IO 最后状态，省电且避免引脚状态异常。

帧结构
一次写操作依次包含三个阶段：

Address Phase（16 bit）
经MOSI发送目标寄存器或缓冲区的16位偏移地址，MSB先传。

Control Phase（8 bit）
经MOSI发送控制字节，包含块选择BSB[4:0]、读写位RWB、操作模式OM[1:0]。写操作中RWB为Write，OM为00表示VDM变长模式。

Data Phase（N×8 bit）
经MOSI连续发送待写入数据。VDM模式下地址阶段只出现一次，后续可连续写入多个字节。

SCSn时序
帧开始前SCSn由高变低；整个地址、控制及数据阶段SCSn保持低电平；全部数据发送完成后SCSn恢复高电平。

MISO行为
写操作期间MISO为高阻，主机不采样MISO。

  • VDM 模式下读 SPI 数据帧

帧结构:
Address Phase（16 bit）

Control Phase（8 bit）

Data Phase（N×8 bit）

时序要点
时钟 0～23：主机发送地址与控制，MISO 无效。
时钟 24 起：从 MISO 接收数据字节。
SCSn 在完整收发结束前保持低电平。

与写操作的差异
写操作数据经 MOSI 输出，读操作数据经 MISO 输入；Address Phase 与 Control Phase 均由 MOSI 承载，差异仅在 RWB 与 Data Phase 方向。

4.33 LAN8720以太网模块

LAN8720A 是一颗 10/100M 以太网物理层芯片（PHY）。它负责把 MAC 侧的数字信号转换成网线上的模拟信号，并完成链路检测、自协商和 Auto-MDIX。它本身不包含 TCP/IP 协议栈，也不替代 MCU 里的 MAC。

典型连接关系是：

  • 1.以太网硬件分层
    完整以太网口通常由三部分组成：

  1. MAC
    负责以太网帧的发送、接收、地址过滤、CRC 等。很多 MCU 片内就带 ETH MAC。

  2. PHY
    负责物理层收发。LAN8720A 就属于这一层。

  3. 变压器 + RJ45
    负责电气隔离和线缆接口。可以外挂，也可以做到网口座里。

MAC 和 PHY 之间需要标准数字接口，常见的是 MII 和 RMII。LAN8720A 使用的是 RMII。

  • 2.MII
    MII 全称 Media Independent Interface，是 IEEE 802.3 定义的 MAC 与 PHY 接口。
    “媒体无关”的含义是：MAC 不关心对面是铜缆还是光纤，只按统一数字脚收发数据；介质相关工作交给 PHY。

2.1 据宽度和时钟

  • 发送数据：TXD[3:0]，4 bit
  • 接收数据：RXD[3:0]，4 bit
  • 100 Mbps：时钟 25 MHz
    4 bit × 25 MHz = 100 Mbps
  • 10 Mbps：时钟 2.5 MHz
    4 bit × 2.5 MHz = 10 Mbps

MII 的发送和接收使用两套独立时钟：

  • TX_CLK
  • RX_CLK

MII 功能完整，但引脚多，布线成本高，对引脚紧张的 MCU 不太友好。

  • 3.RMII
    RMII 全称 Reduced Media Independent Interface，是 MII 的精简版本，目标是减少引脚数量，同时仍支持 10/100 Mbps。

3.1 精简方式
RMII 相对 MII 做了这些调整：

  • 数据位宽从 4 bit 减到 2 bit
  • 100M 时钟从 25 MHz 提高到 50 MHz
  • 收发共用同一个 REF_CLK
  • 将 CRS 和 RX_DV 合并为 CRS_DV
  • 去掉独立的 COL
  • RX_ER 变为可选

100 Mbps 时仍然满足带宽：
2 bit × 50 MHz = 100 Mbps

10 Mbps 时，RMII 通常仍使用 50 MHz 参考时钟，由内部逻辑完成速率适配，不像 MII 那样把时钟降到 2.5 MHz。

4.34 RS485

  • 1.RS485 概念与协议特性
    RS485 是什么
    串行通信标准家族

在工业控制、仪器仪表、楼宇自动化等领域，设备之间经常需要通过线缆进行远距离、抗干扰的数据传输。为此，业界形成了一系列串行通信电气标准，其中最常用的三个是：

标准 全称 传输方式 最大距离 最大节点数 典型应用
RS232 Recommended Standard 232 单端信号，点对点 约15 m 2（1发1收） 电脑串口、调试接口
RS422 — 差分信号，点对点 约1200 m 10 长距离点对点
RS485 TIA/EIA-485 差分信号，总线型 约1200 m 32（可扩展更多） 工业现场总线、Modbus

RS485 由美国电子工业协会（EIA）制定，现行标准为 TIA/EIA-485-A。它定义的是物理层（Physical Layer）的电气特性，并不规定数据帧格式、通信协议或软件流程。

RS485 的定位
RS485 只解决一个问题：如何在较长距离、存在电磁干扰的环境下，让多个设备可靠地交换二进制数据。

它规定了：

  • 用哪两根线传信号（A 线、B 线）
  • 电压多少代表逻辑 0 和逻辑 1
  • 驱动器能驱动多远、挂多少设备
  • 接收器能识别多大的电压差

至于“发什么数据、怎么组帧、谁先发、出错怎么办”，RS485 标准本身不管。这些由上层协议决定，例如 Modbus RTU、自定义帧协议等。

可以这样理解分层关系：

  • 典型应用场景
    RS485 因其远距离、多节点、抗干扰的特点，广泛应用于：
  • 工业自动化：PLC 与变频器、传感器、仪表通信
  • Modbus RTU 总线：目前最常见的 RS485 上层协议
  • 楼宇自控：温湿度采集、门禁、照明控制
  • 电力监测：电表、保护装置组网
  • 安防系统：报警主机与探测器通信
  • 核心通信特性
    差分信号传输
    RS485 使用差分信号传输数据，这是其抗干扰能力的核心。

单端信号（以 RS232 为例）：用一根信号线相对于地（GND）的电压表示 0 或 1。线缆上的噪声会叠加到信号上，距离越远、干扰越大，信号越容易被破坏。

差分信号（RS485）：用两根线 A 和 B 之间的电压差表示 0 或 1，而不是某根线对地的绝对电压。

由于两根线在同一根双绞线里，经过相同的路径，受到的电磁干扰（共模噪声）几乎一样。接收端只关心A、B之间的电压差，共模噪声被抵消，因此 RS485 在工业现场具有很强的抗干扰能力。

半双工与全双工
RS485 支持两种工作模式：
半双工（Half-Duplex）

  • 同一时刻，总线上只能有一个设备在发送
  • 所有设备共用一对 A/B 线
  • 发送前需要切换到”发送模式”，发完后切回”接收模式”
  • 这是最常见的 RS485 用法，成本低、布线简单

全双工（Full-Duplex）

  • 使用两对 A/B 线，一对用于发送，一对用于接收
  • 可以同时收发，无需切换方向
  • 需要 RS422 收发器或具备全双工能力的 RS485 芯片
  • 成本更高，应用较少

多点通信（总线型）
RS485 采用总线型拓扑，一条总线上可以挂载多个设备，每个设备有唯一地址，由主设备轮询或广播。
标准规定一条总线最多支持 32 个标准负载单元（1 个收发器 = 1 个负载单元）。通过降低输入阻抗的收发器或使用中继器，可以扩展到更多节点。

所有设备并联在同一条 A/B 总线上，通过地址区分，同一时刻只有一个设备在发送。

  • 传输距离与波特率
    RS485 标准规定在特定条件下最大传输距离约为 1200 米，最大波特率为 10 Mbps。但实际应用中，距离和速率是相互制约的：
波特率 建议最大距离
9600 bps 1200 m
115200 bps 约 100 m
1 Mbps 约 10 m

速率越高，信号边沿越陡，线缆上的反射和衰减越明显，有效距离就越短。工程上通常根据实际需求在距离和速率之间取舍。

  • 电气特性
    逻辑电平定义
    RS485 用 A、B 两线之间的电压差表示逻辑状态：
逻辑状态 电压条件 说明
逻辑 1（Mark） VAB ≥ +200 mV A 线比 B 线电压高
逻辑 0（Space） VAB ≤ -200 mV B 线比 A 线电压高
无效/不确定 -200 mV < VAB < +200 mV 接收器输出不确定

注意：不同厂商对 A/B 的命名可能不同。有些模块标注为 D+ / D-，有些标注为 A / B，接线时需以芯片手册为准，接反会导致数据取反（可用软件反相处理，但建议按标准接线）。

驱动器在发送时，A、B 之间的电压差典型值为 ±1.5 V ~ ±5 V。

共模电压范围
共模电压是指 A、B 两线相对于参考地（GND）的平均电压。RS485 接收器的共模输入范围为 -7 V ~ +12 V，意味着总线上的共模电压可以在这个范围内浮动，接收器仍能正确识别差分信号。

这一特性使 RS485适合长距离、不同设备地电位可能不一致的场合。但设备之间仍建议连接参考地，以保证共模电压不超出范围。

驱动能力与负载
一个标准 RS485 驱动器可以驱动 32 个标准接收器（输入阻抗 ≥ 12 kΩ）。每个挂在总线上的收发器都占用一个负载单元。

驱动器输出能力：

  • 差分输出电压（有负载时）：≥ ±1.5 V
  • 短路保护：通常具备
  • 发送使能：半双工模式下由 DE 引脚控制

总线通信模型
总线型拓扑
RS485 总线采用线性总线拓扑，所有设备直接并联在 A、B 两条线上：

  • 总线两端各接一个 120 Ω 终端电阻（跨接在 A、B 之间），用于吸收信号反射
  • 所有设备共享同一对 A/B 线
  • 各设备的地（GND）建议相连，作为共模参考

主从通信模式
RS485 总线通常采用主从（Master-Slave）通信模式：

  • 主机（Master）：主动发起通信，发送请求帧
  • 从机（Slave）：被动等待，收到属于自己的地址后才回复

同一时刻总线上只有一个设备在发送。从机之间不直接通信，必须通过主机中转。

收发方向控制
半双工 RS485 通信的核心问题：**什么时候发送，什么时候接收？**这由 DE 引脚控制。

发送模式
当 DE = 1（RE = 1，若短接）时，芯片进入发送模式：

  • 驱动器被使能，将 DI 上的 TTL 电平转换为 RS485 差分电平，驱动到 A/B 线
  • 接收器虽然也可能被使能，但此时总线由本设备驱动，RO 的输出没有实际意义
  • 总线上其他设备应处于接收模式，监听 A/B 线

接收模式
当 DE = 0（RE = 0，若短接）时，芯片进入接收模式：

  • 驱动器关闭，A/B 引脚呈高阻态，不影响总线上其他设备的发送
  • 接收器工作，将 A/B 线上的差分电压转换为 TTL 电平，从 RO 输出给 MCU

4.35 CAN总线

  • 1.什么是 CAN 总线
    CAN（Controller Area Network，控制器局域网）是一种用于设备之间互相通信的总线协议，最早由德国 Bosch 公司为汽车电子设计。

简单说：多台设备共用两根线，就能互相传数据。

在一辆车、一台工业设备或一套嵌入式系统里，发动机控制、刹车、仪表、传感器等模块往往都需要交换信息。如果每个模块之间都单独拉线，线束会又多又乱。CAN 总线把这些模块接到同一条总线上，大家按统一规则轮流发消息，从而减少布线、提高可靠性。

它解决了什么问题

  • 少接线：多节点共享一对差分信号线（CAN_H / CAN_L）
  • 多主通信：任何一个节点都可以主动发数据，不依赖单一主机轮询
  • 实时可靠：适合汽车、工业控制等对稳定性和实时性要求较高的场景

一句话记住
CAN 总线 = 多设备共用两根线、按协议可靠互传数据的现场总线。

  • 2.CAN 总线的特点
    CAN 总线能在汽车、工业控制里长期站稳，靠的不是“传得快”，而是稳、省线、好扩展。常见特点可以记这几条：

1.多主通信
总线上没有必须存在的“唯一主机”。
任何一个节点都可以主动发送数据，适合多个控制器同时工作的场景。

2.线少、易扩展
通信主要靠一对差分线：CAN_H / CAN_L。
新增节点通常只需挂到总线上，不必再给每两个设备单独拉线。

3.实时性较好
通过标识符（ID）做优先级仲裁：
ID 优先级高的报文可以先占用总线，适合刹车、电机控制这类对时效要求高的数据。

4.抗干扰能力强
采用差分信号传输，对共模噪声不敏感。
在电磁环境较差的汽车、工厂现场也能较稳定工作。

5.可靠性高
硬件和协议层都有错误检测与处理机制。
发现错误可重发；错误严重时节点还能自动脱离总线，避免拖垮整条网络。

6.通信距离与速率可折中
波特率越高，可靠通信距离通常越短；
距离拉长时，一般要降低波特率。实际项目里按需求和线长选型即可。

一句话总结
CAN 的核心特点是：多主、少线、可仲裁、抗干扰、带错误处理，特别适合多节点、强干扰、要求可靠的控制系统。

  • 3.经典 CAN 与 CAN FD
    随着车载和工业系统数据量变大会，经典 CAN 逐渐显得“带宽不够用”。于是出现了 CAN FD（CAN with Flexible Data-rate）：兼容经典 CAN 的思路，但能传更多数据、也能在数据段跑得更快。

先记住一句话

  • 经典 CAN：老标准，稳、通用、数据量小
  • CAN FD：升级版，单帧数据更多，数据段可提速

核心对比

项目 经典 CAN CAN FD
数据场长度 最多 8 字节 最多 64 字节
波特率 整帧通常同一速率 仲裁段保持兼容速率，数据段可切换到更高速率
带宽效率 较低 更高，适合大数据包
兼容性 生态成熟 可与经典 CAN 共存（需按网络设计）
典型场景 控制指令、状态信号 标定数据、传感器大数据、刷写/诊断相关传输

为什么需要 CAN FD
经典 CAN 一帧最多 8 字节。
如果要传一组传感器数据、标定参数或较大诊断信息，往往要拆成很多帧，总线占用高、效率低。

CAN FD 主要解决两件事：

  1. 一帧能装更多数据（最高 64 字节）
  2. 数据段可以提速，缩短发送时间，提高有效带宽

仲裁阶段仍用较低速率，保证多节点竞争时的兼容与稳定；真正传数据时再加速。

选型怎么理解

  • 节点少、数据短、控制类报文为主 → 经典 CAN 通常够用
  • 数据量大、希望少拆帧、提升吞吐 → 优先考虑 CAN FD
  • 老设备和新设备混用时 → 注意波特率、帧类型和控制器是否支持 FD

一句话总结
经典 CAN 侧重够用且成熟；CAN FD 侧重更大载荷、更高效率，是经典 CAN 在带宽需求上升后的自然升级。

显性电平与隐性电平
CAN 不用“高电平=1、低电平=0”这种单线直觉来理解仲裁，而用两个术语：

名称 英文 逻辑值 总线含义
显性 Dominant 0 有节点主动驱动差分电压
隐性 Recessive 1 节点释放总线，靠终端电阻偏置

核心规则：
只要有一个节点发显性（0），整条总线就是显性（0）。
只有大家都发隐性（1）时，总线才是隐性（1）。

这很像“线与”：显性能压住隐性。
正因为如此，多个节点可以边发送边监听，在仲裁阶段无损地比出优先级。

高速 CAN 的典型电压（示意，不同收发器略有差异）：

状态 CAN_H CAN_L 差分电压
隐性（逻辑 1） ≈ 2.5 V ≈ 2.5 V ≈ 0 V
显性（逻辑 0） ≈ 3.5 V ≈ 1.5 V ≈ 2 V

为什么逻辑 0 对应显性？
主要为了按位仲裁：

  • 节点发 1（隐性），却读到 0（显性）→ 说明别人在发 0 → 自己仲裁失败，立刻停发
  • ID 二进制中越靠前的 0 越多，越容易“压住”别人
  • 所以通常说：ID 越小，优先级越高

如果反过来定义，仲裁规则和优先级习惯都要重写。现有定义是为整套机制服务的。

总线上的四种帧
经典 CAN 常见四类帧：

帧类型 英文 核心用途 通常谁产生
数据帧 Data Frame 真正传输数据 应用通过控制器发送
远程帧 Remote Frame 请求对方发送某 ID 数据 应用主动请求
错误帧 Error Frame 通知当前传输出错 控制器自动
过载帧 Overload Frame 请求额外帧间隔 控制器自动

4.2 数据帧（Data Frame）
它是干什么的
数据帧是业务通信的主体：把 0～8 字节（经典 CAN）数据放到总线上广播。

    可以把它理解成“拉取请求”，而不是“推送数据”。

远程帧 = “请发 ID=xxx 的数据”；无数据场；靠 RTR=1 与数据帧区分。

  • 4.4 错误帧（Error Frame）
    它是干什么的

当某个节点检测到当前传输不符合协议时，会自动发出错误帧，告诉整条总线：
“这帧有问题，大家别当真，当前传输作废。”

错误帧通常由 CAN 控制器硬件自动产生，不是应用层手动组一帧“错误业务报文”。

基本组成
概念上由两部分构成：

部分 含义
错误标志 主动或被动的一串特殊电平，用于破坏/标识错误传输
错误定界符 随后的隐性位序列，标志错误标志结束

补充：如何处理错误帧？
CAN硬件自动处理：检测到错误 → 发送错误帧 → 终止当前报文；发送节点会自动重发报文。软件一般是读取错误状态寄存器、统计错误计数，做告警、限流或者节点离线保护，软件不需要手动组装错误帧。

主动错误与被动错误
节点会根据历史错误进入不同状态，发出的错误标志也不同：

节点状态 错误标志类型 大致行为
Error Active（主动错误） 主动错误标志：连续显性位 强行打断当前帧，全网容易察觉
Error Passive（被动错误） 被动错误标志：连续隐性位 仍表示出错，但对总线“破坏力”更弱

这与错误计数有关：错得多了，节点从主动错误变为被动错误；再严重可能 Bus-Off（见后文）。

常见触发原因
控制器会检测多种错误，例如：

错误类型 直观理解
位错误 Bit Error 自己发出的电平与总线实际电平不一致（仲裁场有特殊规则）
填充错误 Stuff Error 位填充规则被破坏
CRC 错误 校验失败
格式错误 Form Error 固定格式字段不合规
ACK 错误 发送方在 ACK 槽没看到显性应答

在调试时会看到什么

  • 分析仪上数据帧发到一半被打断，出现错误帧
  • 发送失败，控制器自动重发
  • 错误计数上升；极端情况进 Bus-Off，节点暂时发不出去

错误帧小结
错误帧 = 链路层的“作废通知”；自动产生；目的是否定错误传输并促使重发，不承载应用数据。

  • 4.5 过载帧（Overload Frame）
    它是干什么的
    过载帧用于在两帧之间插入额外延迟，表达：
    “先别连得太紧，给我一点处理时间 / 额外间隔。”

它表示的是时序/接收能力问题，不等于“数据内容校验失败”。

和错误帧的区别

对比 错误帧 过载帧
触发原因 检测到传输错误 接收繁忙，或需要额外帧间隔
语义 “这帧坏了” “帧间隙再拉长一点”
是否意味着数据错误 是 不一定
常见程度（现代 MCU） 调试中较常见 相对少见

形态上两者都有“标志 + 定界符”的味道，但语义完全不同，不能混为一谈。

什么时候可能出现

  • 接收缓冲来不及处理
  • 滤波过宽，短时间涌入大量帧
  • 中断服务程序过重，接收路径堵住
  • 某些协议状态要求插入过载条件

工程提示：若频繁看到过载帧，优先优化接收路径（滤波、队列、中断/DMA），而不是先怀疑 CRC。

过载帧小结
过载帧 = “请增加帧间隔”；自动产生；保接收方节奏，不承载业务数据。

  • 4.6 四种帧如何串在一条时间线上

四句口诀：
1.**数据帧：**我发数据
2.**远程帧：**请你发某 ID 的数据
3.**错误帧：**当前传输有错，作废重来
4.**过载帧：**别发太紧，先缓一缓

  • 4.7 非破坏性按位仲裁
    多主总线最怕同时发送互相踩踏。CAN 用 非破坏性按位仲裁 解决：
  1. 多个节点可能同时从 SOF 开始发送
  2. 在仲裁场，每个节点边发自己的 ID，边听总线真实电平
  3. 自己发隐性（1），却读到显性（0）→ 说明有更高优先级节点 → 立即退出发送，改为接收
  4. 高优先级节点不受影响，继续把整帧发完

因此：

  • 冲突不会毁掉正在获胜的那一帧（非破坏）
  • ID 越小，优先级越高
  • 输掉仲裁的节点稍后由控制器自动重试

  • 刹车、急停、保护类报文应分配较小 ID
  • 若重要报文经常发不出去，先查是否 ID 过大，或是否被大量高优先级洪水报文占满总线

补充：同一 ID 的数据帧与远程帧同时竞争时，数据帧（RTR=0）优先于远程帧（RTR=1），因为显性压过隐性。

  • 4.8 ACK 机制
    CAN 的 ACK 不是“指定地址设备回包”，而是：

    任何一个成功接收并校验通过该帧的节点，都可以在 ACK 槽写入显性位。

含义：

现象 含义
ACK 槽为显性 至少一个节点正确接收
发送方看不到显性 ACK ACK 错误，通常触发错误处理/重发

常见入门坑：

  • 总线上只有一个节点，又没有其他接收者 → 很容易 ACK 失败
  • 两节点波特率不一致 → 也可能表现为收不到/ACK 异常
  • 终端电阻、接线、收发器静默模式配置错误 → 同样影响 ACK

所以最小系统建议：至少两个节点、波特率一致、终端正确、双方都在线。

  • 4.9 位时序与波特率
    “波特率500kbit/s”背后，是把一个比特时间划分成若干时间量子（Time Quantum），再拆成位时序段：
段 作用
SyncSeg 同步段，边沿预期落在这里
PropSeg 补偿线路、收发器传播延迟
PhaseSeg1 / PhaseSeg2 吸收抖动，支持重同步加减
Sample Point 通常在位时间约 75%～87.5% 处采样判决

配置时真正重要的原则：

  1. 同一条总线所有节点波特率必须一致
  2. 不仅数字一致，采样点也尽量接近
  3. 速率越高，可靠通信距离通常越短
  4. CubeMX/手册中常见参数：预分频、BS1、BS2、SJW

经验量级：

波特率 常见场景直觉
125 kbit/s 更远、更稳，吞吐较低
250 / 500 kbit/s 工业与车载很常见
1 Mbit/s 距离通常较短，布局要求更高
  • 4.10 位填充（Bit Stuffing）
    为了让接收方持续看到足够边沿以便同步，经典 CAN 规定：

    若出现连续 5 个相同电平，则自动插入 1 个相反电平（填充位）。
    接收方按规则删除填充位，还原真实数据。

影响：

  • 不改变你应用层那 0～8 字节的含义
  • 会改变“线上实际比特数量”和波形密度
  • 填充规则被破坏时，会报 Stuff Error，并可能引发错误帧

看示波器时，不要惊讶“怎么多了一位”，很可能是填充位。

  • 4.11 错误处理与节点状态
    自动检错与重发
    CAN 的可靠性很大程度来自控制器自动能力：
  • 多种错误检测
  • 出错后发错误帧并否定当前传输
  • 发送失败可自动重发（在未 Bus-Off 等前提下）

应用层仍要做超时、状态机、告警，但链路层已经扛了很大部分。

错误计数与三种状态
控制器维护发送/接收错误计数。节点大致处于：

状态 含义
Error Active 正常；可发主动错误标志
Error Passive 错误较多；发送受限，少拖累总线
Bus-Off 错误严重；节点脱离总线，不能再正常参与通信，需恢复流程

Bus-Off 常见诱因：

  • 波特率配错
  • 接线/终端严重异常
  • 与异速率网络硬连
  • 持续短接、强干扰导致海量错误

恢复通常需要：等待/软件复位控制器，并确认物理层与波特率正确后，再重新参与总线。

  • 4.12 接收过滤（CAN很常用的配套功能）
    CAN本身是广播机制：消息一上总线，所有节点电气上全都能收到。

但CAN控制器自带硬件过滤（Filter + Mask）：

  • 只把我们需要的ID报文放进接收邮箱/FIFO
  • 其他报文直接硬件丢掉，不会打断CPU

它不属于CAN那四种帧类型，但实际开发基本都要配置。

踩坑点：

  • 过滤范围设太大 → 大量报文冲进CPU，收包风暴，CPU过载丢包
  • 过滤范围设太小 → 本该收到的业务报文被挡掉，收不到
  • 4.13 总结
    显性0压隐性1，靠ID做非破坏仲裁；
    数据帧传数据，远程帧请求数据，错误帧否定错误传输，过载帧拉长帧间隔；
    CRC/ACK/位填充/错误计数共同支撑可靠性；波特率与采样点必须全网一致。


5.STM32H747XIH6驱动RGB显示屏

5.1 LTDC控制器

  • 1.什么是 LTDC
    LTDC 是 MCU 内置的 LCD-TFT 显示控制器，用来把存储器里的帧缓冲（Framebuffer），按照显示时序扫描输出成 RGB 并行像素数据；同时输出 HSYNC/VSYNC/DE/像素时钟这些信号，驱动 RGB 接口的 LCD 屏幕。
    本质就是一个视频扫描器：按照固定行、场节拍，从内存持续读出像素，送到屏幕上显示。
  • 2.LTDC 需要哪些信号线
    LTDC硬件连线主要分3类：
  • **时序控制信号：**PCLK（像素时钟）、HSYNC（行同步）、VSYNC（场同步）、DE（数据使能，可选，很多屏幕需要）
  • **像素数据线（并行RGB）：**R[] / G[] / B[]，常用位宽 16/18/24bit（RGB565、RGB666、RGB888）
  • **屏幕附属控制（不属于LTDC本身外设）：**BL（背光PWM/开关）、RESET（复位）、I2C/SPI（屏幕、触摸配置）
    **连接要点：**像素线位数由屏幕和像素格式决定；PCLK、同步信号时序必须和屏幕手册对上。

3.LTDC 的接线怎么理解
把LCD面板看成一个严格按时钟采样的设备：

  • PCLK每跳变一次，面板采样一次RGB数据
  • DE=1时采样有效像素；DE=0是消隐区（前/后沿）
  • HSYNC：标记一行的边界（行同步脉冲）
  • VSYNC：标记一帧的边界（场同步脉冲）

简单理解：LTDC输出节拍+边界信号（PCLK/HSYNC/VSYNC/DE） + RGB像素数据，屏幕只在规定窗口内锁存像素。

4.LTDC 的显示过程是怎么进行的
一帧完整扫描流程：

  • 一帧起始：发出VSYNC脉冲 → 垂直后沿VBP → 开始有效显示行
  • 单行流程：发出HSYNC脉冲 → 水平后沿HBP → DE=1，输出像素 → 水平前沿HFP
  • 像素输出：有效区域内，LTDC从帧缓冲按地址递增读像素，做格式转换、图层混合，输出到RGB数据线

重点：帧缓冲内存要连续、带宽充足，不然画面撕裂、闪屏、花屏。

5.LTDC 最关键的是什么

  • 像素时钟和时序参数匹配屏幕：PCLK、HSYNC/VSYNC极性、脉宽、HFP/HBP/VFP/VBP，严格按屏幕手册配置
  • 帧缓冲地址、像素格式一致：RGB565/RGB888要和内存排布对应，行跨度stride/pitch不能错
  • 内存带宽、缓存一致性：帧缓冲一般放SDRAM，AXI/FMC带宽要够；DCache/MPU处理不好，会出现改了显存但屏幕不刷新、局部不更新
  • 图层混合配置：窗口大小、起始坐标、Alpha透明、色键ColorKey、背景色配置错误，容易黑屏、偏色、透明异常

6.LTDC 的几种显示/图层模式怎么理解

  • 单层（Layer）直出：最简单，一个帧缓冲对应整屏或者窗口区域。
  • 双层叠加（Overlay）：底层作为背景，上层放UI/OSD；使用逐像素Alpha或者固定Alpha做混合。
  • 颜色键（Color Keying）：指定某一种颜色为透明色，实现抠图效果。
  • 像素格式转换：LTDC支持多种输入格式（RGB565、ARGB8888等），硬件按照配置解析内存里的像素数据。
  • 双缓冲/交换缓冲：准备两块帧缓冲，一块用来显示，另一块用来绘图刷新；在帧边界切换，减少画面撕裂（一般搭配VSYNC场中断）。

5.2 DMA2D

1.什么是 DMA2D
DMA2D（Chrom-ART Accelerator）是STM32的二维图像硬件加速器，主要用来快速处理显示内存（FrameBuffer）。

它和普通DMA单纯搬运字节不一样，是面向像素的加速单元，支持矩形区域操作、像素格式转换、图层混合等图形任务。

在LCD/LVGL场景里，DMA2D常用功能：

  • 清屏（纯色填充）
  • 图片拷贝（BitBlt）
  • ARGB8888 ↔ RGB565 这类像素格式转换
  • 前景/背景Alpha混合

一句话总结：LTDC负责把图扫到屏幕上，DMA2D负责高效把图画到帧缓冲里面。

  • 2.DMA2D 的核心模式
    DMA2D 主要有4种工作模式：
  • R2M（Register to Memory）
    将寄存器里的颜色值填充到目标内存的矩形区域，一般用来清屏、画纯色块。
  • M2M（Memory to Memory）
    源图像区域直接拷贝到目标区域，不做像素格式转换。
  • M2M_PFC（Memory to Memory with Pixel Format Conversion）
    拷贝图像的同时自动做像素格式转换，比如 ARGB8888 转 RGB565。
  • M2M_BLEND（Memory to Memory with Blending）
    前景图层和背景图层按照Alpha规则混合，输出到目标缓冲区。
  • 3.DMA2D 需要关注的关键参数
    DMA2D 配置是否正确，80%取决于这些参数：
  • ColorMode（输出颜色格式）
    目标帧缓冲格式，如 RGB565、ARGB8888。
  • InputColorMode（输入格式）
    源图层格式，必须和图片实际格式一致。
  • Width / Height
    操作区域宽高，单位是“像素”。
  • OutputOffset（输出行偏移）
    每行写完后要跳过的像素数。
    计算公式：OutputOffset = FrameBufferWidth - RegionWidth
  • InputOffset（输入行偏移）
    每行读完后跳过的像素数（用于源图是大图子窗口时）。
  • Alpha / AlphaMode（混合模式）
    决定前景和背景的叠加方式（固定Alpha、像素Alpha、组合方式）。
  • 4.DMA2D 的处理流程怎么理解
    DMA2D 的典型执行流程：
    1.配置模式（R2M/M2M/M2M_PFC/M2M_BLEND）
    2.配置前景/背景/输出内存地址
    3.配置输入输出像素格式、宽高、offset、alpha
    4.启动 DMA2D
    5.等待传输完成中断或轮询完成标志

本质：按行读取源数据 → 可选格式转换/混合 → 按行写回目标缓冲区。

  • 5.DMA2D 与 LTDC 的配合关系
    二者在显示系统分工明确：
  • DMA2D：更新帧缓冲内容（画图）
  • LTDC：按显示时序扫描帧缓冲（显示）

典型链路：
应用层/LVGL 刷新区域 → DMA2D 写 SDRAM 中 FrameBuffer → LTDC 下一帧输出到 LCD。

如果只有 LTDC 没有 DMA2D，CPU 逐像素绘制负载很重；
如果只有 DMA2D 没有 LTDC，也无法按 RGB 时序驱动面板。

  • 6.DMA2D 最关键的工程点
  • 像素格式必须一致
    图像源格式、DMA2D输入格式、帧缓冲格式三者要匹配，否则偏色/花屏。
  • Offset 概念必须清楚
    不是字节偏移，而是每行额外跳过的像素数。
  • 带宽要够
    LTDC扫屏 + DMA2D刷新 + CPU访问会同时占用SDRAM/AXI带宽，容易抖动或撕裂。
  • Cache/MPU一致性（M7高频坑）
    开启DCache后，DMA2D与CPU对同一缓冲区操作前后需要 clean/invalidate，或者合理配置MPU属性。

6.触摸屏驱动开发

  • 1.什么是触摸屏
    触摸屏是在显示面板之上（或与之贴合）的一层输入设备：把手指、触控笔等操作变成坐标 (x, y)、按下/抬起、有时还有压力/多指等信息，交给 MCU 或 GUI 库处理。

可以把它理解成三层：

层次 作用
触摸传感器 物理上“感知”接触（电阻膜形变、电容电场变化等）
触摸控制器 IC 采样、滤波、算坐标、通过I2C/SPI等上报
MCU驱动 + GUI 读寄存器、校准、映射到LCD像素，送给LVGL/emWin等

显示（LTDC）负责“画出来”，触摸负责“点哪里”，两者独立但坐标必须一致。

  • 2.触摸屏有哪些类型
    电阻式触摸屏（Resistive）
  • 原理：两层导电膜（X膜、Y膜）之间用间隔点分开；按压时两层接触，通过对一角加压、对角测量电压，轮流得到X、Y。
  • 特点：成本低、不怕灰尘和水汽、可用指甲/手套；透光率差、单点、易划伤、寿命受按压次数影响。
  • 接口：常直接接MCU的ADC + GPIO（四线/五线），不一定有独立触摸IC。

表面电容式 / 投射电容式（Capacitive）

  • 表面电容：玻璃单层导电，手指吸走少量电荷，控制器测电容变化；多为单点，现较少用于新模组。
  • 投射电容（P-CAP）：现成RGB模组几乎全是这种。在玻璃下布透明电极矩阵，通过互电容/自电容变化定位，可多点触控。
  • 特点：透光好、手感顺滑、寿命长；怕强电磁干扰，湿手/厚手套需要算法；成本高于电阻屏。
  • 接口：几乎都有专用触摸IC（GT911、FT5x06、CST816等），MCU走I2C/SPI。

红外式（Infrared）

  • 原理：边框红外发射/接收管构成光栅，手指遮挡光线得到坐标。
  • 特点：透光极好（无膜）、寿命长；边框厚、怕灰尘遮挡光路、户外强光有影响。
  • 接口：多为UART/USB专用模块，嵌入式大板较少。

表面声波式（SAW）

  • 原理：玻璃角发射超声波，手指吸收能量，根据衰减定位。
  • 特点：清晰、耐用；怕油污和水，多用于工控、ATM等固定场景。

电磁/数字电磁（如部分手写屏）

  • 原理：电磁笔改变线圈感应；支持压感、悬停。
  • 特点：适合绘图板，一般手机/工业RGB模组不用。

电阻屏则是 MCU 主动：

  1. GPIO 把 Y+、Y- 设为输出，X 接 ADC，测得 X 电压 → 换算 X；

  • 5.触摸屏最关键的是什么
    1.坐标与LCD一致
    触摸分辨率、原点（左上/左下）、横竖屏是否与LTDC layer宽高、dir一致；不一致就要镜像/交换XY + 校准。

2.稳定读取触摸数据
I2C速率、上拉、线长、与RGB并行走线时的干扰；读寄存器长度、字节序要与手册一致。

3.中断与轮询策略
INT触发后再读，避免空轮询I2C；读完后按手册清标志，否则会一直中断。

4.复位与地址配置
上电顺序：供电 → RST时序 →（必要时）INT配合改I2C地址 → 读Chip ID确认。

5.与GUI的输入链路
最终要变成：pressed?、x、y；LVGL用 lv_indev_drv_t 的 read_cb，emWin 用 GUI_TOUCH_StoreState 等。

显示最关键的是帧缓冲和时序；触摸最关键的是“正确的 (x,y) + 事件时机”。

  • 7.触摸控制器（以电容 I2C IC 为例）
    本节把 GT911、FT5x06、CST816、ILI2511 等统称为一类：带寄存器映射的电容触摸 ASIC。

1.1 什么是触摸控制器
触摸控制器是专用芯片：内部完成高速扫描电极阵列、数字滤波、palm reject（防误触）、多点分配，对 MCU 只暴露：

  • 配置寄存器（分辨率、灵敏度、交换 XY、中断模式）
  • 状态/坐标寄存器（是否有触摸、点数、坐标）
  • 数字接口（I2C 为主，部分 SPI）

MCU 不需要懂电容算法，只需按手册初始化 + 周期性/中断式读坐标。

  • PB10 = I2C2_SCL (CTP_SCL)：触摸芯片的 I2C 时钟线。MCU 在这根线上输出时钟脉冲，用来同步每一位数据的传输。总线上通常需要上拉电阻（开漏方式）。
  • PB11 = I2C2_SDA (CTP_SDA)：触摸芯片的 I2C 数据线。MCU 通过它读写触摸芯片寄存器（比如读触摸点数量、X/Y 坐标、芯片 ID 等），同样是开漏 + 上拉。
  • PB5 = CTP_INT（触摸中断）：触摸芯片的 中断/触摸提示 引脚。屏幕被触摸或有新坐标数据时，触摸芯片会在这根线上拉低/产生下降沿通知 MCU：“有数据了，快来 I2C 读”。不用它也能轮询读，但用中断更省 CPU、延迟更低。
  • PB12 = CTP_RST（触摸复位）：触摸芯片的 硬件复位 引脚。MCU 上电后一般会把它拉低一段时间再拉高，让触摸芯片进入稳定状态；很多触摸 IC（如 GT911 类）还会在上电复位阶段配合 INT 脚电平来决定 I2C 地址或工作模式，所以这根脚很关键。
