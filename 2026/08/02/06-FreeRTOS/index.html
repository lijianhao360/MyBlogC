第1讲: RTOS入门知识

1.裸机与RTOS初识 (概念了解)

1.1 对于裸机系统而言：

这是嵌入式裸机开发经典的主死循环架构：单片机完成所有外设初始化之后，进入while(1)无限循环，串行轮流执行内部所有业务任务，没有操作系统进行任务抢占调度。

💡 补充理解：
在裸机开发中，业务逻辑必须排队执行。如果“打游戏()”这个函数执行时间过长（比如里面有大量的耗时计算或硬件死延时），那么“回复信息()”就必须一直等待，这会导致系统响应迟钝（表现为按键不灵、界面卡顿），也就是所谓的实时性差。

1.2 对于RTOS系统而言：

这是 FreeRTOS 这类实时操作系统的运行架构：

  1. 在 main 函数里调用 xTaskCreate 分别创建多个独立任务；
  2. 两个任务各自内部自带 while(1) 死循环，相互独立；
  3. RTOS内核（调度器）负责分时调度，两个任务宏观上并发运行，和裸机单循环串行执行有本质区别。

💡 补充理解：
虽然宏观上看起来多个任务是“同时”在运行，但微观上（对于单核 MCU 而言）仍然是交替执行的。RTOS 内核会根据任务的优先级和状态，以极快的速度在不同任务之间进行切换，从而产生并发运行的错觉。

2.裸机 while(1) 循环与 RTOS 深入对比

一、裸机前后台系统

  1. 基础定义:
    裸机又称为前后台系统。前台系统指的是“中断服务函数”（处理紧急/突发事件），后台系统指的是 while(1) 大循环（处理常规应用程序）。
  2. 裸机三大痛点:
  • 实时性差：（应用程序）轮流执行，后面的任务必须等前面的任务执行完。
  • delay 空等待：使用传统的 delay_ms() 时，CPU 会在原地做无用功死等，不执行其他代码，极大地浪费了 CPU 算力。
  • 结构臃肿：所有的状态机、标志位、功能逻辑都堆叠在一个无限循环中。随着项目复杂度上升，代码耦合度极高，维护和扩展面临巨大挑战（牵一发而动全身）。

二、RTOS 实时操作系统

RTOS 全称为：Real Time OS（实时操作系统），其最核心的特点就是强调：实时性（确定性）。

  1. 分而治之：将复杂的系统功能划分为多个高内聚、低耦合的独立任务。
  2. 阻塞延时（重中之重）：RTOS 提供自带的延时函数（如 vTaskDelay），它与裸机的死等不同。调用 RTOS 延时会触发任务调度，当前任务交出 CPU 使用权进入阻塞态，CPU 会立刻去执行其他准备就绪的任务，CPU 利用率被榨干。
  3. 抢占式调度：高优先级任务一旦就绪，会立刻打断正在运行的低优先级任务抢占 CPU。
  4. 任务堆栈与上下文切换：每个任务都有自己独立的 RAM 栈空间。当任务被抢占打断时，系统会自动把当前 CPU 的寄存器状态（上下文）保存到该任务的堆栈中；等该任务恢复运行时，再从堆栈恢复寄存器，保证任务“无缝衔接”。

⚠️ 注意事项：

  1. 中断拥有最高特权，硬件中断可以打断任意 RTOS 任务。
  2. FreeRTOS 支持任务设置同等优先级（此时同优先级任务会采用时间片轮转调度）。
  3. 丰富的通信组件：RTOS 完美替代了裸机中满天飞的“全局变量”，它提供了队列（Queue）、信号量（Semaphore）、互斥量（Mutex）等机制，用于任务间的数据传递和资源保护。

3. 扩展：什么时候该用 RTOS？

  • 适合用裸机：逻辑简单、外设较少、对实时性要求不高，或者极致要求低成本/低资源的简单控制类项目（如简单的温湿度采集、小风扇控制）。
  • 必须上RTOS：项目功能复杂（包含图形 UI 刷新、网络协议栈通信、电机控制等并发需求）、需要严格保证某些核心任务响应时间、以及需要团队协作开发（不同工程师负责写不同任务，最后拼接）的项目。

第2讲: FreeRTOS简介(了解)

1.基础概念介绍

FreeRTOS（Free Real Time Operating System）是一个轻量级的、免费的嵌入式实时操作系统，目前在微控制器（MCU）领域市场占有率极高（被亚马逊收购后，进一步推出了 Amazon FreeRTOS）。

它具有以下核心特点：

  • 1. 免费开源（商业无忧）：
    FreeRTOS 采用 MIT 开源许可协议（早期为修改版的 GPL）。这意味着你可以在商业产品中免费使用它，无需公开你的应用程序源代码，没有任何潜在商业版权风险，广大企业可以放心“白嫖”。

  • 2. 极度可裁剪（高度定制化）：
    FreeRTOS 的核心代码只有 9000+ 行，并且主要集中在 3 个核心 .c 文件中（tasks.c、list.c、queue.c）。

    💡 补充： 它是通过一个名为 FreeRTOSConfig.h 的头文件来实现裁剪的。你需要什么功能（比如是否需要互斥量、是否需要软件定时器），只需要在这个头文件里用宏定义（#define ... 1 或 0）像开关一样打开或关闭即可，极大地节省了单片机的 ROM 和 RAM。

  • 3. 简单且可移植性强：
    FreeRTOS 的源码分为硬件无关的通用代码和硬件相关的底层接口（Port 层）。无论是 STM32 (ARM Cortex-M)、ESP32 (Xtensa)、还是 RISC-V 架构，只需要替换对应的 port.c 和 portmacro.h 文件，就能轻松移植。

  • 4. 优先级与任务数量不限：

    • 优先级不限：任务优先级分配没有软件限制，并且允许多个任务共享同一个优先级。
    • 任务不限：可创建的任务数量在软件层面上没有限制。

      ⚠️ 注意： 虽然“软件”上没限制，但“硬件”上是有限制的！每创建一个任务都需要为其分配独立的栈空间（Stack）和任务控制块（TCB）。因此，任务能建多少，最终取决于你单片机的 RAM 容量。

  • 5. 支持三种任务调度方式：

    • 抢占式调度（Preemptive）：这是最常用的模式。高优先级的任务一旦就绪，会立刻“踢开”正在运行的低优先级任务，抢夺 CPU 的控制权，保证了极高的实时性。
    • 时间片轮转（Time Slicing）：针对同等优先级的任务。系统会把 CPU 的时间分成一个个小切片（比如 1ms），同优先级的任务大家排排坐，每人轮流执行 1ms，做到雨露均沾。
    • 协程式调度（Co-routine）：

      🚫 避坑指南： 协程是早期为了极其受限的单片机（RAM 极小）设计的，协程共享堆栈。但在如今 STM32 等 MCU 动辄几十上百 KB RAM 的时代，协程已经过时。FreeRTOS 官方也早已不推荐在新设计中使用协程，因此我们在实际开发和学习中可以直接跳过这部分，专注抢占式和时间片即可。

第3讲: FreeRTOS基础知识

1.任务调度简介(熟悉)

  • 1.FreeRTOS一共支持三种任务调度方式:
  • 调度器就是使用相关的调度算法来决定当前需要执行的哪个任务
    • 1.抢占式调度:主要针对优先级不同的任务，每个任务都有一个优先级，优先级高的任务可以抢占优先级低的任务。
    • 2.时间片调度:主要针对优先级相同的任务，当多个任务的优先级相同时，任务调度器会在每一次系统时钟节拍到的时候切换任务。
    • 3.协程式调度:当前执行的任务会一直运行，同时高优先级的任务不会抢占低优先级任务，FreeRTOS现在虽然还支持，但是官方表示不再更新协程式调度。
  • 2.抢占式调度过程

运行过程如下：
1.首先Task1在运行中，在这个过程中Task2就绪了，在抢占式调度器的作用下，Task2会抢占Task1的运行。
2.Task2运行过程中，Task3就绪了，在抢占式调度器的作用下Task3会抢占Task2的运行。
3.Task3运行过程中，Task3阻塞了(系统延时或者等待信号等)，此时就绪状态中，优先级最高的任务Task2执行。
4.Task3阻塞解除了(延时到了或者接收到信号量)，此时Task3恢复到就绪态中，抢占Task2的运行。

总结：
1.高优先级任务，优先执行。
2.高优先级任务不停止，低优先级任务无法执行。
3.被抢占的任务将会进去就绪态。

  • 3.时间片调度
  • 同等优先级任务轮流享有相同的CPU时间(可设置)，叫做时间片，在FreeRTOS中，一个时间片等于SysTick中断周期。

运行过程如下：
1.首先Task1运行完一个时间片后，切换至Task2运行。
2.Task2运行完一个时间片后，切换至Task3运行。
3.Task3运行过程中(还不到一个时间片)，Task3阻塞了(系统延时或者等待信号量等)，此时直接切换到下一个任务Task1执行。
4.Task1运行完一个时间片后，切换至Task2运行。

总结：
1.同等优先级任务，轮流执行。
2.一个时间片大小，取决滴答定时器中断周期。
3.没有用完的时间片不会再使用，任务Task3下次得到执行时间还是按照一个时间片的时钟节拍运行。

2.任务状态(熟悉)

  • 1.FreeRTOS的任务状态存在4种状态：
    1.运行态 ：正在执行的任务，该任务就处于运行状态(注意：在STM32中，同一时间仅一个任务处于运行态)。
    2.就绪态 ：如果该任务已经能够被执行，但当前还未被执行，那么该任务处于就绪态。
    3.阻塞态 ：如果一个任务因为延时或者等待外部事件发生，那么这个任务就处于阻塞态。
    4.挂起态 ：类似于暂停，调用函数vTaskSuspend()进入挂起态，需要调用解挂函数vTaskResume()才可以进入就绪态。

  • 2.四种任务状态之间的转换图

总结：
1.仅就绪态可以转换成运行态。
2.其他状态的任务想要运行，必须先转换成就绪态。

  • 3、任务状态列表
    任务的四种状态中，除了运行态，其他三种任务状态的任务都有其对应的任务状态列表。
    1.就绪列表 ： pxReadyTasksLists[x]，其中x代表任务优先级数值。

    • 32位的变量，当某个位置置一时，代表所对应的优先级就绪列表有任务存在。

    2.阻塞列表 ：pxDelayedTaskList
    3.挂起列表 ：xSuspendedTaskList

第7讲: 任务创建和任务删除实战编程(动态方法)

  • 1、实验目的：学会 xTaskCreate() 和 vTaskDelete() 的使用
  • 2、实验设计：将设计四个任务：start_task、task1、task2、task3
    四个任务的功能如下：
    • start_task：用来创建其他的三个任务
    • task1：实现LED0每500ms闪烁一次
    • task2：实现LED1每500ms闪烁一次

  • 关键知识点
    1.start_task 作用：专门用来创建其他业务任务，创建完调用vTaskDelete(NULL);自杀，释放自己资源，工程中常用这种模式。
    2.pdMS_TO_TICKS(ms)：毫秒转系统节拍计数，不建议直接写数字，可移植性更好。
    3.FreeRTOS 任务必须写死循环for(;;)，任务函数不能 return。
    4.vTaskDelete(句柄)：删除别的任务；vTaskDelete(NULL)删除当前正在运行的任务。
    5.动态创建任务，需要打开宏configSUPPORT_DYNAMIC_ALLOCATION = 1。
    运行现象：

    • 上电后 LED0、LED1 都 500ms 闪烁；
    • 按下 KEY0，task1 被删除，LED0 停止闪烁；LED1 继续闪烁。

第11讲: FreeRTOS中断管理简介

  • 1.什么是中断
  • 让CPU打断正常运行的程序，转而去处理紧急的事件(程序)，就叫中断。

（示意图：上课为正在执行的主程序，收到中断触发，跳转执行“上厕所”这个中断事件，处理完回到上课继续执行）

  • 中断执行机制，可简单概括为三步：
    1. 中断请求：外设产生中断请求(如：GPIO外部中断、定时器中断…)。
    2. 响应中断：CPU停止执行当前程序，转而执行中断处理程序(ISR)。
    3. 退出中断：执行完毕，返回被打断的程序处，继续往下执行。
  • 2.中断优先级分组设置（熟悉）
    ARM Cortex‑M 使用了 8 位宽的寄存器来配置中断的优先等级，这个寄存器就是中断优先级配置寄存器
    但STM32，只用了中断优先级配置寄存器的高4位 [7:4]，所以STM32提供了最大16级的中断优先等级

寄存器位说明：
Bit7Bit4：用于表达优先级
Bit3Bit0：没有实现，读回零

STM32 的中断优先级可以分为抢占优先级和子优先级：

  • 抢占优先级：抢占优先级高的中断可以打断正在执行但抢占优先级低的中断
  • 子优先级：当同时发生具有相同抢占优先级的两个中断时，子优先级数值小的优先执行

注意：中断优先级数值越小越优先

  • 3.中断优先级分组特点

在使用 FreeRTOS 时，STM32 的中断优先级配置与裸机开发有本质区别，必须严格遵守以下三大特点：

  • 1.严苛的 API 调用限制（重点配置 configMAX_SYSCALL_INTERRUPT_PRIORITY）**

    • 规则：只有优先级数值 大于或等于 configMAX_SYSCALL_INTERRUPT_PRIORITY（通常在 FreeRTOSConfig.h 中默认设为 5）的中断，才允许调用 FreeRTOS 的 API 函数。
    • 💡 补充避坑：
      • 不可控的高优先级：如果你的中断优先级设为 0~4（逻辑优先级极高），FreeRTOS 无法屏蔽它们。在这些中断里绝对不能调用任何 RTOS 的 API，否则系统必死机！这类中断通常留给需要极速响应的致命硬件事件（如电机急停保护）。
      • 专属后缀：即使中断优先级合法（比如设为了 6），在中断服务函数（ISR）中调用 API 时，必须且只能使用带有 FromISR 后缀的专属函数（例如用 xQueueSendFromISR 替代 xQueueSend），决不能混用。

  • 2.必须全部分配为抢占优先级（Group 4）**

    • 规则：强烈建议将所有优先级位指定为抢占优先级位（在初始化时调用 HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);）。
    • 💡 补充原因：
      • STM32 (Cortex-M3) 硬件提供 4 个比特位来配置优先级。NVIC_PRIORITYGROUP_4 意味着这 4 个 bit 全部用于抢占优先级（范围 0~15），响应优先级（子优先级）为 0。
      • FreeRTOS 的内核调度器“不认识”响应优先级。如果混用抢占和响应优先级，会导致 RTOS 的临界区代码无法正确屏蔽中断，进而引发不可预知的优先级反转或系统崩溃。

  • 3.优先级数值的“反直觉”设定**

    • 规则：硬件中断优先级数值越小越优先，软件任务优先级数值越大越优先。
    • 💡 补充总结：
      • 硬件中断 (NVIC)：由 ARM Cortex-M 内核决定。数值越小，特权越大。0 是最高硬件优先级。
      • 软件任务 (FreeRTOS)：由 RTOS 软件代码决定。数值越大，特权越大。configMAX_PRIORITIES - 1 是最高任务优先级，而数值 0 通常分配给系统底层的“空闲任务（Idle Task）”。

  • 任务优先级 (软件)：31，30，29 …… 1，0（31 级别最高，能抢占 0~30）

  • 3.💡 进阶补充：为什么要左移 (8 - configPRIO_BITS)？

这是初学者看 FreeRTOS 源码最容易懵逼的地方。这其实是 ARM 公司和 ST 公司设计差异导致的：

  1. ARM 的设计：ARM Cortex-M 内核在设计时，为每个中断的优先级分配了一个 8 位（1个字节）的寄存器，理论上可以有 256 个优先级。并且 ARM 规定，必须使用这 8 位的“高位”。
  2. STM32 的裁剪：ST 公司在设计 STM32F1 芯片时觉得用不到 256 个级别，于是只使用了高 4 位（即 configPRIO_BITS = 4），低 4 位硬件上固定为 0。
  3. 推演过程：

  • 我们想设置的最低优先级是 15，它的二进制是 0000 1111。

  • 如果直接把这个 0000 1111 写入 Cortex-M 的寄存器，由于只认高 4 位，高 4 位是 0000，系统会认为优先级是 0（最高优先级）！这就酿成大错了。

  • 所以，必须把 0000 1111 向左移动 (8 - 4) = 4 位，变成 1111 0000（即 0xF0）。此时高 4 位才是全 1（代表最低优先级 15）。

  • 这就是 << (8 - configPRIO_BITS) 这一句绝妙代码的由来。

  • 5.中断相关寄存器（核心必懂）

在 Cortex-M 内核中，有三个专门用于管理和屏蔽中断的寄存器：PRIMASK、FAULTMASK 和 BASEPRI。

寄存器名称 功能描述 裸机/RTOS 中的应用场景
PRIMASK 只有一个位。置 1 时，关掉所有可屏蔽异常，只剩下 NMI 和 HardFault 可以响应。默认值为 0（不屏蔽）。 裸机常用：裸机中经常用的全局关中断（__disable_irq()）和开中断（__enable_irq()），底层操作的就是这个寄存器。一刀切，极其霸道。
FAULTMASK 只有一个位。置 1 时，只有 NMI 才能响应，其他所有异常（包括 HardFault）全部被屏蔽。默认值为 0。 较少使用：通常只有在操作系统内核遇到极其严重的致命错误，准备彻底“摆烂”重启时才会动用。
BASEPRI 最多有 9 位。它定义了屏蔽优先级的阈值。当设为某值时，**优先级号 ≥ 该值（即优先级更低）**的中断全被屏蔽。设为 0 表示不屏蔽任何中断（默认值）。 FreeRTOS 专属：FreeRTOS 的中断管理和临界区保护，完全依赖对这个寄存器的操作。

💡 深度补充：FreeRTOS 为什么偏爱 BASEPRI？

  • 1.为什么不用 PRIMASK（全局关中断）？
    在裸机开发中，为了保护一段代码不被打断，我们习惯用 PRIMASK 全局关中断。但在 RTOS 中，这么做是极其危险的。
    如果 FreeRTOS 使用 PRIMASK，那么在系统进行任务切换或操作队列时，所有的硬件中断都会被挂起。如果你的系统里有一个极高频率、要求极高实时性的中断（比如步进电机发脉冲、伺服急停保护），一旦被延迟，可能导致机器损坏或事故。

  • 2.BASEPRI 的“精准打击”机制
    FreeRTOS 选择使用 BASEPRI，相当于提供了一个“白名单”机制。
    举个非常经典的例子（完美呼应上一讲的代码）：
    假设在 FreeRTOSConfig.h 中，受 RTOS 管理的最高中断优先级设为 5（configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5）。

  • 我们知道，STM32 只用了高 4 位，所以实际写入底层寄存器的值是：5 << 4 = 80，转换成十六进制就是 0x50。
  • 当系统调用 __set_BASEPRI(0x50) 后，优先级数值在 515 的中断全部被屏蔽（挂起），而优先级在 04 的中断依然可以毫无阻碍地抢占 CPU！
  • 3.揭秘 FreeRTOS 的临界区（Critical Section）本质
    我们在写 FreeRTOS 应用代码时，经常会用到进入和退出临界区的函数。揭开它们的面纱，底层其实极其简单：
  • 进入临界区 (taskENTER_CRITICAL())：
    本质上就是执行了 __set_BASEPRI(0x50)。关掉受 RTOS 管理的中断，防止任务在关键操作时被切换或打断。
  • 退出临界区 (taskEXIT_CRITICAL())：
    本质上就是执行了 __set_BASEPRI(0)。将阈值清零，重新开放所有中断的响应。

第12讲: FreeRTOS临界段代码保护及调度器挂起和恢复

  • 1.临界段代码保护简介（熟悉）

  • 1.什么是临界段？
    临界段代码也叫做临界区（Critical Section），是指那些必须完整运行、绝对不能被打断的代码段。在这些代码执行期间，系统必须保证它是“原子操作”（即要么不执行，要么一口气毫无阻挡地执行完）。

  • 2.什么会打断当前程序的运行？
    在 RTOS 环境中，正在执行的代码主要面临两级“威胁”：

  1. 任务调度：高优先级的任务突然就绪，触发了任务切换，抢占了当前正在执行的任务。
  2. 中断请求：硬件外设触发了中断（如定时器溢出、串口接收到数据），CPU 强制跳入中断服务函数（ISR）。

💡 核心本质串联：
回忆上一讲，FreeRTOS 的任务调度底层是依靠 PendSV 中断实现的。因此，不管是任务调度还是外设中断，打断程序的本质都是**“中断”**。
保护临界段的底层逻辑，就是利用 BASEPRI 寄存器去“屏蔽中断”。

  • 3.适用场合（什么时候需要用？）
  • 1. 时序严苛的外设通信（外设层面）
    • 补充细节：极其依赖微秒级时序的软件模拟通信协议。例如：软件模拟 IIC、单总线（1-Wire，如读取 DS18B20 温度传感器）。如果拉低引脚准备延时 5us 时被中断打断了 1ms，通信时序直接全毁。
  • 2. 保护全局共享资源（用户层面 - 最常见）
    • 补充细节：当多个任务（或任务与中断之间）同时读写同一个全局变量、数组或硬件寄存器时。如果任务 A 刚读了数据还没来得及修改，就被任务 B 抢占并修改了该数据，等 A 恢复后继续覆盖写入，就会导致数据错乱（经典的并发数据安全问题）。
  • 3. 系统自身需求（系统层面）
    • 补充细节：FreeRTOS 内核在更新任务状态列表、操作队列、信号量等内核核心数据结构时，必须自己进入临界区，防止系统崩溃。
  • 4.进阶补充：临界区的“黄金法则”

在使用临界区保护代码时，必须死死记住这两条工程铁律：

  1. 快进快出，越短越好：
    因为进入临界区就意味着关掉了大部分中断。如果临界区里的代码又臭又长（比如在里面加了个 10ms 的大循环），会导致外部的紧急硬件中断无法及时响应，直接破坏系统的实时性，甚至导致串口丢包、控制失灵。
  2. 严禁在临界区内调用阻塞 / 延时函数：
    绝对不能在临界区内调用 vTaskDelay()，或者去请求一个已经被占用的信号量！这会导致当前任务交出 CPU 且中断已被屏蔽，系统直接陷入死锁，只能按复位键。

  • 1.零中断延迟（与临界区的最大区别）

  • 临界区：防中断 + 防任务抢占。（极其霸道，会增加系统的中断延迟）
  • 挂起调度器：仅防任务抢占，不防中断。（温和，中断照样可以直接极速响应，实时性不受任何影响）

  • 2.挂起期间的中断请求去哪了？（Pending 机制）
  • 既然中断还可以响应，如果此时一个串口接收中断触发，并且在中断里唤醒了一个更高优先级的任务，会发生什么？
  • 答案：FreeRTOS 发现调度器被挂起了，不会立刻进行任务切换。而是将这个被唤醒的高优先级任务暂时放到一个名为 “挂起就绪列表 (xPendingReadyList)” 中。等到你调用 xTaskResumeAll() 恢复调度器时，系统会统一把它们移回正式的就绪列表，并执行一次上下文切换。
  • 3.支持嵌套调用
  • 和临界区一样，它也支持嵌套。系统内部维护了一个 uxSchedulerSuspended 变量，你调用了几次 vTaskSuspendAll()，就必须对应调用多少次 xTaskResumeAll()。

  • 错误示范：在里面调用了 vTaskDelay()，或者使用 xQueueReceive() 等待队列数据。
  • 致命后果：调度器已经被你手动挂起了（禁止切换），但你调用的 API 却又试图让当前任务进入阻塞态并呼叫调度器去执行别的任务。系统逻辑发生严重冲突，直接触发 configASSERT 断言报错，或者导致整个 RTOS 死锁崩溃！

第14讲: 列表和列表项

  • 1.列表和列表项的简介
    列表是FreeRTOS中的一个数据结构，概念上和链表有点类似，列表被用来跟踪FreeRTOS中的任务。
    列表项就是存放在列表中的项目。

列表相当于链表，列表项相当于节点，FreeRTOS中的列表是一个双向环形链表。

列表的特点：列表项间的地址非连续的，是人为的连接到一起的。列表项的数目是由后期添加的个数决定的，随时可以改变。
数组的特点：数组成员地址是连续的，数组在最初确定了成员数量后期无法改变。
在OS中任务的数量是不确定的，并且任务状态会发生改变的，所以非常适用列表(链表)这种数据结构。

  • 2.列表项结构示意

1、在该结构体中，包含了两个宏，这两个宏是确定的已知常量，FreeRTOS通过检查这两个常量的值，来判断列表的数据在程序运行过程中，是否遭到破坏，该功能一般用于调试，默认是不开启的
2、成员uxNumberOfItems，用于记录列表中列表项的个数（不包含xListEnd）
3、成员pxIndex用于指向列表中的某个列表项，一般用于遍历列表中的所有列表项
4、成员变量xListEnd是一个迷你列表项，排在最末尾

这是 FreeRTOS 最核心的底层数据结构之一。FreeRTOS 的调度器、阻塞延时、任务状态流转，全部都是建立在这个“双向链表”机制上的。

  • 1.xItemValue（列表项的值，非常关键）

  • 作用：多用于按升序对列表中的列表项进行排序。

  • 作用：分别指向下一个和上一个列表项。

  • 底层优势：双向链表的设计，使得 FreeRTOS 在知道某个节点指针的情况下，将其从链表中移除的时间复杂度为 $O(1)$，不需要从头遍历链表，满足了实时操作系统的“确定性”要求。

  • 作用：指向包含它的对象（通常是任务控制块 TCB_t）。

  • 精妙机制：通过这个指针，操作系统实现了“逆向顺藤摸瓜”。比如当延时时间到了，系统从阻塞列表中摘下这个列表项，通过 pvOwner 就能直接找到是哪个任务的延时到期了，进而把该任务的 TCB 移入就绪列表。

  • 4.pxContainer（所在列表的指针）

  • 作用：指向该列表项当前所在的根列表（List_t）。

  • 防错机制：比如在将任务移出某个列表前，内核可以通过 pxContainer 确认该任务当前到底有没有挂在这个列表上，防止悬空指针引发死机。

  • 2.为什么需要“迷你”列表项？
  • 极致的内存抠门（节约 RAM）
  • 迷你列表项只用作链表的“尾部标志（End Marker）”，它不代表任何实际的任务，所以它没有“主人”，也就不需要 pvOwner 成员。

在普通列表项中，xItemValue 存放的是延时时间或优先级，用于升序排列。但在迷你列表项中，xItemValue 的作用被赋予了极其巧妙的使命：充当链表的“物理边界”。

  • 最大值垫底：
    当一个根列表（List_t）被初始化时，系统会将内嵌的这个迷你列表项的 xItemValue 强制赋值为系统所能表示的最大值（例如 32 位系统下是 0xFFFFFFFF，或者 portMAX_DELAY）。
  • 免判空的链表插入算法：
    因为 FreeRTOS 的链表大多是按 xItemValue 升序排列的，给尾节点赋予最大值，就保证了新插入的普通列表项数值永远比尾节点小，永远会插在尾节点的前面。
    这样，内核在遍历链表寻找插入位置时，甚至不需要写 if(pxNext == NULL) 这种判断到达链表末尾的代码！只要碰到迷你列表项的值，循环自然就会终止。这种设计省去了分支预测的开销，极大地提升了 RTOS 的运行效率。

  • 5.压栈和出栈的地址增长方向
    堆栈的生长方向从最本质的理解是堆栈入栈方向是从高地址向地址还是低地址向高地址。

从高地址向低地址生长一般叫做向下生长，也叫作逆向生长。
从低地址向高地址生长一般叫做向上生长，也叫作正向生长。

一般来说堆栈是逆向生长的。
51单片机的堆栈生长方向为正向生长，因为执行PUSH指令时先将SP的值加1再将指定的8位数据单元的内容入栈。
80x86微机的堆栈生长方向为逆向生长，因为执行PUSH指令时先将SP的值减2再将指定的16位数据单元内容入栈。高字节放高地址，低字节放低地址（小端模式）。

STM32的堆栈生长方向是逆向生长。

注意：C语言中传递参数，一般是从右向左入栈的，所以最左边的参数是最先出栈的。

    用于初始化启动第一个任务前的环境，主要是重新设置MSP指针，并使能全局中断

1、什么是MSP指针？
程序在运行过程中需要一定的栈空间来保存局部变量等一些信息。当有信息保存到栈中时，MCU 会自动更新 SP 指针，ARM Cortex‑M 内核提供了两个栈空间：

主堆栈指针（MSP）：它由 OS 内核、异常服务例程以及所有需要特权访问的应用程序代码来使用。

进程堆栈指针（PSP）：用于常规的应用程序代码（不处于异常服务例程中时）。

在FreeRTOS中，中断使用MSP（主堆栈），中断以外使用PSP（进程堆栈）

  • 4.出栈/压栈汇编指令详解

出栈（恢复现场），方向：从下往上（低地址往高地址）：假设r0地址为0x04汇编指令示例：
ldmia r0!, {r4-r6} /* 任务栈r0地址由低到高，将r0存储地址里面的内容手动加载到 CPU寄存器r4、r5、r6 */
r0地址(0x04)内容加载到r4，此时地址r0 = r0+4 = 0x08
r0地址(0x08)内容加载到r5，此时地址r0 = r0+4 = 0x0C
r0地址(0x0C)内容加载到r6，此时地址r0 = r0+4 = 0x10

压栈（保存现场），方向：从上往下（高地址往低地址）：假设r0地址为0x10汇编指令示例：
stmdb r0!, {r4-r6} } /* r0的存储地址由高到低递减，将r4、r5、r6里的内容存储到r0的任务栈里面。 */
地址：r0 = r0-4 = 0x0C，将r6的内容（寄存器值）存放到r0所指向地址(0x0C)
地址：r0 = r0-4 = 0x08，将r5的内容（寄存器值）存放到r0所指向地址(0x08)
地址：r0 = r0-4 = 0x04，将r4的内容（寄存器值）存放到r0所指向地址(0x04)
