第一章: RTOS入门知识

1.裸机与RTOS

1.1裸机与RTOS初识 (概念了解)

  • **一.**对于裸机系统而言：

这是嵌入式裸机开发经典的主死循环架构：单片机完成所有外设初始化之后，进入while(1)无限循环，串行轮流执行内部所有业务任务，没有操作系统进行任务抢占调度。

💡 补充理解：
在裸机开发中，业务逻辑必须排队执行。如果“打游戏()”这个函数执行时间过长（比如里面有大量的耗时计算或硬件死延时），那么“回复信息()”就必须一直等待，这会导致系统响应迟钝（表现为按键不灵、界面卡顿），也就是所谓的实时性差。

  • 二.对于RTOS系统而言：

这是 FreeRTOS 这类实时操作系统的运行架构：
1. 在 main 函数里调用 xTaskCreate 分别创建多个独立任务；
2. 两个任务各自内部自带 while(1) 死循环，相互独立；
3. RTOS内核（调度器）负责分时调度，两个任务宏观上并发运行，和裸机单循环串行执行有本质区别。

💡 补充理解：
虽然宏观上看起来多个任务是“同时”在运行，但微观上（对于单核 MCU 而言）仍然是交替执行的。RTOS 内核会根据任务的优先级和状态，以极快的速度在不同任务之间进行切换，从而产生并发运行的错觉。

1.2.裸机 while(1) 循环与 RTOS 深入对比

  • 一、裸机前后台系统

    1. 基础定义:
      裸机又称为前后台系统。前台系统指的是“中断服务函数”（处理紧急/突发事件），后台系统指的是 while(1) 大循环（处理常规应用程序）。
    2. 裸机三大痛点:
    • 实时性差：（应用程序）轮流执行，后面的任务必须等前面的任务执行完。
    • delay 空等待：使用传统的 delay_ms() 时，CPU 会在原地做无用功死等，不执行其他代码，极大地浪费了 CPU 算力。
    • 结构臃肿：所有的状态机、标志位、功能逻辑都堆叠在一个无限循环中。随着项目复杂度上升，代码耦合度极高，维护和扩展面临巨大挑战（牵一发而动全身）。

  • 二、RTOS 实时操作系统
    RTOS 全称为：Real Time OS（实时操作系统），其最核心的特点就是强调：实时性（确定性）。

    1. 分而治之：将复杂的系统功能划分为多个高内聚、低耦合的独立任务。
    2. 阻塞延时（重中之重）：RTOS 提供自带的延时函数（如 vTaskDelay），它与裸机的死等不同。调用 RTOS 延时会触发任务调度，当前任务交出 CPU 使用权进入阻塞态，CPU 会立刻去执行其他准备就绪的任务，CPU 利用率被榨干。
    3. 抢占式调度：高优先级任务一旦就绪，会立刻打断正在运行的低优先级任务抢占 CPU。
    4. 任务堆栈与上下文切换：每个任务都有自己独立的 RAM 栈空间。当任务被抢占打断时，系统会自动把当前 CPU 的寄存器状态（上下文）保存到该任务的堆栈中；等该任务恢复运行时，再从堆栈恢复寄存器，保证任务“无缝衔接”。

⚠️ 注意事项：
> 1.中断拥有最高特权，硬件中断可以打断任意 RTOS 任务。
> 2.FreeRTOS 支持任务设置同等优先级（此时同优先级任务会采用时间片轮转调度）。
> 3.丰富的通信组件：RTOS 完美替代了裸机中满天飞的“全局变量”，它提供了队列（Queue）、信号量（Semaphore）、互斥量（Mutex）等机制，用于任务间的数据传递和资源保护。
>
>

  • 三、扩展：什么时候该用 RTOS？
    • 适合用裸机：逻辑简单、外设较少、对实时性要求不高，或者极致要求低成本/低资源的简单控制类项目（如简单的温湿度采集、小风扇控制）。
    • 必须上RTOS：项目功能复杂（包含图形 UI 刷新、网络协议栈通信、电机控制等并发需求）、需要严格保证某些核心任务响应时间、以及需要团队协作开发（不同工程师负责写不同任务，最后拼接）的项目。

2.2.堆和栈

  • 一、堆
    堆:一块内存空间，可以从中分配出一个小buffer，用完后再释放回去。
    通过malloc/my_malloc向系统申请内存，使用完必须调用free手动释放；不会随函数执行结束自动回收，如果不释放就会产生内存泄漏。堆空间一般很大，用于存放运行时才确定大小的数据。
  • 堆知识点笔记

    1. 栈 vs 堆

      • 栈：局部变量，函数执行完自动回收，系统自动管理；速度快，空间小。
      • 堆：malloc/my_malloc分配，必须手动free释放；不会随着函数结束自动回收，空间大。

    2. 这个my_malloc原理：线性分配（简单堆分配）

      • pos相当于堆的”分界指针”，pos之前代表已经分配，pos之后代表空闲堆空间。
      • 分配的时候直接把pos往后挪size，直接返回旧pos的地址。
      • 优点：分配速度极快，不需要复杂算法。
      • 致命缺点：不能真正释放内存，my_free是空函数，内存只会越用越少，内存泄漏，不能重复利用空闲内存。

    3. 真正标准库malloc/free：

      • 会把堆内存切割成很多空闲块、已占用块链表；
      • free会把内存归还到空闲链表，后续分配可以重复使用这块内存；
      • 需要处理内存碎片，算法复杂。

    4. 本代码的内存泄漏场景：

      main函数结束，局部指针变量buf（栈上）销毁，再也拿不到堆上那100字节地址，没有办法调用my_free回收，堆内存永久浪费。

    5. 补充：

    • buf指针本身：栈
    • *buf、buf[0]~buf[99]：堆内存。
  • 二、栈

    栈：也是一块内存空间，CPU的**SP寄存器（栈指针）**指向它，它可以用于函数调用、局部变量、多任务系统里保存现场。

  • 通俗解释

    1. SP寄存器（R13）：专门记录栈当前的位置，入栈SP减小，出栈SP增大。
    2. 主要用途
    • 存放局部变量：函数里面定义的变量，就放在栈上。
    • 函数调用：函数跳转时保存返回地址LR、寄存器，函数返回后自动恢复。
    • 多任务（FreeRTOS）：任务切换的时候，把寄存器现场保存到当前任务的栈，切回来再恢复现场。
    1. 自动管理，后进先出
      函数进入，栈空间自动分配；函数执行结束，栈自动回收，不需要程序员手动释放。

  • 特点

    • 自动分配自动释放，速度快
    • 栈的空间很小，如果局部变量太大、递归太深，会栈溢出，程序崩溃。

  • 栈 VS 堆（快速背诵）

    栈 堆
    SP寄存器管理，自动分配自动释放 malloc申请、free释放，程序员手动管理
    存放局部变量、函数现场 存放运行时才确定大小的数据
    空间小，速度快 空间大，容易内存泄漏、碎片
    函数结束内存立刻回收 函数结束不会自动回收

ARM里每个FreeRTOS任务，都拥有自己独立的栈，每个任务都有自己的SP。


  • 1.函数调用

  • 结合栈的核心笔记

    1. 栈帧
      每调用一个函数，CPU就会在栈上开辟一块内存，称为栈帧。
      栈帧里面保存：函数形参、局部变量、返回地址。
      函数执行return之后，这个函数对应的栈帧直接自动释放，这块栈内存就作废。

    2. 形参是副本
      b_func(volatile int a)，这里a是存放在b_func栈帧上的副本。
      在函数内部修改a，仅仅修改栈上副本，不会修改调用方的原始变量。

    3. 区分三个存储位置

      • 栈：局部变量、函数形参。函数结束自动释放。ch、i、buf指针本身都在栈。
      • 堆：my_malloc分配出来的内存，buf[0]~buf[99]。必须手动free，函数结束不会自动回收。
      • 全局段：全局变量g_cnt，不在栈也不在堆，程序整个运行周期都存在。

    4. volatile作用
      阻止编译器做优化，防止变量被编译器放到寄存器，强制每次读取都从内存读取，在嵌入式开发用于访问硬件寄存器。

    5. 函数调用栈流程示例（执行a_func(i)）
      1）main把实参i压入栈
      2）跳转到a_func，生成a_func栈帧
      3）a_func调用b_func，压入参数，生成b_func栈帧
      4）b_funcreturn，销毁b_func栈帧，返回值放寄存器
      5）回到a_func，继续调用c_func，生成c_func栈帧
      6）c_func return，销毁c_func栈帧
      7）a_func return，销毁a_func栈帧，回到main

    栈是后进先出，最后调用的函数最先销毁栈帧。

    1. 易错点
      char *buf = my_malloc(100);

      • buf：指针变量，在栈，函数结束自动消失
      • *buf：指向的内存，在堆，不会自动释放

      main结束，buf变量消失，再也找不到堆上100字节地址 → 内存泄漏。


  • 2.局部变量
    代码里所有局部变量，分别属于哪个函数的栈帧

    每一个函数被调用，就会生成属于这个函数独立的栈帧，栈帧就在栈内存上。函数 return，栈帧直接销毁，里面所有局部变量、形参全部失效。

1️.main函数的栈帧（main调用时创建，main结束全部销毁）

2️.a_func函数栈帧（调用a_func时创建，a_func return销毁）

3️.b_func栈帧（调用b_func创建，return立刻销毁）

4️.c_func栈帧（调用c_func创建，return立刻销毁）

  • 函数调用时栈帧的生命周期
    执行 main → a_func(i)
    1. main栈帧：存活，暂停执行
    2. 新建 a_func栈帧：存活
      • 执行b_func(a)：新建b_func栈帧
      • b_func执行return：b_func栈帧直接销毁，回到a_func
      • 执行c_func(g_cnt)：新建c_func栈帧
      • c_func执行return：c_func栈帧直接销毁，回到a_func
    3. a_func执行return：a_func栈帧销毁，回到main
    4. main继续运行，直到main return：main栈帧全部销毁

栈的特点：嵌套调用，栈帧层层新建；函数返回，栈帧立刻销毁，不需要程序员手动操作。

  • 容易踩坑区分
    1.形参也是局部变量，放在当前被调用函数的栈帧上，只是从外面拷贝过来。 2.char *buf
    - buf指针变量：main栈帧（栈）
    - buf[0]~buf[99]：my_malloc申请，堆内存，不在栈，不受栈帧销毁影响。
    3.全局变量g_cnt：既不在栈，也不在堆，存放在全局数据段，程序全程存活。
    哪个函数大括号内定义的局部变量/形参，就属于哪个函数的栈帧，函数结束栈帧销毁，变量全部消失。

  • 3.FreeRTOS如何使用栈

    裸机：全局只有1套栈（MSP），所有函数共用这一个栈。
    FreeRTOS：每个任务拥有自己独立私有任务栈，再加一套公共中断栈（MSP）。

1、任务栈（PSP进程栈指针）
调用xTaskCreate()创建任务时，从**FreeRTOS堆(heap)**分配一块RAM，就是这个任务的栈空间。
参数usStackDepth：栈大小，单位是字(4字节)，不是字节。

每个任务栈干两件事：

  1. 普通C函数调用
    任务里面运行函数，局部变量、形参、函数栈帧，全部存放在本任务自己的栈上。

    任务A调用func()，栈帧在A的栈；任务B调用func()，栈帧在B的栈，互不干扰。

  2. 保存任务上下文（现场）【任务切换核心】
    当任务被抢占、被切出去暂停时：

    • 把全部CPU寄存器（R0‑R12、LR、PC、xPSR）压入当前任务自己的栈保存起来。
    • TCB任务控制块保存当前栈顶pxTopOfStack。
      下次轮到该任务运行：
    • 把寄存器从该任务栈弹出，恢复CPU，任务从暂停处继续运行。

    任务挂起切换，不会销毁栈内容，现场保存在栈里面。只有vTaskDelete()删除任务，才释放这块栈内存还给堆。

2、中断栈 MSP（主栈指针，所有中断共用这一套）
只要进入中断服务函数ISR，硬件自动切换到MSP主栈，不使用当前任务的任务栈。
- 中断里面的局部变量、中断压栈的寄存器，全部在MSP。
- 不管当前正在运行哪个任务，中断永远跑在公共MSP栈。
> 好处：中断栈溢出，不会把任意一个任务的栈给冲坏。

  • 双栈指针区分（STM32 Cortex‑M）
    1.PSP：运行用户任务，指向当前任务的私有栈
    2.MSP：内核调度器、PendSV上下文切换、所有中断服务函数使用的公共栈

3、内存分布
1.每个任务栈：来自FreeRTOS的heap_4堆内存。
2.MSP中断栈：在链接脚本定义，不是来自FreeRTOS堆。
3.TCB任务控制块：任务控制块，记录每个任务的pxTopOfStack栈顶地址。

4、栈溢出（高频考点）
每个任务栈大小是固定的，如果：
- 函数嵌套很深
- 定义很大局部数组
栈往低地址持续增长，超出分配大小 → 栈溢出，系统死机、乱跳。

FreeRTOS提供两种检测：
- `configCHECK_FOR_STACK_OVERFLOW`：栈溢出钩子回调函数。
- `uxTaskGetStackHighWaterMark()`：查询任务历史剩余最小栈空间，调试用。

5、和裸机C栈对比

裸机C FreeRTOS

6、举一个简单例子
有任务1、任务2。
1. CPU运行任务1，PSP指向任务1的栈；任务1内部函数的局部变量、栈帧，都在任务1栈。
2. 调度器触发PendSV，要切到任务2：
- 把任务1全部寄存器压入任务1自己的栈，保存现场。TCB记下任务1栈顶。
- 取出任务2TCB保存的栈顶，PSP切换指向任务2的栈，弹出寄存器。
3. CPU运行任务2，PSP指向任务2的栈。
4. 此时来了外部中断：硬件立刻切MSP，中断的局部变量、寄存器压入公共MSP栈，和任务1、2栈无关。
5. 中断执行完毕，退出，切回PSP，回到任务2继续运行。

重点记忆：任务里面的函数栈帧属于这个任务自己的栈；中断永远跑MSP公共栈。

  • 容易混淆点
    1. 任务栈保存两部分内容：①普通C函数的栈帧（局部变量、形参）；②任务切换压进去的CPU寄存器上下文。
    2. vTaskDelete()：任务栈和TCB会归还FreeRTOS堆；如果不delete，任务栈永远占用RAM。
    3. usStackDepth单位是字，STM32一个字=4字节，设置128代表512字节栈空间。

3.FreeRTOS基础知识

3.1.FreeRTOS简介

FreeRTOS（Free Real Time Operating System）是一个轻量级的、免费的嵌入式实时操作系统，目前在微控制器（MCU）领域市场占有率极高（被亚马逊收购后，进一步推出了 Amazon FreeRTOS）。

它具有以下核心特点：

  • 1.免费开源（商业无忧）：
    FreeRTOS 采用 MIT 开源许可协议（早期为修改版的 GPL）。这意味着你可以在商业产品中免费使用它，无需公开你的应用程序源代码，没有任何潜在商业版权风险，广大企业可以放心“白嫖”。

  • 2.极度可裁剪（高度定制化）：
    FreeRTOS 的核心代码只有 9000+ 行，并且主要集中在 3 个核心 .c 文件中（tasks.c、list.c、queue.c）。

    💡 补充： 它是通过一个名为 FreeRTOSConfig.h 的头文件来实现裁剪的。你需要什么功能（比如是否需要互斥量、是否需要软件定时器），只需要在这个头文件里用宏定义（#define ... 1 或 0）像开关一样打开或关闭即可，极大地节省了单片机的 ROM(硬盘/Flash/程序存储器) 和 RAM(运行内存)。

  • 3.简单且可移植性强：
    FreeRTOS 的源码分为硬件无关的通用代码和硬件相关的底层接口（Port 层）。无论是 STM32 (ARM Cortex-M)、ESP32 (Xtensa)、还是 RISC-V 架构，只需要替换对应的 port.c 和 portmacro.h 文件，就能轻松移植。

  • 4.优先级与任务数量不限：

    • 优先级不限：任务优先级分配没有软件限制，并且允许多个任务共享同一个优先级。
    • 任务不限：可创建的任务数量在软件层面上没有限制。

      ⚠️ 注意： 虽然“软件”上没限制，但“硬件”上是有限制的！每创建一个任务都需要为其分配独立的栈空间（Stack）和任务控制块（TCB）。因此，任务能建多少，最终取决于你单片机的 RAM 容量。

  • 5.支持三种任务调度方式：

    • 抢占式调度（Preemptive）：这是最常用的模式。高优先级的任务一旦就绪，会立刻“踢开”正在运行的低优先级任务，抢夺 CPU 的控制权，保证了极高的实时性。
    • 时间片轮转（Time Slicing）：针对同等优先级的任务。系统会把 CPU 的时间分成一个个小切片（比如 1ms），同优先级的任务大家排排坐，每人轮流执行 1ms，做到雨露均沾。
    • 协程式调度（Co-routine）：

      🚫 避坑指南： 协程是早期为了极其受限的单片机（RAM 极小）设计的，协程共享堆栈。但在如今 STM32 等 MCU 动辄几十上百 KB RAM 的时代，协程已经过时。FreeRTOS 官方也早已不推荐在新设计中使用协程，因此我们在实际开发和学习中可以直接跳过这部分，专注抢占式和时间片即可。

  • **6.务通信和同步：**提供了队列、信号量等机制，支持任务之间的通信和同步，确保数据的安全传递。

  • **7.内存管理：**提供简单的内存管理机制，适用于嵌入式环境，有效利用有限的内存资源。

  • **8.定时器和中断处理：**支持定时器功能，能够处理中断，提供了可靠的实时性能。

  • 三、调度算法
  • 1.概念介绍
    正在运行的任务，被称为”正在使用处理器”，它处于运行状态。在单处理系统中，任何时间里只能有一个任务处于运行状态。

非运行状态的任务，它处于这3中状态之一：阻塞(Blocked)、暂停(Suspended)、就绪(Ready)。就绪态的任务，可以被调度器挑选出来切换为运行状态，调度器永远都是挑选最高优先级的就绪态任务并让它进入运行状态。

阻塞状态的任务，它在等待”事件”，当事件发生时任务就会进入就绪状态。
事件分为两类：时间相关的事件、同步事件。
- 所谓时间相关的事件，就是设置超时时间：在指定时间内阻塞，时间到了就进入就绪状态。使用时间相关的事件，可以实现周期性的功能、可以实现超时功能。
- 同步事件就是：某个任务在等待某些信息，别的任务或者中断服务程序会给它发送信息。怎么”发送信息”？方法很多，有：任务通知(task notification)、队列(queue)、事件组(event group)、信号量(semaphoe)、互斥量(mutex)等。这些方法用来发送同步信息，比如表示某个外设得到了数据。

  • 2.配置调度算法
    所谓调度算法，就是怎么确定哪个就绪态的任务可以切换为运行状态。

通过配置文件FreeRTOSConfig.h的两个配置项来配置调度算法：configUSE_PREEMPTION、configUSE_TIME_SLICING。

还有第三个配置项：configUSE_TICKLESS_IDLE，它是一个高级选项，用于关闭Tick中断来实现省电，后续单独讲解。现在我们假设configUSE_TICKLESS_IDLE被设为0，先不使用这个功能。 调度算法的行为主要体现在两方面：1.高优先级的任务先运行、2.同优先级的就绪态任务如何被选中。调度算法要确保同优先级的就绪态任务，能”轮流”运行，策略是”轮转调度”(Round Robin Scheduling)。轮转调度并不保证任务的运行时间是公平分配的，我们还可以细化时间的分配方法。 从3个角度统一理解多种调度算法：

  • 可否抢占？高优先级的任务能否优先执行(配置项: configUSE_PREEMPTION)

    • 可以：被称作”可抢占调度”(Pre-emptive)，高优先级的就绪任务马上执行，下面再细化。
    • 不可以：不能抢就只能协商了，被称作”合作调度模式”(Co-operative Scheduling)
      当前任务执行时，更高优先级的任务就绪了也不能马上运行，只能等待当前任务主动让出CPU资源。
      其他同优先级的任务也只能等待：更高优先级的任务都不能抢占，平级的更应该老实点

  • 可抢占的前提下，同优先级的任务是否轮流执行(配置项：configUSE_TIME_SLICING)

    • 轮流执行：被称为”时间片轮转”(Time Slicing)，同优先级的任务轮流执行，你执行一个时间片、我再执行一个时间片
    • 不轮流执行：英文为”without Time Slicing”，当前任务会一直执行，直到主动放弃、或者被高优先级任务抢占

  • 在”可抢占”+”时间片轮转”的前提下，进一步细化：空闲任务是否让步于用户任务(配置项：configIDLE_SHOULD_YIELD)

    • 1.空闲任务低人一等，每执行一次循环，就看看是否主动让位给用户任务

    • 2.空闲任务跟用户任务一样，大家轮流执行，没有谁更特殊 列表如下：

      configUSE_PREEMPTION 1 1 1 1 0
      configUSE_TIME_SLICING 1 1 0 0 x
      configIDLE_SHOULD_YIELD 1 0 1 0 x
      说明 常用 很少用 很少用 很少用 几乎不用

      注：

      • A：可抢占+时间片轮转+空闲任务让步
      • B：可抢占+时间片轮转+空闲任务不让步

  • 4.FreeRTOS一共支持三种任务调度方式:

  • 调度器就是使用相关的调度算法来决定当前需要执行的哪个任务

    • 1.抢占式调度:主要针对优先级不同的任务，每个任务都有一个优先级，优先级高的任务可以抢占优先级低的任务。
    • 2.时间片调度:主要针对优先级相同的任务，当多个任务的优先级相同时，任务调度器会在每一次系统时钟节拍到的时候切换任务。
    • 3.协程式调度:当前执行的任务会一直运行，同时高优先级的任务不会抢占低优先级任务，FreeRTOS现在虽然还支持，但是官方表示不再更新协程式调度。

  • 5.抢占式调度过程

运行过程如下：
1.首先Task1在运行中，在这个过程中Task2就绪了，在抢占式调度器的作用下，Task2会抢占Task1的运行。
2.Task2运行过程中，Task3就绪了，在抢占式调度器的作用下Task3会抢占Task2的运行。
3.Task3运行过程中，Task3阻塞了(系统延时或者等待信号等)，此时就绪状态中，优先级最高的任务Task2执行。
4.Task3阻塞解除了(延时到了或者接收到信号量)，此时Task3恢复到就绪态中，抢占Task2的运行。

总结：
1.高优先级任务，优先执行。
2.高优先级任务不停止，低优先级任务无法执行。
3.被抢占的任务将会进去就绪态。

  • 6.时间片调度
  • 同等优先级任务轮流享有相同的CPU时间(可设置)，叫做时间片，在FreeRTOS中，一个时间片等于SysTick中断周期。

运行过程如下：
1.首先Task1运行完一个时间片后，切换至Task2运行。
2.Task2运行完一个时间片后，切换至Task3运行。
3.Task3运行过程中(还不到一个时间片)，Task3阻塞了(系统延时或者等待信号量等)，此时直接切换到下一个任务Task1执行。
4.Task1运行完一个时间片后，切换至Task2运行。

总结：
1.同等优先级任务，轮流执行。
2.一个时间片大小，取决滴答定时器中断周期。
3.没有用完的时间片不会再使用，任务Task3下次得到执行时间还是按照一个时间片的时钟节拍运行。

4.2.任务状态(熟悉)

  • 1.FreeRTOS的任务状态存在4种状态：
  • 1.运行态 ：正在执行的任务，该任务就处于运行状态(注意：在STM32中，同一时间仅一个任务处于运行态)。

  • 2.就绪态(Ready) ：如果该任务已经能够被执行，但当前还未被执行，那么该任务处于就绪态。
    这个任务完全准备好了，随时可以运行：只是还轮不到它。这时，它就处于就绪态(Ready)。

  • 3.阻塞态(Blocked) ：如果一个任务因为延时或者等待外部事件发生，那么这个任务就处于阻塞态。
    在日常生活的例子中，母亲在电脑前跟同事沟通时，如果同事一直没回复，那么母亲的工作就被卡住了、被堵住了、处于阻塞状态(Blocked)。重点在于：母亲在等待。
    在实验中，如果把优先级高的任务中的vTaskDelay调用注释掉，那么低优先级任务1、任务2根本没有执行的机会，任务1、任务2被”饿死”了(starve)。
    在实际产品中，我们不会让一个任务一直运行，而是使用“事件驱动”的方法让它运行：

  • 任务要等待某个事件，事件发生后它才能运行

  • 在等待事件过程中，它不消耗CPU资源

  • 在等待事件的过程中，这个任务就处于阻塞状态(Blocked)

在阻塞状态的任务，它可以等待两种类型的事件：

  • 时间相关的事件

    • 可以等待一段时间：我等2分钟
    • 也可以一直等待，直到某个绝对时间：我等到下午3点

  • 同步事件：这事件由别的任务，或者是中断程序产生

    • 例子1：任务A等待任务B给它发送数据
    • 例子2：任务A等待用户按下按键
    • 同步事件的来源有很多(这些概念在后面会细讲)：
      • 队列(queue)
      • 二进制信号量(binary semaphores)
      • 计数信号量(counting semaphores)
      • 互斥量(mutexes)
      • 递归互斥量、递归锁(recursive mutexes)
      • 事件组(event groups)
      • 任务通知(task notifications)

在等待一个同步事件时，可以加上超时时间。比如等待队里数据，超时时间设为10ms：
- 10ms之内有数据到来：成功返回
- 10ms到了，还是没有数据：超时返回


  • 4.挂起态(Suspended) ：类似于暂停，调用函数vTaskSuspend()进入挂起态，需要调用解挂函数vTaskResume()才可以进入就绪态。

在日常生活的例子中，母亲正在电脑前跟同事沟通，母亲可以暂停：

  • 1.介绍
    空闲任务(Idle任务)的作用之一：释放被删除的任务的内存。

除了上述目的之外，为什么必须要有空闲任务？一个良好的程序，它的任务都是事件驱动的：平时大部分时间处于阻塞状态。有可能我们自己创建的所有任务都无法执行，但是调度器必须能找到一个可以运行的任务：所以，我们要提供空闲任务。在使用vTaskStartScheduler()函数来创建、启动调度器时，这个函数内部会创建空闲任务：
- 空闲任务优先级为0：它不能阻碍用户任务运行
- 空闲任务要么处于就绪态，要么处于运行态，永远不会阻塞

空闲任务的优先级为0，这意味着一旦某个用户的任务变为就绪态，那么空闲任务马上被切换出去，让这个用户任务运行。在这种情况下，我们说用户任务”抢占”(pre-empt)了空闲任务，这是由调度器实现的。

要注意的是：如果使用vTaskDelete()来删除任务，那么你就要确保空闲任务有机会执行，否则就无法释放被删除任务的内存。

我们可以添加一个空闲任务的钩子函数(Idle Task Hook Functions)，空闲任务的循环每执行一次，就会调用一次钩子函数。钩子函数的作用有这些：
- 执行一些低优先级的、后台的、需要连续执行的函数
- 测量系统的空闲时间：空闲任务能被执行就意味着所有的高优先级任务都停止了，所以测量空闲任务占据的时间，就可以算出处理器占用率。
- 让系统进入省电模式：空闲任务能被执行就意味着没有重要的事情要做，当然可以进入省电模式了。
- 空闲任务的钩子函数的限制：
- 不能导致空闲任务进入阻塞状态、暂停状态
- 如果你会使用vTaskDelete()来删除任务，那么钩子函数要非常高效地执行。如果空闲任务移植卡在钩子函数里的话，它就无法释放内存。

第11讲: FreeRTOS中断管理简介

  • 1.什么是中断
  • 让CPU打断正常运行的程序，转而去处理紧急的事件(程序)，就叫中断。

（示意图：上课为正在执行的主程序，收到中断触发，跳转执行“上厕所”这个中断事件，处理完回到上课继续执行）

  • 中断执行机制，可简单概括为三步：
    1. 中断请求：外设产生中断请求(如：GPIO外部中断、定时器中断…)。
    2. 响应中断：CPU停止执行当前程序，转而执行中断处理程序(ISR)。
    3. 退出中断：执行完毕，返回被打断的程序处，继续往下执行。
  • 2.中断优先级分组设置（熟悉）
    ARM Cortex‑M 使用了 8 位宽的寄存器来配置中断的优先等级，这个寄存器就是中断优先级配置寄存器
    但STM32，只用了中断优先级配置寄存器的高4位 [7:4]，所以STM32提供了最大16级的中断优先等级

寄存器位说明：
Bit7Bit4：用于表达优先级
Bit3Bit0：没有实现，读回零

STM32 的中断优先级可以分为抢占优先级和子优先级：

  • 抢占优先级：抢占优先级高的中断可以打断正在执行但抢占优先级低的中断
  • 子优先级：当同时发生具有相同抢占优先级的两个中断时，子优先级数值小的优先执行

注意：中断优先级数值越小越优先

  • 3.中断优先级分组特点

在使用 FreeRTOS 时，STM32 的中断优先级配置与裸机开发有本质区别，必须严格遵守以下三大特点：

  • 1.严苛的 API 调用限制（重点配置 configMAX_SYSCALL_INTERRUPT_PRIORITY）**

    • 规则：只有优先级数值 大于或等于 configMAX_SYSCALL_INTERRUPT_PRIORITY（通常在 FreeRTOSConfig.h 中默认设为 5）的中断，才允许调用 FreeRTOS 的 API 函数。
    • 💡 补充避坑：
      • 不可控的高优先级：如果你的中断优先级设为 0~4（逻辑优先级极高），FreeRTOS 无法屏蔽它们。在这些中断里绝对不能调用任何 RTOS 的 API，否则系统必死机！这类中断通常留给需要极速响应的致命硬件事件（如电机急停保护）。
      • 专属后缀：即使中断优先级合法（比如设为了 6），在中断服务函数（ISR）中调用 API 时，必须且只能使用带有 FromISR 后缀的专属函数（例如用 xQueueSendFromISR 替代 xQueueSend），决不能混用。

  • 2.必须全部分配为抢占优先级（Group 4）**

    • 规则：强烈建议将所有优先级位指定为抢占优先级位（在初始化时调用 HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);）。
    • 💡 补充原因：
      • STM32 (Cortex-M3) 硬件提供 4 个比特位来配置优先级。NVIC_PRIORITYGROUP_4 意味着这 4 个 bit 全部用于抢占优先级（范围 0~15），响应优先级（子优先级）为 0。
      • FreeRTOS 的内核调度器“不认识”响应优先级。如果混用抢占和响应优先级，会导致 RTOS 的临界区代码无法正确屏蔽中断，进而引发不可预知的优先级反转或系统崩溃。

  • 3.优先级数值的“反直觉”设定**

    • 规则：硬件中断优先级数值越小越优先，软件任务优先级数值越大越优先。
    • 💡 补充总结：
      • 硬件中断 (NVIC)：由 ARM Cortex-M 内核决定。数值越小，特权越大。0 是最高硬件优先级。
      • 软件任务 (FreeRTOS)：由 RTOS 软件代码决定。数值越大，特权越大。configMAX_PRIORITIES - 1 是最高任务优先级，而数值 0 通常分配给系统底层的“空闲任务（Idle Task）”。

  • 任务优先级 (软件)：31，30，29 …… 1，0（31 级别最高，能抢占 0~30）

  • 3.💡 进阶补充：为什么要左移 (8 - configPRIO_BITS)？

这是初学者看 FreeRTOS 源码最容易懵逼的地方。这其实是 ARM 公司和 ST 公司设计差异导致的：

  1. ARM 的设计：ARM Cortex-M 内核在设计时，为每个中断的优先级分配了一个 8 位（1个字节）的寄存器，理论上可以有 256 个优先级。并且 ARM 规定，必须使用这 8 位的“高位”。
  2. STM32 的裁剪：ST 公司在设计 STM32F1 芯片时觉得用不到 256 个级别，于是只使用了高 4 位（即 configPRIO_BITS = 4），低 4 位硬件上固定为 0。
  3. 推演过程：

  • 我们想设置的最低优先级是 15，它的二进制是 0000 1111。

  • 如果直接把这个 0000 1111 写入 Cortex-M 的寄存器，由于只认高 4 位，高 4 位是 0000，系统会认为优先级是 0（最高优先级）！这就酿成大错了。

  • 所以，必须把 0000 1111 向左移动 (8 - 4) = 4 位，变成 1111 0000（即 0xF0）。此时高 4 位才是全 1（代表最低优先级 15）。

  • 这就是 << (8 - configPRIO_BITS) 这一句绝妙代码的由来。

  • 5.中断相关寄存器（核心必懂）

在 Cortex-M 内核中，有三个专门用于管理和屏蔽中断的寄存器：PRIMASK、FAULTMASK 和 BASEPRI。

寄存器名称 功能描述 裸机/RTOS 中的应用场景
PRIMASK 只有一个位。置 1 时，关掉所有可屏蔽异常，只剩下 NMI 和 HardFault 可以响应。默认值为 0（不屏蔽）。 裸机常用：裸机中经常用的全局关中断（__disable_irq()）和开中断（__enable_irq()），底层操作的就是这个寄存器。一刀切，极其霸道。
FAULTMASK 只有一个位。置 1 时，只有 NMI 才能响应，其他所有异常（包括 HardFault）全部被屏蔽。默认值为 0。 较少使用：通常只有在操作系统内核遇到极其严重的致命错误，准备彻底“摆烂”重启时才会动用。
BASEPRI 最多有 9 位。它定义了屏蔽优先级的阈值。当设为某值时，**优先级号 ≥ 该值（即优先级更低）**的中断全被屏蔽。设为 0 表示不屏蔽任何中断（默认值）。 FreeRTOS 专属：FreeRTOS 的中断管理和临界区保护，完全依赖对这个寄存器的操作。

💡 深度补充：FreeRTOS 为什么偏爱 BASEPRI？

  • 1.为什么不用 PRIMASK（全局关中断）？
    在裸机开发中，为了保护一段代码不被打断，我们习惯用 PRIMASK 全局关中断。但在 RTOS 中，这么做是极其危险的。
    如果 FreeRTOS 使用 PRIMASK，那么在系统进行任务切换或操作队列时，所有的硬件中断都会被挂起。如果你的系统里有一个极高频率、要求极高实时性的中断（比如步进电机发脉冲、伺服急停保护），一旦被延迟，可能导致机器损坏或事故。

  • 2.BASEPRI 的“精准打击”机制
    FreeRTOS 选择使用 BASEPRI，相当于提供了一个“白名单”机制。
    举个非常经典的例子（完美呼应上一讲的代码）：
    假设在 FreeRTOSConfig.h 中，受 RTOS 管理的最高中断优先级设为 5（configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5）。

  • 我们知道，STM32 只用了高 4 位，所以实际写入底层寄存器的值是：5 << 4 = 80，转换成十六进制就是 0x50。
  • 当系统调用 __set_BASEPRI(0x50) 后，优先级数值在 515 的中断全部被屏蔽（挂起），而优先级在 04 的中断依然可以毫无阻碍地抢占 CPU！
  • 3.揭秘 FreeRTOS 的临界区（Critical Section）本质
    我们在写 FreeRTOS 应用代码时，经常会用到进入和退出临界区的函数。揭开它们的面纱，底层其实极其简单：
  • 进入临界区 (taskENTER_CRITICAL())：
    本质上就是执行了 __set_BASEPRI(0x50)。关掉受 RTOS 管理的中断，防止任务在关键操作时被切换或打断。
  • 退出临界区 (taskEXIT_CRITICAL())：
    本质上就是执行了 __set_BASEPRI(0)。将阈值清零，重新开放所有中断的响应。

第12讲: FreeRTOS临界段代码保护及调度器挂起和恢复

  • 1.临界段代码保护简介（熟悉）

  • 1.什么是临界段？
    临界段代码也叫做临界区（Critical Section），是指那些必须完整运行、绝对不能被打断的代码段。在这些代码执行期间，系统必须保证它是“原子操作”（即要么不执行，要么一口气毫无阻挡地执行完）。

  • 2.什么会打断当前程序的运行？
    在 RTOS 环境中，正在执行的代码主要面临两级“威胁”：

  1. 任务调度：高优先级的任务突然就绪，触发了任务切换，抢占了当前正在执行的任务。
  2. 中断请求：硬件外设触发了中断（如定时器溢出、串口接收到数据），CPU 强制跳入中断服务函数（ISR）。

💡 核心本质串联：
回忆上一讲，FreeRTOS 的任务调度底层是依靠 PendSV 中断实现的。因此，不管是任务调度还是外设中断，打断程序的本质都是**“中断”**。
保护临界段的底层逻辑，就是利用 BASEPRI 寄存器去“屏蔽中断”。

  • 3.适用场合（什么时候需要用？）
  • 1. 时序严苛的外设通信（外设层面）
    • 补充细节：极其依赖微秒级时序的软件模拟通信协议。例如：软件模拟 IIC、单总线（1-Wire，如读取 DS18B20 温度传感器）。如果拉低引脚准备延时 5us 时被中断打断了 1ms，通信时序直接全毁。
  • 2. 保护全局共享资源（用户层面 - 最常见）
    • 补充细节：当多个任务（或任务与中断之间）同时读写同一个全局变量、数组或硬件寄存器时。如果任务 A 刚读了数据还没来得及修改，就被任务 B 抢占并修改了该数据，等 A 恢复后继续覆盖写入，就会导致数据错乱（经典的并发数据安全问题）。
  • 3. 系统自身需求（系统层面）
    • 补充细节：FreeRTOS 内核在更新任务状态列表、操作队列、信号量等内核核心数据结构时，必须自己进入临界区，防止系统崩溃。
  • 4.进阶补充：临界区的“黄金法则”

在使用临界区保护代码时，必须死死记住这两条工程铁律：

  1. 快进快出，越短越好：
    因为进入临界区就意味着关掉了大部分中断。如果临界区里的代码又臭又长（比如在里面加了个 10ms 的大循环），会导致外部的紧急硬件中断无法及时响应，直接破坏系统的实时性，甚至导致串口丢包、控制失灵。
  2. 严禁在临界区内调用阻塞 / 延时函数：
    绝对不能在临界区内调用 vTaskDelay()，或者去请求一个已经被占用的信号量！这会导致当前任务交出 CPU 且中断已被屏蔽，系统直接陷入死锁，只能按复位键。

  • 1. 成对使用（铁律）

  • ENTER 和 EXIT 必须严格成对出现！如果在临界区内写了 return 或 break 导致跳过了 EXIT，系统中断将永远关闭，整个芯片直接变成“植物人”死机。

  • 2. 支持嵌套（极其巧妙的设计）

  • 任务级嵌套原理：FreeRTOS 内核维护了一个全局变量 uxCriticalNesting（临界区嵌套计数器）。每次 ENTER 它就 +1，每次 EXIT 它就 -1。只有当它减到 0 时，系统才会真正去打开中断。 这样设计完美解决了函数互相调用时，临界区提前结束导致中断误开的问题。

  • 中断级嵌套原理：中断里没有使用全局计数器，而是通过你定义的那个局部变量 save_status 实现的。局部变量保存在栈里，天然支持中断嵌套调用。

  • 避坑指南：在临界区内，千万别写 printf，别用死循环延时，别去读写 IIC/SPI 这种慢速外设（除非是死等几个微秒的纯时序控制）。否则，系统的串口可能会丢数据，电机控制可能会失步，直接毁掉 RTOS “实时响应”的招牌。

  • 1.零中断延迟（与临界区的最大区别）

  • 临界区：防中断 + 防任务抢占。（极其霸道，会增加系统的中断延迟）
  • 挂起调度器：仅防任务抢占，不防中断。（温和，中断照样可以直接极速响应，实时性不受任何影响）
  • 适用场景：临界区资源争夺仅仅发生在任务与任务之间，且该段代码执行时间较长（例如屏幕刷屏、长字符串处理）。既不用去阻塞中断，又可以做到数据的安全。
  • 2.挂起期间的中断请求去哪了？（Pending 机制）
  • 既然中断还可以响应，如果此时一个串口接收中断触发，并且在中断里唤醒了一个更高优先级的任务，会发生什么？
  • 答案：FreeRTOS 发现调度器被挂起了，不会立刻进行任务切换。而是将这个被唤醒的高优先级任务暂时放到一个名为 “挂起就绪列表 (xPendingReadyList)” 中。等到你调用 xTaskResumeAll() 恢复调度器时，系统会统一把它们移回正式的就绪列表，并执行一次上下文切换。
  • 3.支持嵌套调用
  • 和临界区一样，它也支持嵌套。系统内部维护了一个 uxSchedulerSuspended 变量，你调用了几次 vTaskSuspendAll()，就必须对应调用多少次 xTaskResumeAll()。

严禁在调度器挂起期间，调用任何可能引发任务阻塞或上下文切换的 FreeRTOS API！

  • 错误示范：在里面调用了 vTaskDelay()，或者使用 xQueueReceive() 等待队列数据。
  • 致命后果：调度器已经被你手动挂起了（禁止切换），但你调用的 API 却又试图让当前任务进入阻塞态并呼叫调度器去执行别的任务。系统逻辑发生严重冲突，直接触发 configASSERT 断言报错，或者导致整个 RTOS 死锁崩溃！

第14讲: 列表和列表项

  • 1.列表和列表项的简介
    列表是FreeRTOS中的一个数据结构，概念上和链表有点类似，列表被用来跟踪FreeRTOS中的任务。
    列表项就是存放在列表中的项目。

列表相当于链表，列表项相当于节点，FreeRTOS中的列表是一个双向环形链表。

列表的特点：列表项间的地址非连续的，是人为的连接到一起的。列表项的数目是由后期添加的个数决定的，随时可以改变。
数组的特点：数组成员地址是连续的，数组在最初确定了成员数量后期无法改变。
在OS中任务的数量是不确定的，并且任务状态会发生改变的，所以非常适用列表(链表)这种数据结构。

  • 2.列表项结构示意

1、在该结构体中，包含了两个宏，这两个宏是确定的已知常量，FreeRTOS通过检查这两个常量的值，来判断列表的数据在程序运行过程中，是否遭到破坏，该功能一般用于调试，默认是不开启的
2、成员uxNumberOfItems，用于记录列表中列表项的个数（不包含xListEnd）
3、成员pxIndex用于指向列表中的某个列表项，一般用于遍历列表中的所有列表项
4、成员变量xListEnd是一个迷你列表项，排在最末尾

这是 FreeRTOS 最核心的底层数据结构之一。FreeRTOS 的调度器、阻塞延时、任务状态流转，全部都是建立在这个“双向链表”机制上的。

  • 1.xItemValue（列表项的值，非常关键）

  • 作用：多用于按升序对列表中的列表项进行排序。

  • 实战场景：

  • 作用：分别指向下一个和上一个列表项。

  • 底层优势：双向链表的设计，使得 FreeRTOS 在知道某个节点指针的情况下，将其从链表中移除的时间复杂度为 $O(1)$，不需要从头遍历链表，满足了实时操作系统的“确定性”要求。

  • 3.pvOwner（列表项的拥有者）

  • 作用：指向包含它的对象（通常是任务控制块 TCB_t）。

  • 精妙机制：通过这个指针，操作系统实现了“逆向顺藤摸瓜”。比如当延时时间到了，系统从阻塞列表中摘下这个列表项，通过 pvOwner 就能直接找到是哪个任务的延时到期了，进而把该任务的 TCB 移入就绪列表。

  • 4.pxContainer（所在列表的指针）

  • 作用：指向该列表项当前所在的根列表（List_t）。

  • 防错机制：比如在将任务移出某个列表前，内核可以通过 pxContainer 确认该任务当前到底有没有挂在这个列表上，防止悬空指针引发死机。

  • 默认状态：为了节省 RAM，默认情况下 configUSE_LIST_DATA_INTEGRITY_CHECK_BYTES 是设为 0 的，这两个宏为空，不占空间。

  • 2.为什么需要“迷你”列表项？
  • 极致的内存抠门（节约 RAM）
  • 迷你列表项只用作链表的“尾部标志（End Marker）”，它不代表任何实际的任务，所以它没有“主人”，也就不需要 pvOwner 成员。
  • 它永远固定在自己所属的根列表中，不会被移动到别的列表去，所以它不需要知道自己挂在哪，也就不需要 pxContainer 成员。
  • 在 RAM 极其宝贵的单片机（尤其早期的 8 位/16 位 MCU）中，每个根列表都能省下 2 个指针变量的空间（在 32 位系统中就是省下 8 个字节）。系统中有几十个列表，积少成多，这是嵌入式工程师对资源的极致压榨。
  • 3.进阶补充：xItemValue 的“挡箭牌”机制（源码精髓）

在普通列表项中，xItemValue 存放的是延时时间或优先级，用于升序排列。但在迷你列表项中，xItemValue 的作用被赋予了极其巧妙的使命：充当链表的“物理边界”。

  • 最大值垫底：
    当一个根列表（List_t）被初始化时，系统会将内嵌的这个迷你列表项的 xItemValue 强制赋值为系统所能表示的最大值（例如 32 位系统下是 0xFFFFFFFF，或者 portMAX_DELAY）。
  • 免判空的链表插入算法：
    因为 FreeRTOS 的链表大多是按 xItemValue 升序排列的，给尾节点赋予最大值，就保证了新插入的普通列表项数值永远比尾节点小，永远会插在尾节点的前面。
    这样，内核在遍历链表寻找插入位置时，甚至不需要写 if(pxNext == NULL) 这种判断到达链表末尾的代码！只要碰到迷你列表项的值，循环自然就会终止。这种设计省去了分支预测的开销，极大地提升了 RTOS 的运行效率。

从高地址向低地址生长一般叫做向下生长，也叫作逆向生长。
从低地址向高地址生长一般叫做向上生长，也叫作正向生长。

一般来说堆栈是逆向生长的。
51单片机的堆栈生长方向为正向生长，因为执行PUSH指令时先将SP的值加1再将指定的8位数据单元的内容入栈。
80x86微机的堆栈生长方向为逆向生长，因为执行PUSH指令时先将SP的值减2再将指定的16位数据单元内容入栈。高字节放高地址，低字节放低地址（小端模式）。

STM32的堆栈生长方向是逆向生长。

注意：C语言中传递参数，一般是从右向左入栈的，所以最左边的参数是最先出栈的。

r0地址(0x0C)内容加载到r6，此时地址r0 = r0+4 = 0x10

压栈（保存现场），方向：从上往下（高地址往低地址）：假设r0地址为0x10汇编指令示例：

地址：r0 = r0-4 = 0x0C，将r6的内容（寄存器值）存放到r0所指向地址(0x0C)
地址：r0 = r0-4 = 0x08，将r5的内容（寄存器值）存放到r0所指向地址(0x08)
地址：r0 = r0-4 = 0x04，将r4的内容（寄存器值）存放到r0所指向地址(0x04)

  2. 不等于xListEnd，if不执行

4、Task1运行完一个时间片后，切换至Task2运行

同步互斥与通信

本章是概述性的内容。可以把多任务系统当做一个团队，里面的每一个任务就相当于团队里的一个人。团队成员之间要协调工作进度(同步)、争用会议室(互斥)、沟通(通信)。多任务系统中所涉及的概念，都可以在现实生活中找到例子。

各类RTOS都会涉及这些概念：任务通知(task notification)、队列(queue)、事件组(event group)、信号量(semaphoe)、互斥量(mutex)等。我们先站在更高角度来讲解这些概念。

1.同步与互斥概念

  • 一句话理解同步与互斥：我等你用完厕所，我再用厕所。
    什么叫同步？就是：哎哎哎，我正在用厕所，你等会。 什么叫互斥？就是：哎哎哎，我正在用厕所，你不能进来。
    同步与互斥经常放在一起讲，是因为它们之的关系很大，“互斥”操作可以使用“同步”来实现。我“等”你用完厕所，我再用厕所。这不就是用“同步”来实现“互斥”吗？

  • 假设有A、B两人早起抢厕所，A先行一步占用了；B慢了一步，于是就眯一会；当A用完后叫醒B，B也就愉快地上厕所了。
    在这个过程中，A、B是互斥地访问“厕所”，“厕所”被称之为临界资源。我们使用了“休眠-唤醒”的同步机制实现了“临界资源”的“互斥访问”。

同一时间只能有一个人使用的资源，被称为临界资源。比如任务A、B都要使用串口来打印，串口就是临界资源。如果A、B同时使用串口，那么打印出来的信息就是A、B混杂，无法分辨。所以使用串口时，应该是这样：A用完，B再用；B用完，A再用。

再举一个例子。在团队活动里，同事A先写完报表，经理B才能拿去向领导汇报。经理B必须等同事A完成报表，AB之间有依赖，B必须放慢脚步，被称为同步。在团队活动中，同事A已经使用会议室了，经理B也想使用，即使经理B是领导，他也得等着，这就叫互斥。经理B跟同事A说：你用完会议室就提醒我。这就是使用”同步”来实现”互斥”。

3.FreeRTOS的解决方案

FreeRTOS 提供专门内核对象来解决同步互斥，底层封装了临界保护、任务阻塞、优先级处理，不要自己裸写标志变量 + 关中断做互斥：
1.互斥量 mutex：用于资源互斥访问（LCD、串口），自带优先级继承，缓解优先级翻转；谁获取谁释放。
2.二进制信号量 binary semaphore：多用于事件同步，任务 / 中断释放，任务获取；不支持优先级继承，谁都可以释放。
3.计数信号量 counting semaphore：资源计数、事件计数。
4.任务通知 task notification：轻量同步，速度快，占用 RAM 小。
5.队列 queue：数据传递，同时完成同步。
6.事件组：
一个事件用一bit表示，1表示事件发生了，0表示事件没发生
可以用来表示事件、事件的组合发生了，不能传递数据
有广播效果：事件或事件的组合发生了，等待它的多个任务都会被唤醒

核心思想：资源得不到时，任务进入Blocked 阻塞状态，让出 CPU，而不是轮询；资源可用时内核自动唤醒等待任务。

  • 1.队列简介
    1，队列简介（了解）
    队列是任务到任务、任务到中断、中断到任务数据交流的一种机制（消息传递）

类似全局变量，假设有一个全局变量 a=0，现有两个任务都在写这个变量a
任务1（）{a++;}
①读数据：r0 <= a
②修改数据：r0 = r0 + 1
③写数据：r0 => a

任务2（）{a++;}
①读数据：r0 <= a
②修改数据：r0 = r0 + 1
③写数据：r0 => a

全局变量的弊端：数据无保护，导致数据不安全，当多个任务同时对该变量操作时，数据易出错

在队列中可以存储数量有限、大小固定的数据。队列中的每一个数据叫做“队列项目”，队列能够存储“队列项目”的最大数量称为队列的长度

1、队列长度为：5个
2、队列项目大小为：10字节
在创建队列时，就要指定队列长度以及队列项目的大小！

  • 2.FreeRTOS队列的特点
    FreeRTOS队列特点：
    1、数据入队出队方式
    队列通常采用“先进先出”(FIFO)的数据存储缓冲机制，即先入队的数据会先从队列中被读取，FreeRTOS中也可以配置为“后进先出” LIFO方式；

2、数据传递方式
FreeRTOS中队列采用实际值传递，即将数据拷贝到队列中进行传递，FreeRTOS采用拷贝数据传递，也可以传递指针，所以在传递较大的数据的时候采用指针传递

3、多任务访问
队列不属于某个任务，任何任务和中断都可以向队列发送/读取消息

4、出队、入队阻塞
当任务向一个队列发送消息时，可以指定一个阻塞时间，假设此时当队列已满无法入队

① 若阻塞时间为0 ：直接返回不会等待；
② 若阻塞时间为0~port_MAX_DELAY ：等待设定的阻塞时间，若在该时间内还无法入队，超时后直接返回不再等待；
③ 若阻塞时间为port_MAX_DELAY ：死等，一直等到可以入队为止。出队阻塞与入队阻塞类似；

  • 队列和数组区别
    1.数组：普通内存缓冲区，没有阻塞机制，需要自己处理读写、多任务互斥，多个任务同时读写容易数据错乱。
    2.队列：FreeRTOS提供的内核对象，自带阻塞等待、线程安全，支持任务、中断互相传递消息；创建时指定长度与每个项目大小；支持FIFO/LIFO；内部完成数据拷贝。
    数组只是一块内存；队列是带完整读写逻辑的消息结构。

第33讲： 互斥信号量

  • 1.互斥信号量简介
    互斥信号量其实就是一个拥有优先级继承的二值信号量，在同步的应用中二值信号量最适合。互斥信号量适合用于那些需要互斥访问的应用中！

优先级继承：当一个互斥信号量正在被一个低优先级的任务持有时，如果此时有个高优先级的任务也尝试获取这个互斥信号量，那么这个高优先级的任务就会被阻塞。不过这个高优先级的任务会将低优先级任务的优先级提升到与自己相同的优先级。等任务A释放互斥锁时，它就恢复为原来的优先级,互斥锁内部就实现了优先级的提升、恢复。

  • 2.优先级继承示例

优先级继承并不能完全的消除优先级翻转的问题，它只是尽可能的降低优先级翻转带来的影响

注意：互斥信号量不能用于中断服务函数中，原因如下：
(1) 互斥信号量有任务优先级继承的机制，但是中断不是任务，没有任务优先级，所以互斥信号量只能用与任务中，不能用于中断服务函数。
(2) 中断服务函数中不能因为要等待互斥信号量而设置阻塞时间进入阻塞态。

使用互斥量可以解决这个问题，互斥量的名字取得很好：

量：值为0、1
互斥：用来实现互斥访问
它的核心在于：谁上锁，就只能由谁开锁。

  • 它的每一个位表示一个事件（高8位不算）
  • 每一位事件的含义，由用户自己决定，如：bit0表示按键是否按下，bit1表示消息……

  • 任意任务或中断都可以读写这些位
  • 可以等待某一位成立，或者等待多位同时成立

    任务通知的优势：
  • 效率更高：使用任务通知向任务发送事件或数据比使用队列、事件标志组或信号量快得多
  • 使用内存更小：使用其他方法时都要先创建对应的结构体，使用任务通知时无需额外创建结构体

任务通知的劣势：

  • 无法发送数据给ISR：ISR没有任务结构体，所以无法给ISR发送数据。但是ISR可以使用任务通知的功能，发数据给任务。

  • 无法缓存多个数据：任务通知是通过更新任务通知值来发送数据的，任务结构体中只有一个任务通知值，只能保持一个数据。
  • 发送受阻不支持阻塞：发送方无法进入阻塞状态等待

第43讲: 软件定时器

下载：FreeRTOS软件定时器知识点框架PDF

  • 1.定时器简介
    1，软件定时器的简介（了解）

  • 定时器：
    从指定的时刻开始，经过一个指定时间，然后触发一个超时事件，用户可自定义定时器的周期

  • 硬件定时器：
    芯片本身自带的定时器模块，硬件定时器的精度一般很高，每次在定时时间到达之后就会自动触发一个中断，用户在中断服务函数中处理信息。

  • 软件定时器：
    是指具有定时功能的软件，可设置定时周期，当指定时间到达后要调用回调函数（也称超时函数），用户在回调函数中处理信息

  • 2.软件定时器优缺点
    优点：
  • 硬件定时器数量有限，而软件定时器理论上只需有足够内存，就可以创建多个；
  • 使用简单、成本低

缺点：

  • 软件定时器相对硬件定时器来说，精度没有那么高（因为它以系统时钟为基准，系统时钟中断优先级又是最低，容易被打断）。对于需要高精度要求的场合，不建议使用软件定时器。
  • 3.FreeRTOS软件定时器特点

  • 可裁剪
    软件定时器是可裁剪可配置的功能，如果要使能软件定时器，需将configUSE_TIMERS配置项配置成1

  • 单次和周期
    软件定时器支持设置成：单次定时器或周期定时器

  • 注意：软件定时器的超时回调函数是由软件定时器服务任务调用的，软件定时器的超时回调函数本身不是任务，因此不能在该回调函数中使用可能会导致任务阻塞的API函数。

  • 软件定时器服务任务：在调用函数vTaskStartScheduler()开启任务调度器的时候，会创建一个用于管理软件定时器的任务，这个任务就叫做软件定时器服务任务。

软件定时器服务任务作用
1、负责软件定时器超时的逻辑判断
2、调用超时软件定时器的超时回调函数
3、处理软件定时器命令队列

  • 4.软件定时器命令队列

FreeRTOS 提供了许多软件定时器相关的 API 函数，这些 API 函数大多都是往定时器的队列中写入消息（发送命令），这个队列叫做软件定时器命令队列，是提供给 FreeRTOS 中的软件定时器使用的，用户是不能直接访问的。

  • 5.软件定时器相关配置
  • 当FreeRTOS 的配置项 configUSE_TIMERS 设置为1，在启动任务调度器时，会自动创建软件定时器的服务/守护任务prvTimerTask();
  • 软件定时器服务任务的优先级为 configTIMER_TASK_PRIORITY = 31;
  • 定时器的命令队列长度为 configTIMER_QUEUE_LENGTH = 5;

注意：软件定时器的超时回调函数是在软件定时器服务任务中被调用的，服务任务不是专为某个定时器服务的，它还要处理其他定时器。

所以，定时器的回调函数不要影响其他“人”：
1、回调函数要尽快实行，不能进入阻塞状态，即不能调用那些会阻塞任务的 API 函数，如：vTaskDelay()
2、访问队列或者信号量的非零阻塞时间的 API 函数也不能调用。

休眠态：软件定时器可以通过其句柄被引用，但因为没有运行，所以其定时超时回调函数不会被执行

运行态：运行态的定时器，当指定时间到达之后，它的超时回调函数会被调用

注意：新创建的软件定时器处于休眠状态，也就是未运行的！

  • 内存碎片化
  • ……

第49讲: 中断管理

1.中断管理简介

  • 1.中断管理简介
    在RTOS中，需要应对各类事件。这些事件很多时候是通过硬件中断产生，怎么处理中断呢？
    假设当前系统正在运行Task1时，用户按下了按键，触发了按键中断。这个中断的处理流程如下：
    • CPU跳到固定地址去执行代码，这个固定地址通常被称为中断向量，这个跳转时硬件实现的
    • 执行代码做什么？
      • 保存现场：Task1被打断，需要先保存Task1的运行环境，比如各类寄存器的值
      • 分辨中断、调用处理函数(这个函数就被称为ISR，interrupt service routine)
      • 恢复现场：继续运行Task1，或者运行其他优先级更高的任务

你要注意到，ISR是在内核中被调用的，ISR执行过程中，用户的任务无法执行。ISR要尽量快，否则：
- 其他低优先级的中断无法被处理：实时性无法保证
- 用户任务无法被执行：系统显得很卡顿

如果这个硬件中断的处理，就是非常耗费时间呢？对于这类中断的处理就要分为2部分：
- ISR：尽快做些清理、记录工作，然后触发某个任务
- 任务：更复杂的事情放在任务中处理
- 所以：需要ISR和任务之间进行通信

要在FreeRTOS中熟练使用中断，有几个原则要先说明：
- FreeRTOS把任务认为是硬件无关的，任务的优先级由程序员决定，任务何时运行由调度器决定
- ISR虽然也是使用软件实现的，但是它被认为是硬件特性的一部分，因为它跟硬件密切相关
-何时执行？由硬件决定
-哪个ISR被执行？由硬件决定
- ISR的优先级高于任务：即使是优先级最低的中断，它的优先级也高于任务。任务只有在没有中断的情况下，才能执行。

2.两套API函数

  • 1.两套API函数
    在任务函数中，我们可以调用各类API函数，比如队列操作函数：xQueueSendToBack。但是在ISR中使用这个函数会导致问题，应该使用另一个函数：xQueueSendToBackFromISR，它的函数名含有后缀”FromISR”，表示”从ISR中给队列发送数据”。

FreeRTOS中很多API函数都有两套：一套在任务中使用，另一套在ISR中使用。后者的函数名含有”FromISR”后缀。

为什么要引入两套API函数？
- 很多API函数会导致任务计入阻塞状态：
- 运行这个函数的 任务 进入阻塞状态
- 比如写队列时，如果队列已满，可以进入阻塞状态等待一会
- ISR调用API函数时，ISR不是”任务”，ISR不能进入阻塞状态
- 所以，在任务中、在ISR中，这些函数的功能是有差别的

5.中断的延迟处理

前面讲过，ISR要尽量快，否则：
- 其他低优先级的中断无法被处理：实时性无法保证
- 用户任务无法被执行：系统显得很卡顿
- 如果运行中断嵌套，这会更复杂，ISR越快执行约有助于中断嵌套

如果这个硬件中断的处理，就是非常耗费时间呢？对于这类中断的处理就要分为2部分：
- ISR：尽快做些清理、记录工作，然后触发某个任务
- 任务：更复杂的事情放在任务中处理

这种处理方式叫”中断的延迟处理”(Deferring interrupt processing)，处理流程如下图所示：
- t1：任务1运行，任务2阻塞
- t2：发生中断，
- 该中断的ISR函数被执行，任务1被打断
- ISR函数要尽快能快速地运行，它做一些必要的操作(比如清除中断)，然后唤醒任务2
- t3：在创建任务时设置任务2的优先级比任务1高(这取决于设计者)，所以ISR返回后，运行的是任务2，它要完成中断的处理。任务2就被称为”deferred processing task”，中断的延迟处理任务。
- t4：任务2处理完中断后，进入阻塞态以等待下一个中断，任务1重新运行

怎么判断栈溢出？有两种方法：

方法1：

  • 当前任务被切换出去之前，它的整个运行现场都被保存在栈里，这时 很可能 就是它对栈的使用到达了峰值。

  • 创建任务时，它的栈被填入固定的值，比如：0xa5
  • 检测栈里最后16字节的数据，如果不是0xa5的话表示栈即将、或者已经被用完了
  • 没有方法1快速，但是也足够快

  • 2.任务运行时间统计
    对于同优先级的任务，它们按照时间片轮流运行：你执行一个Tick，我执行一个Tick。
    是否可以在Tick中断函数中，统计当前任务的累计运行时间？
    不行！很不精确，因为有更高优先级的任务就绪时，当前任务还没运行一个完整的Tick就被抢占了。

我们需要比Tick更快的时钟，比如Tick周期时1ms，我们可以使用另一个定时器，让它发生中断的周期时0.1ms甚至更短。
使用这个定时器来衡量一个任务的运行时间：

  • Task1被切换出去时，使用更快的定时器记录当前时间T4
  • (T4-T1)就是它运行的时间，累加起来
  • 关键点：在 vTaskSwitchContext 函数中，使用 更快的定时器 统计运行时间
